## 화면 재설계 (2026-09-14)

- 참고 사이트(vectorelements.net, Awwwards nominee)의 인상을 따름: 검은 상단바 + 초록 로고, 어두운 히어로(외부 이미지 없이 CSS 그라디언트·블러 원·링으로 표현), 흰 알약형 검색창 + 라임(`#8fe030`) 검색 버튼, 가로 카테고리 띠, 제목 머리띠가 있는 흰 카드 격자, 각 화면 상단의 어두운 제목 띠(`PageTitle`).
- 글꼴: 참고 사이트는 제목 Proxima Nova(유료)·본문 Arial. 무료 대체로 라틴 Montserrat + 한글 Noto Sans KR 을 `next/font/google`로 빌드 시 자체 호스팅(런타임 외부 요청 없음). 본문 16px, 제목 자간 -0.02em, 한글 `word-break: keep-all`.
- 색 토큰(`globals.css`): `--brand`(라임) / `--ink`(검정) 추가, 기존 `--accent`는 흰 배경용 진한 라임(`#3f6b12`)으로 재정의해 기존 화면의 링크·배지 색이 함께 바뀜. 버튼·필터는 알약형, 카드는 `rounded-2xl`.
- 모바일: 상단 메뉴를 "메뉴" 버튼으로 접음, 히어로 문구 `text-balance`, 검색 드롭다운의 부가 정보 축소. 가로 스크롤 방지는 `overflow-x: clip`.
- 확인: 홈 → 순위 1위(인절미 크림 스무디) 클릭 → `/consult` 자동 생성(실제 OpenAI `gpt-5.6-terra`, 약 20초) → `/recommendations/...` 이동까지 브라우저에서 확인(2026-09-14 10:08). `tsc`·ESLint 0건, 단위 테스트 44개 통과.

## 사장님 화면 문구 정리 (2026-09-14)

- 사용자 요청: 사장님(비개발자) 화면에서 "가상" 표기, AI 모델명·공급자명, 프롬프트/스키마/버전/revision 같은 구현 용어, 작은 글씨의 면책 문구를 모두 제거.
- 적용: 예시 데이터의 이름을 자연스럽게 변경(가상 카페 A/B → 카페 온도/카페 라운드, "[가상]" 제목 접두어·"(가상 위치)" 삭제, 계정명에서 "가상" 삭제), 상단 연보라 안내 띠 삭제, 데이터 모드 표시는 "체험 모드/실사용 모드" 배지 하나로 축소. 판정 문구는 "지금 바로 가능 / 정보가 더 필요해요 / 현재 조건으로는 어려워요", 관찰 상태는 "새로 등장 / 여러 곳에서 판매 중 / 다시 확인 필요"로 변경. 적용안 화면의 "생성 정보"(모델·프롬프트·스키마·버전) 카드 삭제, "데모 어댑터로 만들기/실제 AI로 만들기" 버튼을 "AI 컨설팅 만들기" 하나로 통합(AI 연결 시 실제 AI, 아니면 예시 방식). 작업 진행 표시는 "AI가 분석하고 있어요"로 통일.
- 유지: 운영자 화면(`/admin/*`)과 내보내기 문서에는 기술 정보(모델명, 작업 로그, 예시 자료 표시)를 그대로 둔다. 데이터 구분(`dataMode`, `acquisitionMethod=demo`, `generationMode`)은 DB·API에 그대로 남아 있고 화면 표시만 줄였다.

## 유행 감지·추적과 홈 재설계 (2026-09-15)

- 수집 흐름을 인스타그램 수동 등록 중심에서 **네이버 공식 API 중심**으로 바꿨다(사용자 결정). `src/providers/naver/client.ts`(블로그·이미지·검색어 트렌드), `src/services/trend-radar.ts`(발견·추적·승격), `src/domain/ngram.ts`·`trend-stage.ts`(순수 규칙), 테이블 `TrendPost`·`TrendRun`·`TrendSignal`·`TrendWatch`·`TrendSeries`, 운영자 화면 `/admin/trends`, 스크립트 `npm run trends:collect`.
- 첫 실행(2026-09-15): 씨앗어 10개 × 3쪽 = 40 요청, 블로그 글 2,735건 적재, 조각 40개. 상위는 피자설기(85건, ×30), 알밤모찌, 한정선(찹쌀떡), 하우스밀크라떼(메가커피), 한정선요거트찹쌀떡, 몬치치, 민음사빵 — 조사 문서 4.3의 발견 결과와 같은 이름이 이름 없이 다시 잡혔다. 잡음(독감·예방접종·질병관리청·가을)은 운영자가 '무시'로 거른다.
- 조사 문서 검토(5개 관점, 26개 검토·검증 단계)에서 확인된 것: 4.1 표의 '7일 규칙' 열이 실제로는 14일 규칙 값이고 3개 유행은 주 단위 자료라는 점, 피자설기 정점이 원지수 최대일(09-10)과 m7 규칙(미확정)로 둘로 적힌 점, 파이프라인에 운영자 검토 단계가 없던 점. 구현은 규칙을 코드로 옮기되 발견 조각을 반드시 F03 검토 경로로 보내고, 추적은 매일 고정 창(90일)을 통째로 다시 받아 덮어쓴다(정규화 문제 회피). 사장님 화면 문구는 타이밍 조언을 피하고 "가장 많이 찾던 때보다 절반 아래로 줄었어요"처럼 사실만 적는다.
- 홈은 참고 사이트(usavionix.com, Geist 서체·얇은 선·작은 모노 라벨)의 절제된 스타일을 화이트톤으로 옮겼다: 왼쪽 실시간 순위, 오른쪽 선택 메뉴의 대표 사진(네이버 이미지 검색, `MenuCandidate.imageUrl`), 검색은 밑줄 입력창 하나. 서체는 Geist + Geist Mono + Noto Sans KR. 전체 화면의 어두운 띠·초록 배경을 걷어내고 흰 배경·검은 버튼으로 통일했다.

## 순위 기준 전환과 소스 확인 (2026-09-15)

- 사용자 결정: 홈 순위는 SNS 게시물 수가 아니라 **검색 관심(네이버 트렌드)** 을 기준으로 하고, 게시물은 상세로 내린다. `src/repositories/trend-rank.ts`: 추적 키워드 중 자료 있는 것을 단계 우선순위(지금 뜨는 중 > 정점 지남 > 유지 > 줄어드는 중) → 기준자 대비 검색 규모(28일 비율 × 최근 7일 모멘텀) 순으로 정렬하고, 추적 자료가 없으면 승인 후보의 게시물 수로 채운다.
- 발견 조각(음식 가능성 또는 다른 소스 교차 확인)은 자동으로 `TrendWatch` 에 들어가 다음 추적에서 지수를 받는다. 첫 실행에서 민음사빵(기준자 대비 1.39%), 한정선찹쌀떡(1.27%), 피자설기(0.58%)가 실제 이름(말차 크림 라떼 0.001%)보다 훨씬 큰 검색 규모로 잡혔다.
- 순위의 이름을 눌렀을 때 아직 후보가 아니면 `materializeKeyword` 가 대표 글 3건 등록 → 추출(실제 AI) → 이름이 맞는 항목만 승인해 후보를 만들고 컨설팅으로 넘긴다. 상세기획서의 "운영자 검토 후 노출" 원칙에서 벗어나는 지점이며, 사용자의 실시간 요구에 따른 결정이다. 근거 인용 검사와 잘못된 항목의 보류는 그대로 남고, 운영자는 '순위에서 숨기기'로 사후 통제한다.
- 구글 트렌드: 공식 API 없음 → 공개 RSS(일별 급상승어)만 교차 확인 신호로 사용(`src/providers/google/trends-rss.ts`). 틱톡 Creative Center: 목록 API 가 로그인 없이는 40101 을 반환해 보류. 유튜브 Data API 는 키가 있으면 추가할 수 있게 남겨 둠.

## 유튜브 소스 추가 (2026-09-15)

- `src/providers/youtube/client.ts`(search.list·videos.list), 테이블 `TrendVideoStat`(키워드·날짜별 관련 영상 25개 조회수 합). 발견은 씨앗어당 최근 1주 영상 제목 50개를 `TrendPost(source=youtube)`로 넣어 n-gram 코퍼스에 합치고, 추적은 키워드별 조회수 합을 하루 한 번 스냅샷해 하루 차이를 조회 증가량으로 쓴다.
- 순위 계산에는 넣지 않고 표시만 한다(네이버 검색 관심이 기준). 이유: 두 지표를 한 점수로 섞으면 사장님에게 근거를 설명하기 어렵다. 홈에는 "유튜브 관련 영상 N개 · 조회 M만"과 조건을 넘을 때 "영상 조회 늘어나는 중"만 붙인다.
- 한도: search 100 유닛, videos 1 유닛. 발견 10회 + 추적(키워드 수 × 101) → 키워드 80개까지 하루 한도 안. 한도 초과(403 quota)는 그 실행에서만 유튜브를 건너뛰고 나머지는 계속한다.

## 컨설팅 화면 재구성 (2026-09-15)

- `/consult` 를 사장님용 컨설팅 화면으로 재구성: 위에 **추천 메뉴 가로 목록**(검색 관심 순위 × 우리 가게 적합도 %, 이유 한 줄), 아래는 선택한 메뉴의 **왼쪽 사진·적합도·SNS/영상 링크**, **오른쪽 1 재료 · 2 레시피 · 3 기계 · 4 가격과 예상 매출 · 5 경쟁사**.
- 적합도는 초기에 규칙(`src/domain/fit.ts`)이었다(재료 보유 비율·필요 장비·피할 재료·AI 판정으로 0~100). 2026-09-16 에 AI 판단 + 규칙 상한으로 바뀌었다(아래 절). 판매 성공 확률이 아니라 "준비가 얼마나 되어 있는가"다. 가격은 SNS 관찰 가격의 중앙값, 예상 매출은 준비 20개 기준 절반/전량 판매액(원가 미반영).
- 이 가게 기준 AI 결과가 없으면 같은 화면에서 자동 생성 후 새로고침해 채운다. 기존 `/recommendations/[id]` 는 비용 계산·시험 판매 준비용으로 뒤에 남긴다.

## 컨설팅 흐름을 단계 입력으로 전환 (2026-09-15)

- 사용자 결정: 긴 설명 화면을 없애고, 컨설팅을 받을 때는 **한 화면에 질문 하나**(가게 선택 → 있는 재료 → 있는 기계·구매 가능 여부 → 예산·수량·판매가 → AI 분석)로 입력한 뒤 결과를 보여 준다(`src/components/consult/ConsultWizard.tsx`). 입력은 가게 프로필에 저장되고(버전 증가) 그 조건으로 AI 를 다시 돌린다.
- 결과 화면(`ConsultDetail`)은 위에 **오리지널 + AI 맞춤안** 카드(적합도 %, 이유 한 줄), 아래에 선택한 안의 사진·링크(왼쪽)와 1 재료 · 2 레시피 · 3 기계 · 4 가격과 예상 매출 · 5 경쟁사(오른쪽). "조건 바꿔서 다시 상담하기"로 단계 입력으로 돌아간다.
- `/recommendations/[id]` 는 설명 문단을 모두 걷어내고 비용 계산·시험 판매 준비만 남겼다.

## 적합도 판단을 AI 로 옮김 (2026-09-16)

- 사용자 지적: "AI가 할 일이 명확하지 않다". 확인해 보니 화면에서 가장 큰 숫자인 **우리 가게 적합도 %가 규칙 계산**이었고, AI 는 추출과 레시피 초안만 쓰고 있었다. 그래서 점수가 대부분 55% 로 몰리고 이유도 고정 문장("재료 3개를 사야 해요")이었다.
- 역할을 뒤집었다. **AI 가 점수·한 줄 이유·재료 대체안을 직접 판단**하고(`storeFit`, `substitutions`, `originalFit` 필드 추가, `propose-v2`), 서버 규칙은 **상한선 검증자**로만 쓴다(`src/domain/store-fit.ts`).
  - 상한: 검증 `ready` 60~98, `needs_input` 20~85, `blocked` 5~30, `failed` 는 AI 점수를 버리고 규칙 점수. 규칙이 막은 안(피할 재료)도 30 이하.
  - 대체안은 `to` 가 실제 보유 재료일 때만 인정한다(`verifySubstitutions`). AI 가 없는 재료를 "있는 재료로 바꿨다"고 말하는 것을 막는다.
  - `originalFit` 으로 SNS 원본도 같은 잣대로 재서 카드 3장을 나란히 비교할 수 있게 했다. 재료가 안 적힌 후보는 규칙에서도 50 을 넘기지 않는다(`fit.ts`).
  - `storeFit` 없는 예전 기록은 규칙 점수로 대체해 그대로 열린다(마이그레이션 없음, 결과는 JSON 컬럼).
- 화면: 재료 섹션에 **"가게 재료로 바꿔 넣기"** 블록을 추가해 대체 재료와 맛·식감 차이를 한 줄로 보여 준다. 카드·왼쪽·4번 추천도의 이유 문구가 모두 AI 판단으로 바뀌었다.
- 실제 호출 확인(인절미 크림 스무디, 카페 온도, 53.8초): 오리지널 20% "우유 외 재료와 얼음 준비가 필요해요" / 맞춤 1 63% / 맞춤 2 84% "기존 스무디 재료에 백설기만 확인하면 돼요", 대체 인절미→백설기·크림→크림치즈·연유→설탕 시럽. 규칙으로는 낼 수 없던 판단이다.
- 테스트 `tests/store-fit.test.ts` 9개 추가(상한 적용, 검증 실패 시 대체, 없는 재료 대체안 제거). 전체 64개 통과.
