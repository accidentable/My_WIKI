# 해외결제 분쟁 첫 72시간 에이전트 — 아이디어 설명서 ver2

2026 금융 AI Challenge · 2026-09-05 · 아이디어 및 MVP 제안

## 한 문장

해외 디지털 서비스의 이상 청구를 겪은 이용자에게, 청구 메일과 결제 내역을 바탕으로 **지금 필요한 대응 → 부족한 증빙 → 근거가 있는 이의제기 초안**을 제공하고, 새 회신이 오면 다음 행동을 갱신하는 AI 에이전트.

‘첫 72시간’은 사건을 인지한 직후의 대응을 돕는 서비스 범위다. 법정·카드사 신청기한이나 72시간 내 해결 보장을 뜻하지 않으며, 긴급한 조치는 즉시 안내한다.

## 1. 문제 — 결제 문제를 발견한 사람에게는 실행 순서가 없다

이상 청구를 발견한 이용자는 먼저 이것이 청구서인지, 승인 시도인지, 실제 매입된 거래인지부터 구분해야 한다. 이어 사업자에게 무엇을 요구할지, 카드사에는 어떤 내용으로 연락할지, 어떤 증빙을 보존해야 하는지 판단해야 한다. 해외 고객지원의 언어 장벽과 응답 지연까지 겹치면 이 과정을 혼자 수행하기 어렵다.

핵심 문제는 **사업자와의 대화, 카드 거래 상태, 제출 증빙이 서로 분리되어 있다는 것**이다. 서비스는 이를 하나의 사건으로 연결해 다음 행동을 구체화한다.

### 사례 A. 국내 AI 이용자에게 251억 원대 청구와 반복 결제 시도

SBS는 2026년 7월 18일, 국내 클로드 이용자가 약 25억 원의 청구 이메일을 받은 뒤 청구액이 251억 원대로 커진 사례를 보도했다. 카드 결제는 열 차례 넘게 시도됐으나 거절됐고, 이용자는 카드를 정지했다. 보도에 따르면 이용자는 이메일 18건을 보낸 뒤 사흘 만에 AI 응답으로 추정되는 답변을 받았다. 앤트로픽은 이용자와 소통했으며 해결을 완료했다고 밝혔다. **실제 251억 원이 결제된 피해 사례로 표현하지 않는다.** [SBS 원보도, 2026-07-18](https://news.sbs.co.kr/news/endPage.do?news_id=N1008663338)

이 사례에서 서비스가 제공할 가치는 청구서와 승인 거절을 구분하고, 카드사 추가 결제 방지 상담과 사업자 청구 정정 요청을 함께 준비하는 것이다. 시스템 오류의 원인이나 환불 권리를 AI가 확정하지 않는다.

### 사례 B. Gemini API 키 악용으로 48시간에 8만 달러대 비용이 발생했다는 신고

Tom’s Hardware는 2026년 3월 4일, 평소 월 약 180달러를 쓰던 개발팀이 2월 11~12일 사이 82,314.44달러의 비용을 겪었다는 이용자 주장을 보도했다. 기사에 따르면 이용자는 키 폐기, API 비활성화, 자격증명 교체 및 지원 문의를 진행했다. **Reddit 이용자의 신고에 기반한 보도이며, 과금 책임·최종 납부액·환불 결과를 독립적으로 확정한 자료는 아니다.** [관련 보도](https://www.tomshardware.com/tech-industry/artificial-intelligence/gemini-api-key-thief-racks-up-usd82-314-in-charges-in-just-two-days-victim-facing-bankruptcy-affected-devs-call-for-basic-guardrails-against-catastrophic-usage-anomalies)

이 사례는 API 키 악용과 카드정보 도용을 구분해야 함을 보여준다. 서비스는 사업자의 사용량 조사와 청구 검토에 필요한 자료를 안내하고, 카드사 분쟁 가능성은 실제 거래 상태와 적용 요건을 확인한 뒤 검토한다. 구체적인 키 유출 경로나 자동 환불 가능성을 추정하지 않는다.

### 사례 C. 구독 해지를 마쳤다고 생각했지만 계속 청구된 문제

미국 FTC는 2024년 6월 Adobe의 구독 해지 절차와 수수료 고지를 문제 삼아 소송 제기를 발표했다. 공식 발표에는 해지를 완료했다고 생각한 일부 소비자가 이후에도 청구를 발견했다는 내용이 포함되어 있다. 이는 **당국이 제기한 주장과 소비자 신고를 설명하는 자료이며, 이 문서에서 위법 확정 판결로 취급하지 않는다.** [FTC 공식 발표, 2024-06-17](https://www.ftc.gov/news-events/news/press-releases/2024/06/ftc-takes-action-against-adobe-executives-hiding-fees-preventing-consumers-easily-cancelling)

이 경우 중요한 것은 해지 요청일, 실제 해지 효력 발생일, 계약 형태, 후속 청구일을 구분하는 일이다. ‘해지했는데 청구됐다’는 한 문장만으로 부당 청구를 단정하지 않고 확인 메일과 계약 내용을 대조한다. 미국 사례를 한국 이용자의 환불 권리에 그대로 적용하지 않는다.

### 시장 배경과 해석 범위

2026년 6월 9일 금감원 발표를 인용한 보도에 따르면 신용카드 민원은 2022년 6,720건에서 2025년 12,661건으로 88.4% 증가했다. **전체 신용카드 민원 수치이며, 해외결제 또는 AI 과금 분쟁만의 증가율은 아니다.** 본 문서는 금감원 원문 대신 해당 보도를 인용한다. [머니투데이 보도](https://v.daum.net/v/20260609120135371)

위 사례들은 대응 부담이 존재함을 뒷받침한다. 국내 목표 시장 규모, 발생 빈도, 사용자의 지불 의사까지 입증하는 자료로 사용하지는 않는다.

## 2. 대상 사용자와 초기 범위

첫 대상은 해외 AI·SaaS·디지털 구독을 직접 결제한 국내 개인 이용자다. 해지 후 계속 청구, 중복 청구 의심, 고액 청구·승인 거절을 우선 지원한다.

개인 개발자의 API 과금 문제는 초기 사실 정리와 사업자 문의 준비까지 지원한다. 소규모 팀·사업용 계약은 별도로 구분하고, 소비자원 등 외부 경로의 대상 여부를 자동으로 보장하지 않는다.

해외직구 미배송·반품, 여행 취소, 전 브랜드·전 카드사 대응은 후속 범위다. MVP는 **카드 브랜드 1개와 국내 카드사 1~2개의 검증 가능한 안내**로 제한한다. 구체적인 지원 목록은 개발 첫날 자료 검증 후 확정해 화면에 표시한다.

## 3. 해결 방법 — 입력 한 번으로 시작하고, 필요한 정보만 추가로 묻는다

청구 이메일·카드 알림·상황 설명을 붙여넣으면 다음 과정을 수행한다. 입력만으로 확정할 수 없는 부분은 질문으로 보완한다.

| 단계 | 수행 내용 | AI와 규칙의 역할 |
|---|---|---|
| 1. 사건 구조화 | 사업자, 금액·통화, 거래별 날짜, 청구서·승인·거절·매입·취소 상태 추출 | AI 추출 후 사용자 확인. 상태 미상 허용 |
| 2. 긴급 대응 분리 | 반복 결제 시도, 계정·API 키 악용 의심, 실제 청구 여부 확인 | 검증한 조건에 따라 즉시 행동 안내 |
| 3. 정보·증빙 확인 | 계약 형태, 해지 효력일, 거래 내역, 사업자 회신 등 부족한 정보 질문 | AI가 입력 자료와 요구 항목 대조 |
| 4. 근거와 기한 검토 | 지원 범위 내 규정 검색, 적용 조건과 기준일 확인 | 검증한 규칙으로만 날짜 계산. 불명확하면 보류 |
| 5. 경로별 행동 정리 | 사업자 문의, 카드사 상담·분쟁 접수, 소비자상담 경로의 조건과 우선순위 | AI가 설명하고 규칙으로 금지된 단정 차단 |
| 6. 초안 작성·갱신 | 영문 사업자 문의, 국문 사실관계 진술, 증빙 타임라인 생성 | 확인된 사실만 작성. 새 회신을 넣으면 변경 이유와 다음 행동 갱신 |

서류 발송·접수, 카드 정지, API 키 폐기 같은 외부 행동은 사용자가 수행한다. 에이전트는 공식 경로와 필요한 준비물을 제공한다.

### 출력의 기본 형태

- **현재 확인된 상태:** 예) 승인 거절 알림 확인, 매입 내역은 미확인.
- **지금 할 일 3개:** 이유, 공식 접점, 준비물과 함께 표시.
- **경로별 상태:** 준비 가능 / 추가 확인 필요 / 현재 자료로 대상 거래 미확인 / 지원 범위 밖.
- **증빙 목록:** 보유·누락·확인 필요를 구분하고 각 항목의 용도 표시.
- **기한:** 검증된 경우 기준일·계산 근거·남은 날짜 표시. 미확정이면 필요한 날짜와 카드사 확인 항목 표시.
- **초안:** 사실마다 근거 자료를 연결하고 미확인 사항은 빈칸 또는 질문으로 남김.

## 4. 판단 원칙 — 확정할 수 없는 것은 보류한다

### 카드사 상담과 차지백을 분리한다

승인 거절이나 청구서만 있는 사건도 카드사에 반복 시도 차단·해외사용 설정 등을 문의할 필요가 있다. 따라서 ‘승인 없음 → 카드사 경로 불가’ 규칙은 사용하지 않는다. 실제 매입된 거래에 대한 분쟁 검토와 추가 결제 방지 상담을 따로 표시한다. 카드 차단만으로 사업자 계약이나 청구 문제가 해소됐다고 판단하지 않는다.

### 기한은 사유와 기준일을 확인한 뒤 계산한다

모든 사건을 승인일에 120일을 더해 처리하지 않는다. 브랜드·분쟁 사유·거래 유형에 따라 기준일과 조건이 다를 수 있다. Mastercard 공개 가이드에도 특정 사유에서 서비스 예정일을 기준으로 하는 규정이 나타난다. [Mastercard 공개 가이드](https://www.mastercard.com/content/dam/mccom/shared/business/support/rules-pdfs/chargeback-guide.pdf)

규정의 발행·적용일, 적용 지역과 거래 유형, 필요한 날짜, 카드사 접수 안내를 확인한다. 브랜드사의 절차상 기한을 소비자가 그날까지 기다려도 되는 마감으로 제시하지 않는다. 사유코드는 검증한 후보로만 표시하고, 최종 적용은 카드사 확인이 필요함을 알린다.

### 도메인 대조를 발신자 인증으로 표현하지 않는다

입력에서 발견한 도메인·링크를 공식 목록과 비교하되, 결과는 일치 / 불일치 / 정보 부족으로 표시한다. 복사한 본문만으로 SPF·DKIM·DMARC 검증이나 피싱 여부를 확정할 수 없다. 링크는 공식 경로를 직접 제시하고 ‘정상 메일 인증 완료’ 문구는 사용하지 않는다. [IETF 메일 인증 문서](https://datatracker.ietf.org/doc/html/rfc7489.html)

### 과금 통제 기능도 서비스·시점별로 구분한다

Google Cloud 공식 문서는 알림 전용 예산이 사용량을 자동 차단하지 않는다고 설명한다. 한편 현재는 지원 서비스에 대한 Spend cap 예산도 제공하며, 적용 범위와 집행 지연 등의 제한을 설명한다. 따라서 ‘예산 상한은 작동하지 않는다’고 일반화하지 않는다. 사건 당시 설정이 알림인지 차단인지, 서비스와 프로젝트 범위가 맞는지 확인하도록 안내한다. [알림 예산 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets) · [Spend cap 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)

## 5. AI의 역할과 차별성

AI는 서로 다른 형식의 자료에서 사건을 구조화하고, 빠진 정보를 질문하고, 다국어 초안을 작성하는 데 사용한다. 날짜 산술, 필수 항목 검사, 지원 범위 검사는 코드로 처리한다. AI가 추출한 날짜나 상태 자체가 틀릴 수 있으므로 계산 전에 확인할 수 있게 한다.

범용 AI도 번역과 초안 작성을 할 수 있다. 우리의 차별성은 다음을 제품 차원에서 일관되게 제공하고 검증하는 데 있다.

1. **근거가 남는 판단:** 결론마다 규정 출처·버전·적용 조건·입력 증빙을 연결한다.
2. **누락을 찾는 질문:** 없는 사실을 채워 쓰지 않고 판정에 필요한 정보만 요청한다.
3. **사건의 연속성:** 추가 자료가 들어오면 기존 결론과 달라진 부분을 표시한다.
4. **접수 준비 완성도:** 제출 초안과 증빙 목록이 같은 사실관계와 타임라인을 사용한다.

에이전트성은 고정된 여섯 단계 애니메이션이 아니라, 자료에 따라 질문과 다음 행동이 달라지는 과정으로 보여준다. 예를 들어 해지 요청 메일만 있을 때는 효력일을 질문하고, 확인 메일이 추가되면 후속 청구와 대조해 안내를 갱신한다.

Visa 등에는 금융기관·사업자용 AI 분쟁 도구가 이미 존재한다. 본 서비스는 국내 이용자가 접수 전에 자료를 준비하는 구간을 초기 진입점으로 삼는다. 독점적 기술이나 ‘최초’ 주장은 하지 않는다. [Visa 분쟁 도구 발표, 2026-04-01](https://usa.visa.com/about-visa/newsroom/press-releases.releaseId.22261.html)

## 6. 해커톤 데모 — 합성 시나리오 3종

아래 이름·금액·날짜는 모두 시연용 가상 데이터다. 앞의 실제 보도 당사자나 사업자의 거래 내역을 재현한 것이 아니다.

### A. 해지 후 계속 청구 — 질문과 증빙 추가로 결론이 바뀌는 장면

- 입력: 가상 서비스 AlphaWrite에 8월 20일 해지를 요청했고 9월 1일 29달러가 청구됐다는 설명.
- 첫 응답: 해지 요청일과 효력일은 다를 수 있어, 계약 형태·확인 메일·매입 내역을 질문한다.
- 추가 입력: 8월 31일 종료 확인 메일과 9월 1일 매입 내역.
- 갱신: 후속 청구의 과금 대상 기간을 확인할 사업자 문의 초안을 만들고, 지원 카드사 안내에 맞춘 증빙 목록을 제시한다. 환불을 확정하지 않는다.
- 결과물: 영문 문의 초안, 국문 사실관계 진술, 해지·청구 타임라인.

### B. 중복 청구 의심 — 같은 금액 두 건을 바로 중복 결제로 단정하지 않는 장면

- 입력: 가상 서비스 BetaDesign의 49달러 알림 두 건.
- 첫 응답: 승인 알림과 매입 내역의 중복 표시인지, 실제 별도 매입 두 건인지 확인한다.
- 추가 입력: 서로 다른 거래 식별자를 가진 매입 두 건과 주문 한 건.
- 갱신: 중복 청구 검토 후보로 분류하고 사업자 정정 요청과 카드사 문의 자료를 준비한다. 확인되지 않은 사유코드는 생성하지 않는다.
- 결과물: 거래 비교표, 증빙 누락 목록, 정정 요청 초안.

### C. 고액 청구·승인 거절 — 돈이 빠져나가지 않아도 대응을 이어가는 장면

- 입력: 가상 서비스 GammaAI의 12,000달러 청구서와 반복 승인 거절 알림.
- 첫 응답: 실제 매입은 확인되지 않았다고 표시하고, 카드사 반복 시도 대응 상담·사업자 청구 근거 요청·자료 보존을 안내한다. 차지백 D-값은 표시하지 않는다.
- 추가 입력: 사업자의 청구서 취소 회신.
- 갱신: 청구서 취소는 기록하되, 다른 매입이나 재시도 여부는 별도 확인 항목으로 남긴다.
- 결과물: 긴급 행동 목록, 청구 정정 요청 초안, 상태 변경 이력.

API 키 악용 의심은 확장 시나리오로 두되, MVP에서도 입력되면 계정 보안 대응과 청구 검토를 분리해 안내하고 지원 범위 밖의 권리 판단을 보류한다.

## 7. 데이터와 보안 설계

- **규정 데이터:** 공식 브랜드 문서와 카드사·소비자기관 안내를 사람이 확인해 구조화한다. 해커톤 실행 중 임의 웹 검색 결과를 곧바로 판정 규칙으로 채택하지 않는다.
- **규정 레코드:** 출처 URL, 문서 버전·적용일, 확인일, 적용 조건, 필요 증빙, 날짜 기준, 지원 범위를 보관한다. 본 설명서는 구현할 규정의 검수 완료를 뜻하지 않는다.
- **데모 데이터:** 합성 텍스트만 사용한다. 실제 청구서 업로드와 실제 금융 계정 연동은 MVP에서 제공하지 않는다.
- **전송 전 확인:** 브라우저에서 카드번호·연락처·이름·주소·API 키·링크 토큰 등의 탐지와 마스킹을 수행하고 사용자가 전송 내용을 확인한다. 정규식만으로 완전 익명화를 보장하지 않는다.
- **저장 최소화:** 마스킹된 사건 요약과 필요한 이력만 저장한다. 서버 요청 본문·오류 로그·분석 도구에 원문이 남지 않도록 구현과 검증 항목에 포함한다. 사용자는 원본 증빙을 별도로 보관한다.
- **사건 접근:** 합성 데이터 데모는 무작위 사건 링크와 삭제 기능을 사용한다. 실제 서비스에는 접근 보호와 링크 폐기 기능이 필요하다.
- **보관 정책:** 데모 사건은 7일 후 자동 삭제한다. 실제 서비스의 보관기간은 별도 설계하며, 임의 기간을 ‘모든 분쟁의 최대 처리기간’으로 설명하지 않는다.
- **입력 신뢰 경계:** 이메일·회신 본문의 지시는 사건 자료로만 취급한다. AI가 해당 지시에 따라 규칙을 바꾸거나 외부 도구를 실행하지 않게 한다.

## 8. MVP 범위와 3일 구현 계획

**핵심 흐름:** 합성 사례 선택 또는 텍스트 입력 → 사실 확인 → 필요한 질문 → 행동·증빙 안내 → 초안 복사 → 사건 저장 → 회신 추가 → 변경 이유 표시.

기술 구성은 Next.js, Claude API, 구조화된 규정 파일, Upstash Redis, Vercel 배포를 제안한다. 기존 Vercel KV 대신 현재 제공되는 저장소 연동을 사용한다. [Vercel 공식 저장소 안내](https://github.com/vercel/storage/blob/main/README.md)

| 일정 | 구현 내용 | 완료 기준 |
|---|---|---|
| 1일 차 | 지원 자료 검증, 사건 상태·규정 스키마, 합성 사례·정답표, 입력 화면 | 세 시나리오의 필수 질문·허용 결론·보류 조건 정의 |
| 2일 차 | AI 추출·질문·초안, 규칙 검사, 출처·증빙 표시 | 사실을 추가 생성하지 않고 입력 부족 시 보류 |
| 3일 차 | 사건 저장·갱신, 삭제, 사용자 비교 평가, 배포·시연 점검 | 회신 추가에 따른 변화와 예외 상황을 재현 |

실제 카드사 접수 연동, 자동 메일 발송, 전 브랜드 규정 검색, 성공 확률 예측은 후속 단계다. 기한 규정을 검증하지 못한 조합은 날짜 계산 기능을 억지로 넣지 않고 카드사 확인 안내로 처리한다.

## 9. 검증 계획 — 환불 성공률 대신 접수 준비의 품질을 측정한다

아래는 목표이며 아직 달성한 실적이 아니다.

| 지표 | 검증 방법 | 초기 목표 |
|---|---|---|
| 잘못된 단정 | 거래 상태 미상·날짜 누락·해지 미완료 등 합성 예외 20건 | 평가 세트에서 근거 없는 기한·환불 확정 0건 |
| 사실 보존 | 입력 자료와 생성 서류 대조 | 금액·날짜·행동 이력의 임의 추가 0건 |
| 근거 연결 | 결론과 규정·증빙의 연결 검사 | 확정적으로 표시한 판단 모두에 근거 연결 |
| 준비 시간 | 사용자 5~10명, 비슷한 난도의 사례와 사용 순서를 바꿔 일반 AI와 비교 | 초안 준비 시간 중앙값 30% 감소 목표 |
| 증빙 누락 | 사전 정의한 체크리스트로 결과물 비교 | 일반 AI 대비 필수 증빙 누락 감소 |

비교 대상에는 동일한 규정 자료와 과제를 제공하고 모델·프롬프트 조건을 기록한다. 가능하면 카드 분쟁 실무 경험자의 검토를 받는다. 확보하지 못하면 내부 체크리스트 평가임을 명시한다. 소규모 합성 평가 결과를 실제 환불률이나 전체 정확도로 확대하지 않는다.

## 10. 사업화와 확장

초기에는 이용자가 초안을 준비하는 데 실제로 도움이 되는지 검증한다. 장기적으로는 카드사·핀테크의 접수 전 안내 기능으로 확장해 상담 시간, 증빙 보완 요청 횟수, 사건당 처리 비용 감소를 검증한다. 현재 카드사 제휴나 도입 의사가 확보된 상태는 아니다.

결과 데이터는 사업자 자발 환불, 카드사 분쟁 처리 결과, 사용자 취하, 미해결을 구분해 수집하는 방향으로 설계한다. 자발적 응답의 편향과 결과 검증 문제를 해결하기 전에는 성공 확률을 표시하지 않는다.

후속 범위는 카드사 접수 양식에 맞춘 내보내기, 동의 기반 메일 연동, 해외직구 유형 확대다. 상용화 전에는 실제 개인정보 처리와 맞춤형 분쟁 지원의 법적 범위를 별도 검토한다.
