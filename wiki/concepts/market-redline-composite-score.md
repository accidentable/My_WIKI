# 레드라인 근접도 합산 점수

## 1. 한 줄 정의

%, 포인트, 달러처럼 단위와 스케일이 다른 지표들을 하나의 숫자로 합치기 위해, 지표마다 "여기까지는 아무 일 없음"인 **safe**와 "여기 닿으면 만점"인 **redline** 두 값을 사람이 정하고, 그 사이를 선형 보간해 0~1점으로 바꾼 뒤 단순 합산하는 방식.

## 2. 어디서 썼는가

- [[taco-index-2026-03]]: TACO Index. S&P 선물 고점대비 하락률, VIX, 10년물 금리, WTI, 달러인덱스, 지지율 6개를 각각 0~1점으로 바꿔 만점 6.0으로 합산하고, 1.8 / 3.0 / 4.2를 경계로 레벨 1~4를 붙였다.

## 3. 어떻게 계산하나

방향(`direction`)이 `above`면 값이 클수록 위험, `below`면 작을수록 위험이다.

```python
if direction == "above":
    if value <= safe: return 0.0
    if value >= redline: return 1.0
    return (value - safe) / (redline - safe)
else:
    if value >= safe: return 0.0
    if value <= redline: return 1.0
    return (safe - value) / (safe - redline)
```

`below`는 safe > redline이므로 분모가 양수로 유지된다. 음수 구간(S&P 하락률 safe=-3, redline=-15)에서도 같은 식이 그대로 성립한다. TACO Index의 `api/_shared.py`는 `rl < 0`인 경우를 따로 분기해 두었지만 두 분기의 계산식이 동일해 실제로는 불필요하다.

## 4. 왜 이렇게 하나 (장점)

- **정규화 기준을 데이터가 아니라 도메인이 정한다.** min-max나 z-score는 관측 구간에 따라 기준이 흔들리지만, safe/redline은 "VIX 35면 패닉"처럼 고정된 의미를 가진다. 과거 데이터가 없어도, 데이터 분포가 바뀌어도 점수의 뜻이 유지된다.
- **부분 점수가 자연스럽다.** 임계값을 넘었나/아닌가의 0-1 판정이 아니라, 레드라인에 얼마나 가까운지가 연속적으로 반영돼 총점이 부드럽게 움직인다. 대시보드처럼 매 시각 값이 바뀌는 화면에 맞는다.
- **지표를 빼거나 더하기 쉽다.** 각 항이 독립적으로 0~1이므로 지표 수 = 만점이고, 가중치 논쟁 없이 항목만 추가하면 된다. TACO Index도 커밋 도중 VIX를 추가하며 만점을 5에서 6으로 올렸다.
- **한 항목만 봐도 설명이 된다.** UI에서 지표 카드마다 자기 점수와 레드라인 값을 같이 보여줄 수 있다.

## 5. 실제로 겪은 문제

- **safe/redline 값의 근거가 남지 않는다.** TACO Index 코드에는 VIX 35, 10년물 4.5, 유가 100 같은 숫자만 있고 왜 그 값인지 설명이 없다. 이 방식은 임계값에 결과가 통째로 좌우되므로, 값 옆에 근거(역사적 분위, 참고 기사, 정한 날짜)를 주석으로 남기지 않으면 나중에 아무도 손댈 수 없다.
- **주석과 상수가 어긋난다.** 같은 파일에 `# S&P 500: safe=-5, redline=-20`이라 적혀 있는데 실제 상수는 `-3.0 / -15.0`이었다. 임계값 튜닝은 잦으므로 주석에 숫자를 복사해 두면 반드시 썩는다. 상수 딕셔너리 하나만 진실로 두는 편이 낫다.
- **항목을 하나 빠뜨려도 티가 안 난다.** TACO Index의 `backend/` 쪽은 6개 중 지지율을 빼고 5개만 합산하면서 레벨 경계는 만점 6.0 기준을 그대로 써서, 구조적으로 점수가 낮게 나왔다. 합산 항목 수와 만점을 같은 곳에서 유도하지 않으면 생기는 사고다.
- **단순 합산은 곧 균등 가중이다.** 지지율 1점과 VIX 1점이 같은 무게를 가진다. 자료에는 이 선택에 대한 검토 흔적이 없다(추정: 의도적 단순화).
- **과거 시계열이 없는 지표를 섞으면 히스토리가 오염된다.** 지지율은 일별 과거값을 못 구해 현재값을 전 구간에 채워 넣었고, 그 결과 과거 총점이 오늘의 지지율을 가정한 값이 됐다. 히스토리 차트를 그릴 거라면 "모든 지표에 과거 시계열이 있는가"를 지표 선정 단계에서 먼저 확인해야 한다.

## 6. 참고 자료

- `tacotrump/backend/app/services/score_engine.py`: REDLINES 상수와 레벨 경계
- `tacotrump/api/_shared.py`: 배포판 구현, `calc_indicator_score` / `calc_total` / `get_risk`

## 학습

### CS 주제
- 통계: 정규화 방식(min-max·z-score·기준점 거리)의 선택과 가중 합산, 균등 가중의 함의
- 소프트웨어공학: 상수와 주석의 단일 진실 소스, 같은 로직의 중복 구현이 갈라지는 문제

### 설명할 수 있어야 하는 것
- min-max나 z-score 대신 safe/redline 선형 보간을 쓴 이유를, 기준을 데이터가 아니라 도메인이 정한다는 점과 함께 말할 수 있습니다.
- 임계값 0-1 판정이라는 대안과 비교해, 부드러운 총점을 얻고 임계값 근거 부담을 떠안았다는 맞바꿈을 설명할 수 있습니다.
- 임계값 근거가 없을 때, 항목 수와 만점이 어긋날 때, 과거 시계열이 없는 지표일 때 이 방식이 깨진다는 것을 말할 수 있습니다.

### 확인 질문
1. **Q:** (L1 개념) 단위가 다른 지표를 하나로 합칠 때 흔히 쓰는 정규화가 무엇이 있고, 이 프로젝트에서는 왜 그걸 안 쓰셨는지 설명해 주시겠어요?
   **A:** 흔한 선택지는 min-max 재척도와 z-score 표준화입니다. 둘 다 정규화 기준을 관측 데이터에서 가져오기 때문에 관측 구간이 바뀌면 같은 값의 점수가 달라집니다. TACO Index에서는 지표마다 "여기까지는 아무 일 없음"인 safe와 "여기 닿으면 만점"인 redline을 사람이 정하고 그 사이를 선형 보간해 0~1로 바꿨습니다. "VIX 35면 패닉"처럼 고정된 뜻을 갖고 있어서 과거 데이터가 없어도, 분포가 바뀌어도 점수의 뜻이 유지된다고 판단했습니다.
   **꼬리:** 그러면 데이터 기반 정규화가 오히려 나은 상황은 어떤 경우일까요?
   **틀리기 쉬운 답:** "min-max도 0~1이니 결국 같다"라고 답하는 경우가 있는데, 실제로는 min/max가 관측 구간에 따라 움직이면 같은 VIX 값이 어제와 오늘 다른 점수를 받습니다.

2. **Q:** (L2 판단) `direction`이 `below`인 지표와 음수 구간 지표를 같은 식으로 처리하셨는데, 그게 가능한 이유를 설명해 주시겠어요?
   **A:** `above`면 값이 클수록 위험하고 `below`면 작을수록 위험한데, `below`는 safe > redline이라 `(safe - value) / (safe - redline)`의 분모가 양수로 유지됩니다. S&P 하락률처럼 음수 구간(safe=-3, redline=-15)에서도 같은 식이 그대로 성립합니다. 처음에는 음수를 따로 다뤄야 한다고 생각해서 `api/_shared.py`에 `rl < 0` 분기를 뒀는데, 나중에 보니 두 분기의 계산식이 같아서 필요 없는 분기였습니다. 각 항이 따로 0~1이라 지표 수가 곧 만점이 되고 가중치를 정할 일이 없어서, 커밋 도중에 VIX를 넣으며 만점을 5에서 6으로 올릴 수 있었습니다.
   **꼬리:** 그러면 항목을 쉽게 더할 수 있는 만큼 어떤 위험이 같이 따라올까요?
   **틀리기 쉬운 답:** "음수 지표는 부호를 뒤집어 따로 처리해야 한다"라고 답하는 경우가 있는데, 실제로는 safe/redline의 대소 관계가 방향을 이미 담고 있습니다.

3. **Q:** (L2 판단) 단순 합산을 고르신 것은 어떤 가중치 결정과 같은가요? 그 부분을 검토하셨나요?
   **A:** 단순 합산은 균등 가중과 같습니다. 지지율 1점과 VIX 1점이 총점에서 똑같은 무게를 갖는다는 뜻입니다. 자료에는 이 선택을 검토한 흔적이 없고, 문서에도 의도적 단순화로 추정해 적어 뒀습니다. 총점 6.0 만점에 1.8 / 3.0 / 4.2를 경계로 레벨 1~4를 붙이고 있어서, 가중치를 바꾸면 레벨 경계도 같이 다시 정해야 한다고 생각합니다.
   **꼬리:** 그러면 가중치를 넣는다면 그 값의 근거를 어디서 가져오시겠어요?
   **틀리기 쉬운 답:** "가중치를 안 줬으니 중립적이다"라고 답하는 경우가 있는데, 실제로는 균등 가중도 하나의 선택이고 지표를 하나 더 넣는 순간 기존 지표의 상대 비중이 줄어듭니다.

4. **Q:** (L3 한계) 이 방식에서 실제로 사고가 났던 곳을 셋만 들고, 각각 어떻게 다시 막으실지 말씀해 주시겠어요?
   **A:** 먼저 주석과 상수가 어긋났습니다. 같은 파일에 `# S&P 500: safe=-5, redline=-20`이라 적혀 있는데 실제 상수는 `-3.0 / -15.0`이었고, 임계값을 자주 손보다 보니 생긴 일이라 상수 딕셔너리 하나만 진실로 두는 편이 낫다고 생각합니다. 두 번째로 `backend/` 쪽이 6개 중 지지율을 빼고 5개만 합산하면서 레벨 경계는 만점 6.0 기준을 그대로 써서 점수가 늘 낮게 나왔는데, 합산 항목 수와 만점을 같은 곳에서 유도하면 막을 수 있었습니다. 세 번째로 safe/redline 값의 근거가 코드에 없습니다. VIX 35, 10년물 4.5, 유가 100 같은 숫자만 있고 왜 그 값인지 설명이 없어서, 값 옆에 역사적 분위와 참고 기사, 정한 날짜를 주석으로 남기지 않으면 나중에 아무도 손댈 수 없다고 봅니다.
   **꼬리:** 그러면 임계값에 결과가 통째로 좌우되는 지수라면, 배포 전에 무엇을 한 번 돌려 보시겠어요?
   **틀리기 쉬운 답:** "테스트가 통과했으니 두 구현이 같다"라고 답하는 경우가 있는데, 실제로는 만점 상수가 다른 두 구현이 각자 일관되게 틀린 값을 낼 수 있습니다.

5. **Q:** (L3 한계) 이 점수로 과거 히스토리 차트를 그리려 하셨을 때 어디가 먼저 깨졌나요?
   **A:** 과거 시계열이 없는 지표에서 막혔습니다. 지지율은 일별 과거값을 구하지 못해 현재값을 전 구간에 채워 넣었고, 그래서 과거 총점이 오늘의 지지율을 가정한 값이 됐습니다. 히스토리를 그릴 생각이었다면 모든 지표에 과거 시계열이 있는지를 지표 고르는 단계에서 먼저 확인했어야 한다고 생각합니다. 지금 방식은 실시간 대시보드에는 맞지만 과거 비교에는 그대로 쓰기 어렵습니다.
   **꼬리:** 그러면 과거값이 없는 지표를 히스토리에서 빼면 총점은 어떻게 읽어야 하나요?
   **틀리기 쉬운 답:** "빈 값은 최신값으로 채우면 된다"라고 답하는 경우가 있는데, 실제로는 그 순간 과거 점수가 관측이 아니라 오늘의 가정이 됩니다.

### 더 파볼 것
- [Feature scaling (Wikipedia)](https://en.wikipedia.org/wiki/Feature_scaling) — min-max 재척도와 z-score 표준화의 정의, 이상치에 약하다는 점과 중앙값·IQR을 쓰는 robust scaling. safe/redline 방식이 무엇을 피하려 한 것인지 대조해서 볼 수 있다.
