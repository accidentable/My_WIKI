# 차지백 기한과 사유코드를 단정하지 않고 다루기

## 1. 한 줄 정의

카드 분쟁의 신청기한과 사유코드는 브랜드·사유·거래 유형·지역에 따라 기준일과 조건이 달라지므로, 하나의 공식(예: 승인일 + 120일)으로 일괄 계산하지 않고 검증된 조합에서만 계산하고 나머지는 카드사 확인 안내로 넘기는 처리 방식.

## 2. 어디서 썼는가

- [[finance-ai-2026-subscription-cut]] — 이의신청 패키지 단계에서 사유코드 후보와 참고 기한을 표시한다.

## 3. 실제로 겪은 문제와 해결

가장 유혹적인 구현은 "승인일 + 120일"을 전부에 적용하는 것이다. 설명서 ver2는 이를 명시적으로 배제했다. 근거로 Mastercard 공개 가이드에 특정 사유에서는 서비스 예정일을 기준으로 삼는 규정이 나타난다는 점을 들었다. 따라서 확인해야 할 항목을 규정 레코드의 필드로 못박았다. 출처 URL, 문서 버전·적용일, 확인일, 적용 조건, 필요 증빙, 날짜 기준, 지원 범위.

파생된 규칙 세 가지.

1. **사유코드는 후보로만.** 검증한 후보만 표시하고 최종 적용은 카드사 확인이 필요함을 함께 알린다. 확인되지 않은 사유코드는 생성하지 않는다(데모 시나리오 B). 구현에서는 API 키 유출을 카드 도용 사유코드로 자동 매핑하지 않는다.
2. **브랜드사의 절차상 기한 ≠ 소비자의 마감일.** 그날까지 기다려도 되는 마감으로 제시하지 않는다.
3. **카드사 상담과 차지백을 분리.** 승인 거절이나 청구서만 있는 사건도 반복 시도 차단·해외사용 설정 문의가 필요하므로 "승인 없음 → 카드사 경로 불가" 규칙은 쓰지 않는다. 실제 매입 거래의 분쟁 검토와 추가 결제 방지 상담을 따로 표시한다. 데모 C에서는 매입 미확인 상태에서 차지백 D-값을 표시하지 않는다.

기한을 검증하지 못한 조합은 날짜 계산 기능을 억지로 넣지 않고 카드사 확인 안내로 처리한다는 것이 3일 계획의 명시 방침이었다.

구현 쪽 데이터는 `data/`에 카드사 9곳 이의신청 절차와 Visa·Mastercard 사유코드 14개를 출처·조회일과 함께 두고, 사건 티켓의 카드사 선택에 따라 접수 안내(채널·기한·서류·처리기간·사유 명칭)와 신청서 항목을 바꾼다.
