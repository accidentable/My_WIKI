## 한 줄 정의

제출물(README · 랜딩 · 컨트랙트 소스)이 주장하는 주소·개수·값·거래를 실제 상태(체인)에서 다시 읽어 대조하고, 하나라도 어긋나면 종료 코드 1로 실패시키는 자체 검사.

## 어디서 썼는가

- [[blockthon-2026-memory-market]], `node tools/consistency.mjs`가 아홉 가지를 대조한다. README에 "저장소·랜딩·체인, 셋의 수치가 어긋나면 그건 잘못입니다"라고 규칙으로 못박았다.

## 왜 필요했나

해커톤 제출물은 사람이 손으로 쓴 수치(팩 개수, 값, 기간, 산 사람 수, tx 링크)가 여러 곳에 흩어진다. 체인 상태는 데모 도중에도 바뀐다. 후기 하나만 더 남겨도 `subscriber_count`가 는다. 사람이 세 곳을 눈으로 맞추면 반드시 어긋나고, 심사위원이 체인을 직접 열어 보면 그 자리에서 드러난다.

## 어떻게

- 체인을 직접 읽어 랜딩 · README · 컨트랙트 소스의 아홉 가지를 대조한다. 기록 주소, 수치, 거래가 실제와 맞는지, 컨트랙트 함수가 소스와 같은지.
- **ground-truth를 한 곳으로 정한다.** README의 기록 표가 기준이고, 데모 대본은 "이 대본과 어긋나면 ground-truth가 맞다"고 스스로 적어 두었다. 대본 안의 표는 파생물이다.
- 새 팩을 올리면 그 자리에서 기준 표에 추가하는 것이 준비 체크리스트 항목이다.
- 랜딩이 값을 하드코딩하지 않고 브라우저에서 같은 GraphQL·aggregator를 직접 읽는 것도 같은 목적이다. 읽는 소스를 하나로 만들면 어긋날 자리가 준다.
- 같은 결의 검사가 더 있다. `tools/check.mjs`(디자인 5항목)와 `check-copy.mjs`(한국어 카피 6항목)는 산출물을, `scripts/e2e.ts`는 발행에서 구독·만료·폐기까지 전 과정을 실제 트랜잭션으로 검증한다.

## 실제로 겪은 문제

- 검사기 자체가 틀릴 수 있다. 실측 중 "없는 파일도 4/5로 채점되던 `check.mjs`"를 발견해 고쳤다. 자동 채점을 신뢰하려면 채점기부터 한 번 의심해야 한다.
- 이름과 개수가 어긋난 팩 하나(`0xd2902d30…`, 이름은 "다섯 번에"인데 14개)는 지울 수 없어 기간을 5분 아래로 내려 목록에서 빠지게 했다. 체인 기록은 지워지지 않으므로 심사위원이 물을 수 있는 자리로 미리 적어 두었다.
- 파생 문서(발표 대본)가 기준 문서와 어긋나는 것도 같은 문제다. 발표 대본은 화면의 비교 수치가 "판매 페이지에 제시된 비교 예시이며 이번 데모의 실측 결과는 아니다"라고 말로 구분하도록 적어 두었다. [[measured-baseline-over-claimed-gain]]

## 학습

### CS 주제
- 소프트웨어공학: 단일 진실 원천(SSOT)과 파생물, 검사 자동화와 종료 코드로 실패시키기
- 분산시스템: 외부에서 계속 바뀌는 상태(체인)와 그것을 베껴 적은 문서 사본의 표류

### 설명할 수 있어야 하는 것
- README의 기록 표를 ground-truth로 정하고 데모 대본이 스스로 파생물임을 선언하게 한 이유, 그리고 랜딩이 값을 하드코딩하지 않고 같은 GraphQL·aggregator를 직접 읽게 만든 판단
- 사람의 눈 대조 대신 `tools/consistency.mjs`가 체인을 읽어 아홉 가지를 대조하고 어긋나면 종료 코드 1로 실패시키게 한 이유 — 체인 상태는 데모 도중에도 바뀌고 심사위원이 직접 열어 본다
- "없는 파일도 4/5로 채점되던 `check.mjs`"처럼 채점기 자체가 틀릴 수 있다는 점과, 지울 수 없는 어긋난 팩(`0xd2902d30…`)을 감추는 대신 기간을 내리고 미리 밝히는 쪽을 택한 이유

### 확인 질문
1. **Q:** (L1 개념) 단일 진실 원천(SSOT)이 무엇이고, 이 프로젝트의 어디가 그 개념에 해당하는가?
   **A:** 모든 데이터 요소를 한 곳에서만 수정·보관하고, 나머지는 그것을 참조하거나 파생시키는 구조다. 사본을 각자 고칠 수 있게 두면 시간이 갈수록 서로 어긋난다. 이 프로젝트는 **README의 기록 표를 기준(ground-truth)으로 정했고**, 데모 대본은 스스로 "이 대본과 어긋나면 ground-truth가 맞다"고 적어 자신이 파생물임을 선언한다. 랜딩 페이지도 값을 하드코딩하지 않고 브라우저에서 같은 GraphQL·aggregator를 직접 읽는다. 읽는 소스를 하나로 만들면 어긋날 자리가 준다.
   **꼬리:** 파생물을 아예 없앨 수 있었는가? 없앨 수 없다면 무엇으로 대신 보장하는가?
   **틀리기 쉬운 답:** "세 곳을 꼼꼼히 맞춰 적으면 된다." 체인 상태는 데모 도중에도 바뀐다 — 후기 하나만 더 남겨도 `subscriber_count`가 는다.
2. **Q:** (L2 판단) 왜 사람이 눈으로 대조하지 않고, 어긋나면 **종료 코드 1로 실패하는 스크립트**를 만들었는가?
   **A:** 해커톤 제출물은 사람이 손으로 쓴 수치(팩 개수, 값, 기간, 산 사람 수, tx 링크)가 여러 곳에 흩어지는데, 기준이 되는 체인 상태는 실시간으로 변한다. 사람이 세 곳을 맞추면 반드시 어긋나고, 심사위원이 체인을 직접 열어 보면 그 자리에서 드러난다. 그래서 `node tools/consistency.mjs`가 체인을 직접 읽어 랜딩·README·컨트랙트 소스의 아홉 가지(기록 주소, 수치, 거래, 컨트랙트 함수가 소스와 같은지)를 대조하고, 하나라도 어긋나면 실패시킨다. 같은 결의 검사가 더 있다 — `tools/check.mjs`(디자인 5항목), `check-copy.mjs`(한국어 카피 6항목)는 산출물을, `scripts/e2e.ts`는 발행에서 구독·만료·폐기까지 실제 트랜잭션으로 검증한다.
   **꼬리:** 이 검사를 언제 돌려야 의미가 있는가 — 커밋 훅, CI, 데모 직전 중 어디인가?
   **틀리기 쉬운 답:** "단위 테스트가 통과하니 문서 수치도 맞다." 코드의 정확성과 산출물 간 수치 정합은 다른 축이고, 후자는 외부 상태를 읽어야만 검증된다.
3. **Q:** (L3 한계) 검사기 자체가 틀렸다면 어떻게 알아차리는가? 그리고 지울 수 없는 어긋남은 어떻게 처리했는가?
   **A:** 실제로 겪었다. 실측 중 **"없는 파일도 4/5로 채점되던 `check.mjs`"**를 발견해 고쳤다. 자동 채점을 신뢰하려면 채점기부터 한 번 의심해야 한다는 교훈이 그대로 남았다. 또 이름과 개수가 어긋난 팩 하나(`0xd2902d30…`, 이름은 "다섯 번에"인데 14개)는 체인에서 지울 수 없어 기간을 5분 아래로 내려 목록에서 빠지게 했고, 기록은 지워지지 않으므로 **심사위원이 물을 수 있는 자리로 미리 적어 두었다.** 파생 문서가 어긋나는 문제도 같은 결이어서, 발표 대본은 화면의 비교 수치가 "판매 페이지에 제시된 비교 예시이며 이번 데모의 실측 결과는 아니다"라고 말로 구분하도록 적어 두었다.
   **꼬리:** 채점기가 맞는지 검증하려면 어떤 입력을 일부러 넣어 봐야 하는가?
   **틀리기 쉬운 답:** "잘못된 기록은 체인에서 지우면 된다." 체인 기록은 지워지지 않으므로, 감추는 대신 미리 밝히는 쪽이 유일한 대응이었다.
