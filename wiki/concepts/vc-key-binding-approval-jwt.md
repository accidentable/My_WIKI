## 한 줄 정의

KB-JWT는 "지금 제출한 사람이 그 VC의 주인"임을 증명하고, 별도의 승인 JWT는 "그 사람이 **이 금액·이 달의 요청**에 동의했다"를 증명한다. 신원 증명과 업무 동의는 다른 문제라서 서명을 두 개 쓴다.

## 어디서 썼는가

- [[blockchain-valley-2026-sabonx]] — 월 급여 요청 승인과 소득 신고 제출.

## 실제로 겪은 문제와 해결

### 문제 1: 복사한 VC로 다른 사람이 제출

발급기관 서명만으로는 제출자가 정당한 소유자인지 알 수 없다.

- 기관이 홀더 공개키를 `cnf.jwk`로 VC에 결합한다.
- 지갑이 그 개인키로 KB-JWT를 만들어 요청의 `nonce`, 수신자 `aud`, 제시 내용의 `sd_hash`를 서명한다.
- 검증기는 VC에 묶인 공개키로 확인한다.

결과: VC만 복사하거나 다른 키로 서명한 제출은 거절된다. nonce·aud 검증이 제출 묶음의 다른 요청 재사용도 막는다. 단, **개인키 자체가 탈취되는 문제는 해결하지 못한다.**

### 문제 2: 유효한 신원 제시 ≠ 특정 금액 동의

지급 요청이나 제시 묶음을 바꿔 끼우는 공격도 막아야 한다.

- 서버가 금액·월·사업체·근로자 공개키·nonce를 담은 **요청 JWT**를 서명한다.
- 브라우저가 요청 서명을 검증하고 화면 내용과 대조한다.
- 지갑이 별도의 **승인 JWT**를 서명한다.

```text
request_id        = 승인할 급여 요청
request_hash      = SHA-256(서명된 요청 JWT)
presentation_hash = SHA-256(SD-JWT 제시 + KB-JWT)
decision          = approve
```

결과: 서버는 두 서명과 요청 대상 공개키를 함께 검증한다. 9월에 승인했더라도 금액이 다른 10월 요청에는 새 승인이 필요하다.

### 문제 3: 실기기 시계 차이

실기기 시연에서 브라우저의 `iat`가 서버 시각보다 앞서 발급이 거절됐다. JWT 검증에 **60초 Clock Tolerance**를 적용했다. 시간 검증을 없앤 것이 아님을 확인하려고, 30초 미래 요청은 허용하고 과도한 미래·만료 요청은 거절하는 테스트를 둔다.

### 동시 제출

같은 요청의 동시 제출은 세션 잠금과 `pending → accepted` 상태 전이로 한 번만 접수한다. 정정 요청은 `correction` 상태로 바꿔 승인을 막는다. 단일 서버 메모리 기반이라 다중 인스턴스에는 DB 트랜잭션이 필요하다.

## 학습

### CS 주제
- 보안: 재사용(replay) 공격 방지, nonce·audience 검증, 권한과 동의의 분리
- 암호학: 공개키 소유 증명, 서명 대상에 컨텍스트를 묶는 바인딩
- 분산시스템: 시계 편차와 clock skew 허용, 동시 요청의 상태 전이

### 설명할 수 있어야 하는 것
- 왜 이 방법을 골랐는가: 발급기관 서명만으로는 "제출자가 주인인가"와 "이 금액에 동의했는가"를 둘 다 답할 수 없어 서명을 두 개로 나눴다.
- 대안은 무엇이었고 무엇을 포기했는가: 서명 하나로 합치면 구현은 단순하지만 신원 제시와 업무 승인의 유효기간·재사용 범위가 같아진다. 나눠서 검증 단계가 늘어나는 비용을 받아들였다.
- 어떤 조건에서 깨지는가: 홀더 개인키 탈취, 그리고 단일 서버 메모리 기반 잠금이라 다중 인스턴스에서는 동시 제출 제어가 성립하지 않는다.

### 확인 질문
1. **Q:** (L1 개념) 키 바인딩(KB-JWT)은 무엇을 증명하며 어떤 값들을 서명 대상에 넣는가?
   **A:** "지금 제출하는 사람이 그 VC에 묶인 개인키를 가진 홀더"임을 증명한다. 발급기관이 홀더 공개키를 `cnf.jwk`로 VC 안에 결합해 서명해 두고, 지갑이 그 개인키로 요청의 `nonce`, 수신자 `aud`, 제시 내용의 `sd_hash`를 서명한다. 검증기는 VC에 묶인 공개키로 이 서명을 확인한다(`kb-signature`, `kb-nonce`, `kb-audience`, `kb-sd-hash` 검사 항목). 덕분에 VC만 복사하거나 다른 키로 서명한 제출은 거절되고, nonce·aud 검증이 다른 요청에 묶인 제출 묶음의 재사용도 막는다.
   **꼬리:** `sd_hash`를 서명에서 빼면 어떤 바꿔치기가 가능해지는가?
   **틀리기 쉬운 답:** "KB-JWT가 있으면 VC 도용이 완전히 막힌다"는 답. 개인키 자체가 탈취되면 막지 못한다.
2. **Q:** (L2 판단) 신원 제시가 유효한데도 별도의 승인 JWT를 둔 이유는 무엇인가?
   **A:** 유효한 신원 제시는 "이 사람이 맞다"까지만 말하고 "이 금액·이 달의 요청에 동의했다"는 말하지 않는다. 지급 요청이나 제시 묶음을 바꿔 끼우는 공격이 가능하기 때문에, 서버가 금액·월·사업체·근로자 공개키·nonce를 담은 요청 JWT를 서명하고, 브라우저가 그 서명을 검증해 화면 내용과 대조한 뒤, 지갑이 `request_id`·`request_hash`·`presentation_hash`·`decision`을 담은 승인 JWT를 따로 서명한다. 서버는 두 서명과 요청 대상 공개키를 함께 검증한다. 그래서 9월에 승인했더라도 금액이 다른 10월 요청에는 새 승인이 필요하다.
   **꼬리:** `presentation_hash`가 없으면 승인 JWT를 어떻게 악용할 수 있는가?
   **틀리기 쉬운 답:** "요청 JWT 서명만 검증하면 충분"이라는 답. 그건 서버가 보낸 내용의 무결성이지 사용자의 동의가 아니다.
3. **Q:** (L3 한계) 실기기 시연에서 시계 차이로 발급이 거절됐다. 어떻게 처리했고, 규모가 커지면 무엇이 먼저 깨지는가?
   **A:** 브라우저의 `iat`가 서버 시각보다 앞서 거절됐고, JWT 검증에 60초 Clock Tolerance를 적용해 풀었다. 시간 검증을 없앤 것이 아님을 확인하려고 30초 미래 요청은 허용하되 과도한 미래·만료 요청은 거절하는 테스트를 뒀다. 동시 제출은 세션 잠금과 `pending → accepted` 상태 전이로 한 번만 접수하고, 정정 요청은 `correction` 상태로 바꿔 승인을 막는다. 다만 이 잠금은 단일 서버 메모리 기반이라 인스턴스를 늘리면 먼저 깨지며, DB 트랜잭션으로 옮겨야 한다.
   **꼬리:** Clock Tolerance를 늘리면 어떤 공격 창이 같이 넓어지는가?
   **틀리기 쉬운 답:** 시계 문제를 "만료 시간을 길게 주면 된다"로 푸는 답. 미래 `iat` 거절은 만료와 다른 검사다.
