## 한 줄 정의

코딩 에이전트 세션에 훅을 붙여, 파일이 실제로 바뀐 턴만 "프롬프트 · diff · 화면 · 왜 · 알게 된 것" 한 덩어리로 확정하고 해시 사슬로 묶어, 사람이 따로 글을 쓰지 않아도 팔 수 있는 기록이 쌓이게 하는 것.

## 어디서 썼는가

- [[blockthon-2026-memory-market]], `tools/capture.mjs`. 판매자는 평소처럼 Claude Code로 랜딩을 고쳤고 그 세션이 그대로 15단계·5단계 팩이 됐다.

## 훅 3종

| 훅 | 하는 일 |
|---|---|
| `UserPromptSubmit` | 프롬프트를 `.mm/pending.json`에 모은다. 첫 턴이면 기준선 HTML 스냅샷 |
| `PostToolUse` (Edit · MultiEdit · Write) | 손댄 파일과 편집 방식(targeted / rewrite) 기록 |
| `Stop` | **파일이 바뀐 턴만** 한 단계로 확정. HTML 복사, 이전 단계와 unified diff(8KB), transcript에서 이유와 교훈 추출, Playwright로 1280×800·375×812 스크린샷, `check.mjs` 5항목 채점, `step-N.json` 저장, `git commit "mm step N"` |

## 실제로 겪은 문제와 해결

**기록이 진짜 그 순서였다는 보장.** 단계를 해시 사슬로 묶는다. `record_hash = sha256(canonical JSON)`, `prev_hash`는 앞 단계의 `record_hash`(1단계는 `sha256(pack_id + series_id)`). 목차(manifest)에 단계마다 `record_hash`를 평문으로 실으므로 구매자는 복호화한 것이 사기 전에 본 목차 그대로인지 대조할 수 있다. 다만 이 사슬은 **사후 수정**만 드러내고 처음부터 지어낸 기록은 못 막는다.

**훅이 세션을 망가뜨리면 안 된다.** 훅 안에서 LLM 호출도 네트워크 호출도 하지 않고, 예외는 전부 삼킨다. 실측에서 Stop 훅은 턴당 1.7~2.1초였다(판매자 5턴의 턴 자체는 41/70/46/55/40초).

**에이전트는 시키지 않으면 기억 도구를 안 부른다.** 그래서 구매자 쪽 플러그인의 `UserPromptSubmit` 훅이 주제어가 보이면 "먼저 시장을 확인하라" 한 줄을 프롬프트에 덧붙인다(MemWal 공식 플러그인의 패턴). 도구를 만들어 두는 것만으로는 호출되지 않는다는 뜻이다.

**올리기 전 걸러내기.** `filter.ts`가 비밀키·니모닉·API 키 형태는 문장째 버리고(drop), 경로와 이메일은 가린다(redact). 포집이 자동이므로 필터도 자동이어야 한다.

## 학습

### CS 주제
- 암호학: 해시 사슬과 변조 증거성, SHA-256 기반 무결성
- 운영체제: 이벤트 훅(생명주기 콜백), 동기 실행이 주 작업 지연에 미치는 영향
- 보안: 비밀정보 자동 필터링(drop / redact)

### 설명할 수 있어야 하는 것
- 왜 이 방법을 골랐는가: 사람이 따로 글을 쓰지 않아도 팔 수 있는 기록이 쌓이게 하려고, 코딩 에이전트 세션에 훅을 붙여 파일이 실제로 바뀐 턴만 한 단계로 확정했다.
- 대안은 무엇이었고 무엇을 포기했는가: 모든 턴을 기록하면 잡음이 섞이고, 사람이 직접 쓰면 아무도 안 쓴다. 파일 변경을 확정 조건으로 삼는 대신 코드 변경 없는 사고 과정은 단계로 남지 않는다.
- 어떤 조건에서 깨지는가: 해시 사슬은 사후 수정만 드러내고 처음부터 지어낸 기록은 못 막는다.

### 확인 질문
1. **Q:** (L1 개념) 해시 사슬로 기록을 묶는다는 것이 무엇이고, 여기서 구매자는 그것으로 무엇을 확인하나?
   **A:** 단계마다 `record_hash = sha256(canonical JSON)`을 만들고 `prev_hash`에 앞 단계의 `record_hash`를 넣는다(1단계는 `sha256(pack_id + series_id)`). 목차(manifest)에 단계마다 `record_hash`를 평문으로 싣기 때문에, 구매자는 복호화한 내용이 사기 전에 본 목차 그대로인지 대조할 수 있다. 즉 사슬이 보장하는 것은 "구매 전에 광고된 것과 구매 후 받은 것이 같다"는 대응 관계다.
   **꼬리:** 중간 한 단계만 몰래 고치면 사슬의 어디가 깨지고, 검증자는 무엇을 다시 계산해야 하나?
   **틀리기 쉬운 답:** "해시 사슬이 있으니 기록이 진짜라는 뜻이다." 사슬은 사후 수정만 드러내고 처음부터 지어낸 기록은 못 막는다.
2. **Q:** (L2 판단) 훅을 세 종류로 나눈 이유와, `Stop` 훅에서 "파일이 바뀐 턴만" 확정한 이유는?
   **A:** `UserPromptSubmit`은 프롬프트를 `.mm/pending.json`에 모으고 첫 턴이면 기준선 HTML 스냅샷을 찍는다. `PostToolUse`(Edit·MultiEdit·Write)는 손댄 파일과 편집 방식(targeted / rewrite)을 기록한다. `Stop`은 턴이 끝나는 시점이라 그 턴의 결과가 확정되므로 여기서 한 단계를 만든다. 파일이 바뀐 턴만 고르는 것은 팔 수 있는 단위가 "무엇이 어떻게 달라졌는가"이기 때문이고, `Stop`에서 HTML 복사, 이전 단계와의 unified diff(8KB), transcript에서 이유와 교훈 추출, Playwright 스크린샷(1280×800·375×812), `check.mjs` 5항목 채점, `step-N.json` 저장, `git commit "mm step N"`까지 한 번에 한다.
   **꼬리:** 한 턴에서 파일을 고쳤다가 되돌리면 이 판정은 어떻게 되나?
   **틀리기 쉬운 답:** "PostToolUse에서 바로 단계를 만들면 된다." 한 턴에 여러 번 편집이 일어나므로 턴 경계인 `Stop`에서 확정해야 단계가 쪼개지지 않는다.
3. **Q:** (L2 판단) 훅 안에서 LLM 호출도 네트워크 호출도 하지 않기로 한 이유는? 실제 비용은 얼마였나?
   **A:** 훅이 세션을 망가뜨리면 안 되기 때문이다. 훅은 사용자의 작업 흐름 안에서 동기로 실행되므로 느려지거나 예외가 나면 작업 자체를 방해한다. 그래서 외부 호출을 쓰지 않고 예외는 전부 삼킨다. 실측에서 `Stop` 훅은 턴당 1.7~2.1초였고, 판매자 5턴의 턴 자체는 41/70/46/55/40초였으므로 훅 비용이 턴 시간에 묻히는 수준이다.
   **꼬리:** 예외를 전부 삼키면 훅이 조용히 실패해 기록이 빠지는 경우는 어떻게 알아채나?
   **틀리기 쉬운 답:** "훅에서 LLM으로 요약을 만들면 기록 품질이 올라간다." 지연과 실패 위험을 주 작업에 얹는 대가가 크고, 이 구현은 transcript에서 뽑는 쪽을 택했다.
4. **Q:** (L3 한계) 도구를 만들어 두었는데 에이전트가 부르지 않는 문제와, 자동 포집이 만드는 유출 위험은 각각 어떻게 다뤘나?
   **A:** 에이전트는 시키지 않으면 기억 도구를 안 부른다. 그래서 구매자 쪽 플러그인의 `UserPromptSubmit` 훅이 주제어가 보이면 "먼저 시장을 확인하라" 한 줄을 프롬프트에 덧붙인다(MemWal 공식 플러그인의 패턴). 유출 쪽은 `filter.ts`가 비밀키·니모닉·API 키 형태는 문장째 버리고(drop) 경로와 이메일은 가린다(redact). 포집이 자동이므로 필터도 자동이어야 한다는 것이 이유다.
   **꼬리:** 필터가 놓친 비밀이 이미 해시 사슬에 들어가 커밋까지 됐다면 무엇을 할 수 있나?
   **틀리기 쉬운 답:** "MCP 도구로 등록하면 에이전트가 알아서 쓴다." 도구 존재만으로는 호출되지 않아 프롬프트에 유도 문장을 주입하는 훅이 필요했다.

### 더 파볼 것
- [Claude Code hooks reference](https://code.claude.com/docs/en/hooks) — `UserPromptSubmit` / `PostToolUse` / `Stop`이 각각 언제 발화하고 어떤 입력(JSON)을 받으며 exit code 2가 무엇을 막는지. 훅으로 무엇까지 강제할 수 있는지의 경계
- [RFC 6962 (Certificate Transparency)](https://datatracker.ietf.org/doc/html/rfc6962) — 추가 전용 로그의 변조 증거성을 Merkle 트리로 설계한 표준. 단순 해시 사슬과 비교하면 "일관성 증명"이 무엇을 더 주는지 보인다
