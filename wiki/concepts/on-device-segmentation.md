## 1. 한 줄 정의

서버로 사진을 보내지 않고 브라우저 안에서 MediaPipe InteractiveSegmenter로 마스크를 뽑아, 후처리를 거쳐 물체 윤곽 폴리곤과 bbox까지 만들어내는 방식.

## 2. 어디서 썼는가

- [[wanted-hackathon-2026]] — 사진 모드에서 부술 대상을 잘라낼 때. 래퍼는 `src/photo/segment.js`, 후처리는 `src/photo/contour.js`.

## 3. 실제로 겪은 문제와 해결

**시드 지정을 사용자에게 묻지 않기.** 확인·수정 UI를 없애는 것이 목표였기 때문에 사진 중앙 점을 시드로 넣어 자동 선택했다. 대신 물체가 중앙에 없을 때를 위해 "물체 밖을 탭하면 그 자리의 다른 물체를 새로 잘라내고 대상 변경(스윙은 하지 않음)"이라는 조작을 뒀다. 실패를 UI로 막지 않고 재시도 동작으로 흡수한 셈이다.

**마스크를 그대로 쓰지 않기.** 원시 마스크에는 시드와 무관한 영역이 섞이므로 시드 연결 성분만 남기고, 외곽선을 추적한 뒤 RDP로 단순화해 폴리곤을 만든다. 단순화 정도는 `contour.js`의 `simplify(..., 1.2)`, 잡티 제거는 `maskToPolygon`의 최소 면적으로 조절한다.

**모델 로딩 비용.** `vendor/models/magic_touch.tflite`가 약 16MB라 사진 모드 첫 진입에 몇 초가 걸린다. 이후에는 사진당 1초 내외. 입력 사진은 1024px 이하로 줄여 넣는다.

**번들 제약.** MediaPipe WASM과 모델, 샘플 사진은 단일 HTML 파일 빌드(`npm run build:single`)에 담기지 않는다. 그래서 단일 파일 배포본과 Claude 아티팩트용 변형(`dist/artifact.html`)은 사진 탭 없이 테스트 벤치만 열린다. 온디바이스 모델을 쓰면 "파일 하나로 공유" 경로를 포기하거나 기능을 이중화해야 한다는 교환이 그대로 드러난 사례다.

## 학습

### CS 주제
- 머신러닝: 대화형 분할 모델, 확률(confidence) 마스크와 임계값
- 알고리즘: 연결 성분 탐색, RDP 곡선 단순화
- 웹: WebAssembly 온디바이스 추론, 모델 크기와 첫 로딩 비용

### 설명할 수 있어야 하는 것
- 확인·수정 UI를 없애기 위해 사진 중앙 점을 자동 시드로 넣기로 한 판단과, 시드가 빗나갈 때 이를 "물체 밖 탭으로 대상만 바꾸기"라는 재시도 동작으로 흡수한 과정
- 서버 추론 대신 브라우저 안에서 모델을 돌려 사진을 내보내지 않는 대신, 16MB 모델 때문에 단일 HTML 파일 배포(`build:single`, `artifact.html`)에서 사진 탭을 통째로 포기해야 했던 교환
- 원시 마스크를 바로 쓰지 않고 시드 연결 성분 필터 → 외곽선 추적 → RDP `simplify(..., 1.2)`를 거치는 이유와, 단순화 강도·최소 면적을 움직였을 때 윤곽 충실도와 처리 비용이 어느 쪽으로 기우는지

### 확인 질문
1. **Q:** (L1 개념) 대화형 세그멘테이션이 무엇이고, 왜 "시드(관심 영역)"를 입력으로 받는가?
   **A:** 이미지를 "선택한 물체"와 "나머지" 둘로 나누는 분할이다. 어느 물체를 원하는지는 이미지만 봐서는 알 수 없으므로, 점이나 획으로 관심 영역을 찍어 알려준다. 이 프로젝트는 사진(1024px 이하)을 MediaPipe InteractiveSegmenter에 넣고 **사진 중앙 점을 시드로** 자동 지정해 마스크를 얻는다. 모델(`vendor/models/magic_touch.tflite`)이 브라우저 안에서 돌기 때문에 사진을 서버로 보내지 않는다.
   **꼬리:** 마스크가 0/1이 아니라 확률값으로 나온다면 어디서 임계값을 정하고, 그 값이 윤곽에 어떤 영향을 주는가?
   **틀리기 쉬운 답:** "세그멘테이션이니 물체 종류(나무·금속·유리)까지 같이 나온다." 이 태스크는 시드 물체의 영역만 내놓고, 소재 판단은 `/api/analyze`(OpenAI 비전)와 색상 휴리스틱이 따로 한다.
2. **Q:** (L2 판단) 확인·수정 UI 없이 "중앙 점 자동 시드"를 택한 이유는 무엇이고, 시드가 빗나갈 때는 어떻게 처리했는가?
   **A:** 목표 자체가 "사진 → 바로 부수기"였고 확인·수정 UI를 없애는 것이 요구사항이었다. 그래서 사용자에게 시드를 묻지 않고 중앙 점을 넣었다. 대신 물체가 중앙에 없을 경우를 위해 "물체 밖을 탭하면 그 자리의 다른 물체를 새로 잘라내고 대상만 바꾼다(스윙은 하지 않음)"는 조작을 뒀다. 실패를 UI(확인 화면)로 막지 않고 **재시도 동작으로 흡수**한 셈이다.
   **꼬리:** 사진 중앙에 두 물체가 겹쳐 있으면 어떤 마스크가 나오고, 사용자는 그걸 어떻게 알아차리는가?
   **틀리기 쉬운 답:** "정확도를 올리려면 사용자가 마스크를 다듬게 하면 된다." 그 다듬기 UI를 없애는 것이 이 데모의 전제였으므로, 정확도를 조작 흐름으로 바꿔 푼 것이 핵심이다.
3. **Q:** (L2 판단) 원시 마스크를 그대로 쓰지 않고 연결 성분 필터 → 외곽선 추적 → RDP 단순화를 거치는 이유는? 단순화 강도를 올리면 무엇이 좋아지고 무엇이 나빠지는가?
   **A:** 원시 마스크에는 시드와 무관한 영역이 섞여 들어오므로 **시드가 포함된 연결 성분만** 남기고, 잡티는 `maskToPolygon`의 최소 면적으로 걸러낸다. 남은 영역의 외곽선을 추적한 뒤 RDP(`contour.js`의 `simplify(..., 1.2)`)로 정점을 줄여 폴리곤과 bbox를 만든다. 단순화 강도를 올리면 정점이 줄어 이후 처리가 가벼워지지만 윤곽이 뭉툭해지고, 낮추면 윤곽은 충실해지지만 마스크의 톱니와 잡음까지 그대로 남는다.
   **꼬리:** RDP의 시간복잡도는 어떻게 되고, 정점이 아주 많은 윤곽에서 최악의 경우는 언제 생기는가?
   **틀리기 쉬운 답:** "ε(단순화 임계값)을 작게 할수록 결과가 항상 좋다." 잡음까지 보존해 정점만 늘어난다.
4. **Q:** (L3 한계) 16MB 모델을 온디바이스에 두면서 무엇을 포기했는가? 서버 추론으로 바꾸면 어디가 달라지는가?
   **A:** 첫째, 비용이 앞단으로 몰린다. 사진 모드 첫 진입에 모델을 받느라 몇 초가 걸리고 이후에는 사진당 1초 내외다. 둘째, **단일 파일 배포를 포기했다.** MediaPipe WASM·모델·샘플 사진은 `npm run build:single`이 만드는 단일 HTML에 담기지 않아, `dist/index.html`과 Claude 아티팩트용 `dist/artifact.html`은 사진 탭 없이 테스트 벤치만 열린다. 온디바이스 모델을 쓰면 "파일 하나로 공유" 경로를 버리거나 기능을 이중화해야 한다는 교환이 그대로 드러났다. 서버 추론으로 바꾸면 번들 문제와 첫 로딩은 사라지지만, 사진이 서버로 나가고 왕복 지연과 서버 비용이 생긴다.
   **꼬리:** 모델을 브라우저 캐시에 남긴다면 어떤 비용이 사라지고 어떤 비용은 그대로 남는가?
   **틀리기 쉬운 답:** "모델을 캐싱하면 16MB 문제는 해결된다." 첫 방문 비용과 단일 파일 번들에 못 담는다는 제약은 그대로다.

### 더 파볼 것
- [MediaPipe Interactive segmentation task](https://developers.google.com/edge/mediapipe/solutions/vision/interactive_segmenter) — 시드(점·브러시) 입력 규약, MagicTouch 모델 구조, 출력이 float32 신뢰도 마스크라는 점과 Web/JS 구현
- [Ramer–Douglas–Peucker algorithm](https://en.wikipedia.org/wiki/Ramer%E2%80%93Douglas%E2%80%93Peucker_algorithm) — `simplify(..., 1.2)`의 ε이 하는 일과 시간복잡도(평균 Ω(n log n), 최악 O(n²))
