# 정정공시 체인

## 1. 한 줄 정의

정정공시를 원공시와 `superseded_by` / `supersedes`로 연결해 두고,
일반 조회는 최신 유효 판만 돌려주되 "정정 전에는 얼마였나"는 별도 테이블에서 읽게 하는 데이터 모델.

## 2. 어디서 썼는가

- [[miraeasset-ai-festival-2026]] — DART 공시 4,204건을 SQLite `disclosure.db`로 적재하면서 적용. `corrections` 테이블 2,160행.

## 3. 실제로 겪은 문제와 해결

### 왜 필요한가

공시 데이터에서 같은 계약 한 건이 원공시 + 정정공시 여러 건으로 존재한다.
그냥 쌓아 두면 두 가지가 동시에 깨진다.

- 금액을 물었을 때 낡은 원공시 값이 나온다.
- "정정 이력이 있었나"를 물었을 때 답할 수 없다.

### 모델

- 원본 공시는 `superseded_by`로 무효화 표시하고, 정정공시는 `supersedes`로 원본을 가리킨다. 초기 설계 단계에서 이미 "본문 표가 정정후 최신값, 원본은 `superseded_by`로 무효화"라는 판단 기준을 세워 두었다.
- 도구 조회의 **기본값은 최신 유효 판**이다.
- 정정 전후 값은 `corrections` 테이블(정정 전·후 항목)에서 읽는다.
- 계약 관련 질의는 `contracts` / `corrections` / `terminations`(1,106 / 2,160 / 20행)를 함께 본다.

### 답변 쪽에서의 규칙

- 인용은 질문이 특정한 **공시 체인 안에서만** 한다. 같은 유형의 다른 연도 공시가 함께 검색돼도 그 값을 끌어오지 않는다.
- 검증 단계에서 철회·정정 사실을 답변에 덧붙인다.

### 남은 한계

같은 달에 같은 상대방과 맺은 계약이 여럿이면, 질문만으로 어느 건인지 특정하지 못할 수 있다.
체인은 "같은 건의 버전"은 묶지만 "다른 건의 구분"까지 해결해 주지는 않는다.

### 설명할 수 있어야 하는 것
- 같은 계약 한 건이 원공시와 정정공시 여러 건으로 존재하는데 그냥 쌓아 두면 금액을 물었을 때 낡은 값이 나오고 정정 이력도 답할 수 없다는 것을, 그래서 체인으로 묶은 이유와 함께 설명할 수 있습니다.
- 정정본으로 원본을 덮어쓰면 조회는 단순해지지만 정정 전에는 얼마였나를 잃는다는 것과, 두 판을 다 남긴 대신 조회마다 어느 판인지 정해야 하는 부담을 졌다는 것을 말할 수 있습니다.
- 체인이 같은 건의 버전만 묶기 때문에 같은 달에 같은 상대방과 맺은 다른 계약이 여럿이면 질문만으로 특정하지 못한다는 한계를 설명할 수 있습니다.

### 확인 질문
1. **Q:** (L1 개념) 정정공시 체인이 어떤 모델이고, 최신값으로 덮어쓰지 않으신 이유는 무엇인가요?
   **A:** 원본 공시는 `superseded_by`로 무효화 표시하고 정정공시는 `supersedes`로 원본을 가리키게 해서 같은 건의 버전들을 연결했습니다. 덮어쓰면 정정 전에는 얼마였나와 정정 이력이 있었나에 답할 수 없기 때문입니다. 초기 설계 단계에서 이미 본문 표는 정정후 최신값으로 두고 원본은 `superseded_by`로 무효화한다는 기준을 세워 두었고, DART 공시 4,204건을 SQLite `disclosure.db`로 적재하면서 적용했습니다. `corrections` 테이블은 2,160행입니다.
   **꼬리:** 그러면 정정이 두 번 이상 일어나면 체인은 어떻게 이어지고 최신 판은 어떻게 찾나요?
   **틀리기 쉬운 답:** 최신 공시만 남기고 나머지를 지우면 된다고 답하는 경우가 있는데, 실제로는 정정 이력 자체가 질의 대상이라 이력을 지우면 답할 수 없는 질문이 생깁니다.
2. **Q:** (L2 판단) 도구 조회의 기본값을 최신 유효 판으로 두신 이유는 무엇이고, 정정 전 값은 어디서 읽나요?
   **A:** 대부분의 질문이 현재 유효한 금액과 조건을 묻기 때문에 기본값을 최신 유효 판으로 두면 흔한 질문에서 낡은 값이 새어 나올 여지가 없다고 판단했습니다. 정정 전후 값은 별도의 `corrections` 테이블(정정 전·후 항목)에서 읽고, 계약 관련 질의는 `contracts` / `corrections` / `terminations`(각각 1,106 / 2,160 / 20행)를 함께 봅니다. 기본 경로는 안전하게 두고 이력은 명시적으로 요구할 때만 꺼내는 쪽으로 정리했습니다.
   **꼬리:** 그러면 반대로 기본값을 모든 판으로 두면 어떤 오답이 늘어나나요?
   **틀리기 쉬운 답:** 조회할 때마다 최신인지 판단하면 된다고 답하는 경우가 있는데, 실제로 기본값을 정해 두지 않으면 호출 지점마다 판단이 갈려 같은 질문에 다른 답이 나옵니다.
3. **Q:** (L2 판단) 데이터 모델만으로 부족해서 답변 쪽에 더하신 규칙은 무엇인가요?
   **A:** 인용을 질문이 특정한 공시 체인 안에서만 하도록 묶었고, 같은 유형의 다른 연도 공시가 함께 검색돼도 그 값을 끌어오지 않게 했습니다. 검증 단계에서는 철회와 정정 사실을 답변에 덧붙입니다. 스키마가 버전을 구분해 두어도 검색이 다른 체인의 문서를 가져오면 결국 섞이기 때문에 모델과 답변 규칙이 짝을 이뤄야 한다고 생각합니다.
   **꼬리:** 그러면 다른 연도 공시의 값을 끌어오지 않는다는 것을 자동으로 검사하려면 무엇을 보면 되나요?
   **틀리기 쉬운 답:** 스키마를 제대로 만들면 답변 규칙은 필요 없다고 답하는 경우가 있는데, 실제로 검색 결과에 다른 체인이 섞이는 것은 스키마가 막아 주지 않습니다.
4. **Q:** (L3 한계) 이 체인으로는 풀리지 않는 질문은 어떤 것인가요?
   **A:** 같은 달에 같은 상대방과 맺은 계약이 여럿이면 질문만으로 어느 건인지 특정하지 못할 수 있습니다. 체인은 같은 건의 버전은 묶지만 다른 건의 구분까지 해 주지는 않습니다. 버전 축은 정리됐어도 동일 키 후보가 여럿인 식별 문제는 그대로 남아 있다고 봅니다.
   **꼬리:** 그러면 이 모호함을 줄이려면 어떤 필드를 식별자로 더 잡으시겠어요?
   **틀리기 쉬운 답:** 정정 체인을 더 촘촘히 연결하면 해결된다고 답하는 경우가 있는데, 실제로는 연결 대상이 되는 건 자체가 특정되지 않는 문제라 축이 다릅니다.
