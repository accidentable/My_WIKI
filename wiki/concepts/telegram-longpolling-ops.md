## 한 줄 정의

텔레그램 봇 명령을 웹훅 대신 롱폴링(`getUpdates`)으로 받으면
공개 엔드포인트도 인바운드 포트도 없이 서버 1대에서 봇을 운영할 수 있다.

## 어디서 썼는가

- [[kis-openapi-invest-2026-09]] — `core/commands.py`, `cli.py serve`

## 실제로 겪은 문제와 해결

- 롱폴링은 서버가 텔레그램 쪽으로 나가는 연결만 쓴다. 방화벽에 구멍을 내거나
  API Gateway 같은 공개 엔드포인트를 둘 필요가 없다.
- 웹훅을 쓰지 않으니 `getUpdates` 409 충돌이 구조적으로 생기지 않는다.
  단, 예전 배포에서 남은 웹훅이 걸려 있으면 `getUpdates`가 막혀 409가 난다.
  위 프로젝트는 `cli.py chatid --reset-webhook`으로 해제하고, `cli.py serve`도
  시작할 때 자동으로 해제한다.
- 스케줄러(APScheduler)와 롱폴링 스레드를 같은 프로세스에 두면 실행 단위가 하나로 끝난다.
  프로세스가 죽는 것이 유일한 단일 장애점이라 systemd `Restart=always`로 10초 뒤 자동 재기동한다.
- 대안인 AWS 람다 + API Gateway 웹훅 구성은 프로세스 사망 걱정이 없는 대신
  컴포넌트가 5개로 늘고 장애 추적에 CloudWatch를 뒤져야 한다.
- 봇 토큰은 `@BotFather`에게 `/newbot`, chat ID는 봇에게 메시지를 보낸 뒤 조회한다.

### 확인 질문
1. **Q:** (L1 개념) 롱폴링과 웹훅은 무엇이 다르고, 롱폴링이 유리한 상황은 언제인가?
   **A:** 롱폴링은 내 서버가 텔레그램에 `getUpdates`를 걸어 두고, 새 업데이트가 생기거나 타임아웃이 될 때까지 응답을 기다리는 방식이다. 즉 **나가는 연결만** 쓴다. 웹훅은 반대로 텔레그램이 내 공개 URL로 요청을 밀어 넣으므로 공개 엔드포인트와 인바운드 경로가 필요하다. 서버 1대로 돌리는 봇처럼 방화벽에 구멍을 내거나 API Gateway를 세우기 싫은 상황에서는 롱폴링이 유리하다.
   **꼬리:** 일반 폴링과 롱폴링은 요청 수와 지연 면에서 어떻게 다른가?
   **틀리기 쉬운 답:** "롱폴링은 WebSocket처럼 서버가 먼저 밀어 주는 방식이다." 연결을 여는 쪽은 언제나 내 서버이고, 그래서 인바운드 포트가 필요 없는 것이다.
2. **Q:** (L2 판단) 이 프로젝트가 롱폴링 + 서버 1대를 택한 이유는 무엇이고, 그 대가로 무엇을 떠안았는가?
   **A:** `python cli.py serve` 한 줄이면 APScheduler가 09:05 진입 / 장중 10분 감시 / 15:15 마감을 KST로 돌리고, **같은 프로세스 안에서** 텔레그램 롱폴링 스레드가 명령을 받는다. 실행 단위가 하나라 배포·추적이 단순하고, 공개 엔드포인트도 인바운드 포트도 필요 없다. 대가는 **프로세스 사망이 유일한 단일 장애점**이라는 것이고, systemd `Restart=always`로 10초 뒤 자동 재기동해 버틴다. 대안인 AWS 람다 + API Gateway 웹훅 구성은 프로세스 사망 걱정이 없는 대신 컴포넌트가 5개로 늘고 장애 추적에 CloudWatch를 뒤져야 한다.
   **꼬리:** 스케줄러와 폴링을 한 프로세스에 둔 탓에 같이 죽는 것은 무엇이고, 나누면 무엇이 복잡해지는가?
   **틀리기 쉬운 답:** "공개 엔드포인트가 없으니 장애 지점도 없다." 공개 면은 줄었지만 프로세스 하나가 전부를 떠안는 구조로 바뀌었을 뿐이다.
3. **Q:** (L3 한계) `getUpdates` 409 충돌은 왜 나는가? 웹훅을 안 쓰면 정말 안 나는가?
   **A:** 텔레그램은 웹훅과 `getUpdates`를 동시에 쓸 수 없어서, 웹훅이 설정된 상태로 `getUpdates`를 부르면 충돌이 난다. 이 프로젝트는 웹훅을 쓰지 않으니 그 충돌이 **구조적으로는** 생기지 않는다. 다만 예외가 하나 있다 — **예전 배포에서 남은 웹훅이 걸려 있으면** `getUpdates`가 막혀 409가 난다. 그래서 `cli.py chatid --reset-webhook`으로 해제할 수 있게 했고, `cli.py serve`도 시작할 때 자동으로 해제한다. 즉 "쓰지 않는다"가 아니라 "확실히 꺼 둔다"까지 해야 성립한다.
   **꼬리:** 처리량을 늘리려고 같은 봇 토큰으로 서버를 2대 띄우면 어떻게 되는가?
   **틀리기 쉬운 답:** "409는 봇 토큰이 잘못됐다는 뜻이다." 토큰은 멀쩡하고, 같은 토큰에 대해 업데이트를 가져가려는 주체가 둘이라는 뜻이다.
4. **Q:** (L2 판단) 매매 판단을 봇이 하지 않는데 왜 텔레그램 채널을 붙였는가?
   **A:** 이 봇은 **LLM을 쓰지 않고 매매 판단은 전부 코드가 한다.** 텔레그램은 모니터링과 비상 개입용 창구다. `/status`(보유 포지션·손익·보유일차·현재 5일선), `/scan`(주문 없이 시그널만), `/history`, `/config`, `/pause`, `/resume`, `/sell 005930`을 제공한다. 특히 `/pause`는 **자동 진입만 정지하고 보유 종목의 청산 감시는 계속한다** — 개입은 새 위험을 막는 데 쓰고, 이미 진 위험을 방치하지는 않는다는 설계다.
   **꼬리:** `/pause`가 청산 감시까지 멈추는 구현이었다면 어떤 사고가 날 수 있는가?
   **틀리기 쉬운 답:** "봇에 명령 창구가 있으니 판단도 맡길 수 있겠다." 판단은 코드에 두고 사람의 개입 경로만 연 것이 이 설계의 요점이다.
