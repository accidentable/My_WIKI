## 1. 한 줄 정의

해커톤 프로토타입에서 "실물 자산"을 흉내 내야 할 때, 테스트넷에 기업별 ERC-20을 배포하고 서버가 조건 충족을 확인한 뒤 `onlyOwner mint`로 유저 지갑에 지급하는 구조.

## 3. 실제로 겪은 문제와 해결

네트워크는 Base Sepolia 테스트넷. 선택 이유는 Ray가 Base 해커톤 수상 경험이 있어 익숙하고, 테스트넷이라 가스비가 없으며, 추후 Base 메인넷으로 옮길 수 있기 때문. 테스트넷 ETH는 faucet에서 무료 수급.

컨트랙트는 OpenZeppelin `ERC20` + `Ownable`을 상속한 최소 구성이고, 기업마다 별도 토큰을 둔다(예: `KO_005930` = 삼성전자).

```solidity
contract KoWalkToken is ERC20, Ownable {
    constructor(string memory name, string memory symbol)
        ERC20(name, symbol)
        Ownable(msg.sender) {}

    // 서버에서 퀴즈 통과 확인 후 호출
    function mint(address to, uint256 amount) external onlyOwner {
        _mint(to, amount);
    }
}
```

핵심 설계 판단은 **지급 권한을 온체인이 아니라 서버에 둔 것**이다. 퀴즈 채점·위치 검증 같은 조건은 오프체인에서 하고, 컨트랙트는 owner만 mint할 수 있게 해 두어 단순하게 유지한다. 발행 트랜잭션 해시는 `visits.tx_hash`에 저장해 수집 성공 화면에서 그대로 보여 준다.

지갑은 별도 월렛 앱 연동 없이 앱 내장으로 만들고 privateKey를 Secure Storage에 저장한다. 온보딩에서 자동 생성되므로 유저가 지갑 개념을 몰라도 진입할 수 있다. 프론트 연동은 ethers.js v6로 잔액 조회·포트폴리오 표시.

범위 제한: 이 토큰은 실제 주식이 아니고, 화면의 가치 표기("만원 상당")도 표시용일 뿐이라고 원자료가 명시하고 있다.

## 학습

### CS 주제
- 보안: 권한 분리, 단일 소유자(onlyOwner)의 단일 실패점, 개인키 보관
- 소프트웨어공학: 온체인/오프체인 경계 설정, 프로토타입에서의 범위 제한
- 블록체인: ERC-20 표준, 테스트넷과 메인넷의 차이

### 설명할 수 있어야 하는 것
- 퀴즈 통과나 위치 검증 같은 조건은 온체인에서 확인할 수 없어서 조건 판정은 서버가 하고 컨트랙트는 `onlyOwner mint`만 남겨 단순하게 둔 이유를 설명할 수 있습니다.
- 지급 조건을 컨트랙트에 넣으면 신뢰가 덜 필요하지만 오프체인 데이터를 넣을 방법이 없었다는 점과, 서버 신뢰를 전제하는 대신 구현을 단순하게 만든 대가를 말할 수 있습니다.
- owner 키가 털리면 무제한 발행이 가능하고 앱 내장 지갑의 privateKey가 단말에 있어 단말 탈취가 곧 자산 탈취라는 점, 계획 단계 문서라 실제 운영 검증이 없다는 점을 설명할 수 있습니다.

### 확인 질문
1. **Q:** (L1 개념) `onlyOwner mint`는 무엇을 보장하고 무엇을 보장하지 않나요?
   **A:** `Ownable`의 `onlyOwner`는 호출한 계정이 저장된 owner 주소와 같은지만 확인합니다. 이 프로젝트에서는 서버가 퀴즈 통과를 확인한 뒤 owner 키로 `mint(to, amount)`를 부르기 때문에 다른 사람이 임의로 토큰을 찍는 일은 막힙니다. 다만 owner 자신이 무제한 발행할 수 있다는 점은 그대로 남아서, owner 키가 유출되면 토큰 경제 전체가 무너진다고 봤습니다. 보장되는 것은 외부인의 발행 차단이지 발행량의 정당성은 아니라고 정리했습니다.
   **꼬리:** 그러면 실서비스라면 owner를 무엇으로 대체하시겠어요?
   **틀리기 쉬운 답:** "owner만 mint할 수 있으니 안전합니다"라고 답하는 경우가 있는데, 실제로는 중앙화 위험을 없앤 게 아니라 한 계정에 모은 것입니다.
2. **Q:** (L2 판단) 지급 조건 판정을 컨트랙트가 아니라 서버에 두신 이유는 무엇인가요?
   **A:** 퀴즈 채점과 위치 검증이 오프체인 데이터에 기대고 있어서 컨트랙트가 스스로 확인할 수 없었습니다. 그래서 조건 판정은 서버가 하고 컨트랙트는 owner만 mint할 수 있게 해서 OpenZeppelin `ERC20`과 `Ownable`을 상속한 최소 구성으로 뒀습니다. 대신 발행 트랜잭션 해시를 `visits.tx_hash`에 저장해 수집 성공 화면에서 그대로 보여 줘서, 사용자가 지급 사실을 체인에서 확인할 수 있게 했습니다. 기업마다 별도 토큰을 두는 구성(`KO_005930`이 삼성전자)도 컨트랙트를 단순하게 유지하려는 선택의 일부였습니다.
   **꼬리:** 그러면 서버가 거짓으로 지급했을 때 사용자는 그걸 어떻게 알 수 있을까요?
   **틀리기 쉬운 답:** "온체인 기록이 남으니 지급이 공정합니다"라고 답하는 경우가 있는데, 실제로 기록되는 것은 발행 사실이지 조건 충족 여부가 아닙니다.
3. **Q:** (L3 한계) Base Sepolia 테스트넷을 고르신 근거는 무엇이고, 메인넷으로 옮기면 어디가 먼저 문제가 될까요?
   **A:** Ray가 Base 해커톤 수상 경험이 있어 익숙했고, 테스트넷이라 가스비 부담이 없으며 테스트넷 ETH는 faucet에서 무료로 받을 수 있고, 나중에 Base 메인넷으로 옮길 수 있다는 점이 이유였습니다. 옮기면 발행 트랜잭션마다 실제 가스비가 들어 사용자 방문 1건당 비용이 생기고, 앱 내장 지갑 privateKey를 Secure Storage에 두는 구성이 실자산을 다루게 됩니다. 원자료에도 적어 뒀듯이 이 토큰은 실제 주식이 아니고 화면의 만원 상당 표기도 표시용이라, 메인넷 발행은 그 범위 제한을 넘어서는 일이 된다고 생각합니다.
   **꼬리:** 그러면 방문마다 트랜잭션을 날리지 않으려면 지급 구성을 어떻게 바꾸시겠어요?
   **틀리기 쉬운 답:** "테스트넷에서 됐으니 메인넷도 그대로 됩니다"라고 답하는 경우가 있는데, 실제로는 비용 구성과 법적 성격이 함께 바뀝니다.
