# 백엔드 이중 구조와 로직 표류

## 1. 한 줄 정의

같은 서비스의 백엔드를 "풀 기능 로컬판(FastAPI + 스케줄러 + DB + WebSocket)"과 "배포용 서버리스판(요청마다 실시간 fetch, 상태 없음)" 둘로 두고 핵심 로직을 손으로 복제해 유지하는 구조. 빠르게 배포되지만 두 판이 곧 어긋난다.

## 2. 어디서 썼는가

- [[taco-index-2026-03]]: TACO Index. `backend/`(FastAPI)와 `api/`(Vercel 파이썬 함수)에 점수 엔진이 각각 들어 있고, `score_engine.py` 주석이 "(Vercel 배포 버전과 동기화)"라고 스스로 밝힌다.

## 3. 두 판이 어떻게 다른가

| | `backend/` (FastAPI) | `api/` (Vercel 서버리스) |
| --- | --- | --- |
| 프레임워크 | FastAPI + uvicorn, 라우터 3개 | 없음. `BaseHTTPRequestHandler` 직접 |
| 데이터 갱신 | APScheduler가 1분 간격 `collect_all_data()` | 요청이 올 때마다 fetch |
| 저장 | aiosqlite (`indicator_history`, `latest_indicators`) | 없음. Redis에 알림용 상태만 |
| 캐시 | 프로세스 메모리 전역 변수 `_latest_data` | HTTP `Cache-Control: s-maxage` (엣지) |
| 실시간 전파 | WebSocket 브로드캐스트 | 없음. 프론트가 폴링 |
| 수집 지표 | 확장 지표(휘발유·30년물·러셀2000) 포함 | 핵심 6개만 |

즉 서버리스판은 **"상시 프로세스가 없다"는 제약을 캐시 헤더와 Redis로 치환**한 축약판이다. 스케줄러는 크론으로, 메모리 캐시는 엣지 캐시로, DB 히스토리는 Yahoo에서 과거 구간을 매번 다시 받아 계산하는 방식(`/api/history`)으로 각각 대체됐다.

## 4. 왜 이렇게 되는가

원인은 대개 순서다. 먼저 익숙한 FastAPI로 전체를 만들고, 배포 단계에서 Vercel 무료 플랜(상시 프로세스 없음, WebSocket 없음, 로컬 파일 저장 불가)에 맞춰 급히 축약판을 따로 썼다. 첫 커밋 이틀째에 `fix: TS errors for Vercel deploy`가 나오는 걸 보면 배포가 초반 관심사였다(추정).

이 선택 자체는 합리적일 수 있다. 로컬판은 개발 중 WebSocket으로 즉시 확인하고 SQLite에 이력을 쌓을 수 있어 디버깅이 편하고, 배포판은 가볍고 공짜다.

## 5. 실제로 겪은 문제: 표류

TACO Index의 두 판은 이미 다음이 어긋나 있다.

- **총점 구성이 다르다.** `backend/app/services/data_collector.py`는 `core_values`를 만들 때 `["sp500", "vix", "treasury_10y", "oil", "dollar_index"]` 5개만 넣고 `approval_rating`을 빠뜨렸다. 그런데 `get_risk_level()`의 경계값(1.8/3.0/4.2)은 만점 6.0 기준 그대로다. 로컬판은 구조적으로 점수가 낮게 나온다. `api/_shared.py`의 `fetch_all()`은 6개를 모두 넣는다.
- **레벨 색이 다르다.** Lv.1이 backend는 `#16A34A`, api는 `#3CD5AF`.
- **주석과 상수가 다르다.** `api/_shared.py`에 `# S&P 500: safe=-5, redline=-20`이라 써 있지만 실제는 `-3.0 / -15.0`.
- **히스토리 티커가 다르다.** 실시간 `ES=F`, 히스토리 `^GSPC`.

어느 쪽도 에러를 내지 않고 사용자에게 보이지도 않는다. 이게 복제 유지의 성질이다. 같은 이름의 상수와 같은 모양의 함수가 두 곳에 있으면, 한쪽만 고친 것을 리뷰에서 잡아낼 방법이 없다.

## 6. 다음에 어떻게 할 것인가

- **순수 로직은 프레임워크 없는 모듈 하나로 빼고 양쪽이 import한다.** 점수 엔진은 외부 의존이 없는 순수 함수라 공유가 쉬웠다. 이 프로젝트는 그러지 않고 복사했다.
- 공유가 구조상 불가능하면(서버리스 번들 경로 제약 등) **같은 입력에 두 구현이 같은 점수를 내는지 확인하는 테스트 하나**라도 둔다.
- **배포 환경의 제약을 먼저 확인하고 로컬판을 그 제약 안에서 만든다.** WebSocket과 상시 스케줄러를 쓸 수 없는 곳에 배포할 것이라면 로컬판에도 굳이 넣지 않는 편이 낫다.
- 배포판만 살아 있다면 **로컬판을 지우는 것도 선택지**다. TACO Index에서 `backend/`가 실제로 어디에 배포됐는지는 자료에 없다(추정: 로컬 개발용).

## 학습

### CS 주제
- 소프트웨어공학: DRY와 단일 진실 원천, 복제된 로직의 표류, 두 구현을 묶는 계약 테스트
- 클라우드: 상시 프로세스가 없는 환경의 제약과 그 치환(스케줄러→크론, 메모리 캐시→엣지 캐시)
- 분산시스템: HTTP 캐시 의미론(`s-maxage`, `stale-while-revalidate`)과 신선도

### 설명할 수 있어야 하는 것
- 익숙한 FastAPI로 전체를 먼저 만들고 배포 단계에서 Vercel 제약(상시 프로세스·WebSocket·로컬 파일 저장 불가)에 맞춰 축약판을 따로 썼다는 순서와, 그 치환 관계(스케줄러→크론, 메모리 캐시→`s-maxage` 엣지 캐시, SQLite 이력→매번 재계산, WebSocket→폴링)를 말할 수 있습니다.
- 두 판을 유지해 얻은 것과 포기한 것을 설명할 수 있습니다. 로컬은 WebSocket과 SQLite로 디버깅이 편하고 배포판은 가볍고 공짜였지만, 순수 함수인 점수 엔진조차 공유 모듈로 빼지 않고 복사했습니다.
- 표류가 어디서 났고 왜 안 잡혔는지 설명할 수 있습니다. `core_values` 5개와 6개로 총점 구성이 어긋났는데 경계값은 만점 6.0 기준 그대로였고, 레벨 색과 주석 상수, 히스토리 티커까지 어긋났는데도 어느 쪽도 에러를 내지 않았습니다.

### 확인 질문
1. **Q:** (L1 개념) 상시 프로세스가 없는 서버리스 환경에서는 스케줄러와 메모리 캐시, WebSocket, DB 히스토리를 각각 무엇으로 대체하나요?
   **A:** TACO Index의 두 판을 나란히 놓으면 치환 관계가 그대로 보입니다. APScheduler의 1분 주기 `collect_all_data()`는 크론으로 바꿔 요청이 올 때마다 fetch하게 했고, 프로세스 메모리 전역 변수 `_latest_data`는 HTTP `Cache-Control: s-maxage` 엣지 캐시로, aiosqlite에 쌓던 `indicator_history`는 Yahoo에서 과거 구간을 매번 다시 받아 계산하는 방식(`/api/history`)으로, WebSocket 브로드캐스트는 프론트의 폴링으로 대체했습니다. 서버리스판은 상시 프로세스가 없다는 제약을 캐시 헤더와 Redis로 치환한 축약판이라고 보시면 됩니다.
   **꼬리:** 그러면 `max-age`와 `s-maxage`는 무엇이 다르고, `stale-while-revalidate`는 사용자 체감을 어떻게 바꾸나요?
   **틀리기 쉬운 답:** 서버리스도 인스턴스가 살아 있는 동안은 전역 변수 캐시가 통한다고 답하는 경우가 있는데, 실제로는 인스턴스가 언제 재활용될지 믿을 수 없어 정확성을 거기에 걸 수 없고, 그래서 알림용 직전 레벨도 Redis에 두었습니다.
2. **Q:** (L2 판단) 백엔드가 두 판이 된 경위는 무엇이고, 그 선택에 합리적인 면은 어디였나요?
   **A:** 원인은 대체로 순서였습니다. 익숙한 FastAPI로 전체를 먼저 만들고, 배포 단계에서 Vercel 무료 플랜의 제약(상시 프로세스 없음, WebSocket 없음, 로컬 파일 저장 불가)에 맞춰 급히 축약판을 따로 썼습니다. 첫 커밋 이틀째에 `fix: TS errors for Vercel deploy`가 나오는 것을 보면 배포가 초반 관심사였던 것 같습니다(추정). 선택 자체는 합리적일 수 있다고 생각하는데, 로컬판은 개발 중 WebSocket으로 즉시 확인하고 SQLite에 이력을 쌓을 수 있어 디버깅이 편했고 배포판은 가볍고 공짜였습니다.
   **꼬리:** 그러면 처음부터 배포 제약에 맞춰 하나만 만들었다면 개발 과정에서 무엇을 잃으셨을까요?
   **틀리기 쉬운 답:** 중복이니 무조건 잘못된 설계라고 답하는 경우가 있는데, 실제 문제는 중복 자체가 아니라 복제본을 동기화할 장치를 두지 않은 것이었습니다.
3. **Q:** (L3 한계) 표류가 실제로 어디에 났고 왜 아무도 잡지 못했나요?
   **A:** 네 군데가 이미 어긋나 있었습니다. 총점 구성에서 `backend/app/services/data_collector.py`가 `core_values`에 `["sp500", "vix", "treasury_10y", "oil", "dollar_index"]` 5개만 넣고 `approval_rating`을 빠뜨렸는데 `get_risk_level()`의 경계값(1.8/3.0/4.2)은 만점 6.0 기준 그대로여서 로컬판은 점수가 낮게 나오고, `api/_shared.py`의 `fetch_all()`은 6개를 모두 넣습니다. 레벨 색은 Lv.1이 backend에서 `#16A34A`, api에서 `#3CD5AF`로 갈렸고, `api/_shared.py`에는 `# S&P 500: safe=-5, redline=-20`이라고 써 있지만 실제 값은 `-3.0 / -15.0`이며, 히스토리 티커도 실시간은 `ES=F`, 히스토리는 `^GSPC`였습니다. 잡지 못한 이유는 어느 쪽도 에러를 내지 않고 사용자에게 보이지도 않기 때문이고, 같은 이름의 상수와 같은 모양의 함수가 두 곳에 있으면 한쪽만 고친 것을 리뷰에서 걸러낼 방법이 없다고 생각합니다.
   **꼬리:** 그러면 이런 종류의 버그를 잡는 테스트는 어떤 모양이어야 하고, 단위 테스트로는 왜 부족한가요?
   **틀리기 쉬운 답:** 상수 이름이 같으니 IDE나 리뷰에서 걸린다고 답하는 경우가 있는데, 실제로 이름이 같다는 사실은 값이 같다는 보장을 주지 않습니다.
4. **Q:** (L2 판단) 다시 하신다면 무엇을 다르게 하시겠어요?
   **A:** 네 가지를 적어 두었습니다. 먼저 순수 로직은 프레임워크 없는 모듈 하나로 빼고 양쪽이 import하게 하겠습니다. 점수 엔진은 외부 의존이 없는 순수 함수라 공유가 쉬웠는데도 복사했습니다. 공유가 구조상 불가능하면, 예를 들어 서버리스 번들 경로 제약 같은 것이 걸리면, 같은 입력에 두 구현이 같은 점수를 내는지 확인하는 테스트 하나라도 두겠습니다. 배포 환경의 제약을 먼저 확인하고 로컬판을 그 제약 안에서 만드는 편이 낫다고 보는데, WebSocket과 상시 스케줄러를 쓸 수 없는 곳에 배포할 것이라면 로컬판에도 굳이 넣지 않겠습니다. 배포판만 살아 있다면 로컬판을 지우는 것도 방법인데, TACO Index에서 `backend/`가 실제로 어디에 배포됐는지는 자료에 없습니다(추정: 로컬 개발용).
   **꼬리:** 그러면 두 구현이 같은 점수를 낸다는 테스트는 어떤 입력 집합으로 돌려야 의미가 있을까요?
   **틀리기 쉬운 답:** `(Vercel 배포 버전과 동기화)` 같은 주석을 달아 두면 동기화된다고 답하는 경우가 있는데, 실제로 `score_engine.py`에 그 주석이 달려 있는데도 네 군데가 어긋났습니다.

### 더 파볼 것
- [Don't repeat yourself](https://en.wikipedia.org/wiki/Don%27t_repeat_yourself) — "모든 지식은 단 하나의 명확하고 권위 있는 표현을 가져야 한다"는 원 문장, 그리고 중복(WET)이 만드는 유지보수 비용
- [Single source of truth](https://en.wikipedia.org/wiki/Single_source_of_truth) — 사본을 두더라도 읽기 전용으로 두거나 조정 장치를 붙여야 하는 이유, 독립적으로 편집되는 사본이 시간이 갈수록 어긋나는 메커니즘
