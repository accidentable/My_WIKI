## 1. 한 줄 정의

음성을 텍스트로 옮기면서(전사) 동시에 "누가 말했는가"로 발언을 나누는 것. 대화형 영상에서는 전사만으로는 부족하고, 발언 주체가 붙어야 근거로 쓸 수 있다.

## 2. 어디서 썼는가

- [[wanted-interview-ai-2026]] — FRAME. AssemblyAI(`universal-2` 기본값)로 한국어 전사와 화자 구분을 수행한다.

## 3. 실제로 겪은 문제와 해결

녹화 면접 영상에는 면접관과 지원자의 말이 섞여 있다. 전사문만 있으면 "협업 경험을 말해달라"는 질문과 그에 대한 답변이 구분되지 않아, 기준별 근거를 뽑을 때 면접관의 말이 지원자의 근거로 잡힐 수 있다.

FRAME의 처리 방식은 **자동 화자 구분 + 사람의 역할 지정**의 2단계다. AssemblyAI가 화자를 분리해 주면, 사용자가 전사된 발언을 보고 어느 화자가 지원자이고 어느 쪽이 면접관인지 직접 지정한다. 화자 지정이 끝나야 근거 분석 단계로 넘어간다. 즉 모델은 "화자 A/B"까지만 책임지고, "A가 지원자"라는 역할 매핑은 사람이 확정한다. 이렇게 확정된 역할이 [[evidence-linked-llm-output]]의 전제가 된다.

운영상 기록된 것:

- 전사는 [[background-job-pipeline]]의 백그라운드 작업으로 돌린다. 영상 업로드 후 전사 완료 → 화자 지정 → 분석이라는 순서가 강제된다.
- 전사 모델은 `ASSEMBLYAI_MODEL` 환경변수로 바꿀 수 있지만, 바꿀 때 **한국어 전사와 화자 구분을 지원하는지** 확인해야 한다고 문서에 못박아 두었다.
- 전사를 위해 영상 자체가 AssemblyAI로 전달된다. 삭제 요청 시 저장된 영상뿐 아니라 **외부 전사도 함께 삭제**하고, 실패하면 정리 작업에서 재시도한다.
- 입력은 한국어 MP4 최대 50MB·15분으로 제한했다.

### 확인 질문
1. **Q:** (L1 개념) 전사(transcription)와 화자 구분(diarization)은 무엇이 다르고, 화자 구분이 실제로 내놓는 것은 무엇인가?
   **A:** 전사는 음성을 텍스트로 옮기는 것이고, 화자 구분은 "언제부터 언제까지를 누가 말했는가"로 발언을 나누는 것이다. 중요한 점은 화자 구분이 **신원이 아니라 라벨**만 준다는 것이다. FRAME에서 AssemblyAI(`universal-2` 기본값)는 "화자 A/B"까지만 책임지고, 어느 쪽이 지원자이고 어느 쪽이 면접관인지는 사용자가 전사된 발언을 보고 직접 지정한다.
   **꼬리:** 화자 수를 미리 알려줄 수 있다면 정확도에 어떤 영향이 있고, 잘못 알려주면 어떻게 되는가?
   **틀리기 쉬운 답:** "diarization이 화자의 이름이나 역할까지 알아낸다." 모델이 내놓는 것은 A·B 같은 익명 라벨이다.
2. **Q:** (L2 판단) 왜 역할 매핑(A=지원자)을 자동화하지 않고 사람이 확정하게 했는가?
   **A:** 녹화 면접 영상에는 면접관과 지원자의 말이 섞여 있다. 전사문만 있으면 "협업 경험을 말해달라"는 **질문**과 그에 대한 **답변**이 구분되지 않아, 기준별 근거를 뽑을 때 면접관의 말이 지원자의 근거로 잡힐 수 있다. 그래서 FRAME은 자동 화자 구분 + 사람의 역할 지정이라는 2단계를 두고, 화자 지정이 끝나야 근거 분석으로 넘어가게 순서를 강제했다. 이렇게 확정된 역할이 [[evidence-linked-llm-output]]의 전제가 된다.
   **꼬리:** 사용자가 역할을 반대로 지정하면 뒤따르는 분석 결과는 어떤 방식으로 틀리는가?
   **틀리기 쉬운 답:** "질문·답변 말투를 보고 LLM이 역할을 붙이면 사람 단계는 없앨 수 있다." 서비스 원칙이 "사람의 최종 판단"이고, 역할 오배정은 근거 전체를 오염시키므로 자동 추정으로 되돌리기 어렵다.
3. **Q:** (L2 판단) 전사를 왜 요청 안에서 처리하지 않고 백그라운드 작업으로 뺐는가?
   **A:** 영상 전사와 뒤따르는 LLM 분석은 수 분이 걸릴 수 있어 서버리스 HTTP 요청 수명 안에서 끝나지 않는다. 그래서 업로드 직후에는 Supabase 비공개 버킷에 저장만 하고, 전사는 [[background-job-pipeline]]의 Trigger.dev 작업으로 돌린다. 그 결과 "영상 업로드 → 전사 완료 → 화자 지정 → 분석"이라는 순서가 구조적으로 강제된다.
   **꼬리:** 전사 작업이 중간에 실패하면 사용자 화면에는 무엇이 남고, 재시도는 누가 거는가?
   **틀리기 쉬운 답:** "업로드 응답에서 바로 전사 결과를 돌려주면 흐름이 단순해진다." 그 응답을 기다리는 동안 함수 수명이 먼저 끝난다.
4. **Q:** (L3 한계) 전사 모델을 바꾸려면 무엇을 먼저 확인해야 하고, 원본이 외부로 나가는 문제는 어떻게 처리했는가?
   **A:** 모델은 `ASSEMBLYAI_MODEL` 환경변수로 바꿀 수 있지만, 문서에 **한국어 전사·화자 구분·구조화된 응답을 지원하는지 확인하라고 못박아 두었다.** 셋 중 하나만 빠져도 뒷단이 조용히 망가진다. 데이터 쪽으로는, 전사를 위해 영상 자체가 AssemblyAI로 전달되므로 삭제 요청 시 저장된 영상뿐 아니라 **외부 전사도 함께 삭제**하고 실패하면 정리 작업에서 재시도한다. 입력은 한국어 MP4 최대 50MB·15분으로 제한했다.
   **꼬리:** 앱의 24시간 보관 정책과 외부 제공자의 데이터 처리 정책은 같은 것인가?
   **틀리기 쉬운 답:** "우리 스토리지에서 지웠으니 데이터는 다 지워졌다." 외부 전사본이 남고, 앱의 보관 기간과 제공자 정책은 문서에서 별개로 구분하고 있다.
