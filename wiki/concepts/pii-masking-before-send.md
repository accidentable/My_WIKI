# 전송 전 개인정보 마스킹과 그 한계

## 1. 한 줄 정의

사용자가 붙여넣은 청구 메일·카드 문자에서 카드번호·연락처·이름·주소·API 키·링크 토큰 등을 브라우저 단계에서 탐지·마스킹하고, 전송될 내용을 사용자가 눈으로 확인하게 하는 처리. 단 정규식만으로 완전 익명화를 보장하지는 않는다고 명시한다.

## 2. 어디서 썼는가

- [[finance-ai-2026-subscription-cut]] — 입력 화면과 `app/api/agent/route.ts`, `lib/case.ts`에 마스킹이 들어 있고, 테스트가 마스킹을 검증한다.

## 3. 실제로 겪은 문제와 해결

이 서비스는 성격상 가장 민감한 텍스트(카드 알림, 청구서)를 통째로 받는다. 설계는 네 겹으로 짰다.

- **전송 전 확인**: 브라우저에서 탐지·마스킹을 수행하고 사용자가 전송 내용을 확인한다. 정규식만으로 완전 익명화를 보장하지 않는다고 문서에 남겼다.
- **저장 최소화**: 마스킹된 사건 요약과 필요한 이력만 저장한다. 서버 요청 본문·오류 로그·분석 도구에 원문이 남지 않도록 구현·검증 항목에 포함했다. 원본 증빙은 사용자가 따로 보관한다.
- **사건 접근**: 합성 데이터 데모는 무작위 사건 링크와 삭제 기능을 쓴다. 실제 서비스에는 접근 보호와 링크 폐기가 필요하다고 따로 적었다.
- **보관 정책**: 데모 사건은 7일 후 자동 삭제. 실제 서비스의 보관기간은 별도 설계하며, 임의 기간을 "모든 분쟁의 최대 처리기간"이라고 설명하지 않는다.

이미지 입력에서 구멍이 하나 드러났다. 카드 문자·청구 화면 캡처는 최대 4장까지 첨부할 수 있는데, **사진은 자동 마스킹되지 않는다**. 대신 서버가 먼저 멀티모달 호출로 사진 속 글자를 옮겨 적고, 그 텍스트를 마스킹한 뒤 원문에 이어 붙이며, 이후 단계는 텍스트만 본다. 즉 원본 이미지는 최초 한 번 모델에 그대로 전달된다. 브라우저에서 1600px 이하 JPEG로 줄여 보내는 것은 용량 대책이지 마스킹이 아니다.

같은 맥락의 인접 원칙으로, 발신 도메인 대조 결과를 "발신자 인증"으로 표현하지 않는다. 복사한 본문만으로는 SPF·DKIM·DMARC 검증이 불가능하므로 일치 / 불일치 / 정보 부족으로만 표시하고 "정상 메일 인증 완료" 문구는 쓰지 않는다. 테스트에도 "발신 도메인 오인 방지" 항목이 있다.

### 설명할 수 있어야 하는 것
- 마스킹을 브라우저 단계에 두고도 완전 익명화가 아니라고 문서에 남긴 이유를 설명할 수 있습니다.
- 이미지 입력에서 어떤 구멍이 남았고 왜 그렇게 설계했는지를 대가와 함께 말할 수 있습니다.
- 무작위 링크와 7일 삭제 같은 데모 수준 보호가 실서비스 요구와 어떻게 다른지 말할 수 있습니다.

### 확인 질문
1. **Q:** (L1 개념) 정규식 마스킹으로 완전 익명화를 보장할 수 없다고 문서에 적으신 이유가 무엇인가요?
   **A:** 정규식은 카드번호나 연락처, API 키, 링크 토큰처럼 형식이 고정된 식별자에는 강한데, 이름이나 주소처럼 자유 서술로 들어오는 정보는 고정된 형식이 없습니다. 그래서 브라우저에서 탐지와 마스킹을 하되 정규식만으로 완전 익명화를 보장하지 않는다고 명시하고, 보내기 전에 사용자가 전송될 내용을 눈으로 확인하게 했습니다. 모자란 부분은 다른 겹으로 메웠는데, 저장은 마스킹된 사건 요약과 필요한 이력만 하고, 서버 요청 본문과 오류 로그, 분석 도구에 원문이 남지 않도록 구현·검증 항목에 넣었으며, 데모 사건은 7일 뒤 자동으로 지웁니다.
   **꼬리:** 그러면 같은 마스킹을 서버나 게이트웨이에서 하면 무엇이 좋아지고 무엇이 나빠질까요?
   **틀리기 쉬운 답:** "마스킹을 넣었으니 개인정보는 전송되지 않는다"라고 답하는 경우가 있는데, 실제로는 탐지하지 못한 값이 그대로 나갑니다.
2. **Q:** (L2 판단) 이미지 첨부가 왜 구멍이 되고, 어떻게 절충하셨나요?
   **A:** 카드 문자나 청구 화면 캡처를 최대 4장까지 붙일 수 있는데 사진은 자동 마스킹이 안 됩니다. 대신 서버가 먼저 멀티모달 호출로 사진 속 글자를 옮겨 적고, 그 텍스트를 마스킹한 뒤 원문에 이어 붙이고, 이후 단계는 텍스트만 보게 했습니다. 마스킹이 둘째 단계부터 걸리니까 원본 이미지는 최초 한 번 모델에 그대로 전달됩니다. 브라우저에서 1600px 이하 JPEG로 줄여 보내는 것은 용량 대책이라 마스킹으로 치지 않았습니다.
   **꼬리:** 그러면 그 최초 한 번을 없애려면 파이프라인의 무엇을 바꾸시겠어요?
   **틀리기 쉬운 답:** "해상도를 낮추면 사진 속 개인정보도 사실상 지워진다"라고 답하는 경우가 있는데, 실제로 축소는 용량 대책일 뿐입니다.
3. **Q:** (L1 개념 · L2 판단) 발신 도메인 대조 결과를 발신자 인증이라고 표시하지 않으신 이유가 있나요?
   **A:** 사용자가 복사해 붙여넣은 본문만으로는 SPF와 DKIM, DMARC 검증이 불가능하기 때문입니다. 그래서 결과를 일치, 불일치, 정보 부족 세 가지로만 표시하고 정상 메일 인증 완료 같은 문구는 쓰지 않았으며, 링크는 공식 경로를 직접 보여 줍니다. 테스트에도 발신 도메인 오인 방지 항목을 뒀습니다. 확정할 수 없는 것은 보류한다는 같은 프로젝트의 판단 원칙과 같은 줄기라고 생각합니다.
   **꼬리:** 그러면 본문 말고 무엇이 더 있어야 DMARC 판정이 가능할까요?
   **틀리기 쉬운 답:** "보낸 사람 도메인이 공식 도메인과 같으면 위조가 아니다"라고 답하는 경우가 있는데, 실제로 표시된 From 도메인은 그 자체로 인증 결과가 아닙니다.
4. **Q:** (L3 한계) 합성 데모에서 실제 사용자 데이터로 넘어가면 어디가 먼저 문제가 될까요?
   **A:** 사건 접근이 먼저라고 봅니다. 합성 데이터 데모는 무작위 사건 링크와 삭제 기능만 쓰기 때문에 링크를 아는 사람은 열 수 있고, 실제 서비스에는 접근 보호와 링크 폐기 기능이 필요하다고 따로 적어 뒀습니다. 보관 정책도 데모는 7일 자동 삭제지만 실제 서비스의 보관기간은 따로 설계해야 하고, 임의로 정한 기간을 모든 분쟁의 최대 처리기간이라고 설명하지 않기로 했습니다. 같이 묶이는 하나가 입력 신뢰 경계인데, 이메일이나 회신 본문의 지시는 사건 자료로만 다루고 AI가 그 지시에 따라 규칙을 바꾸거나 외부 도구를 실행하지 않게 했습니다.
   **꼬리:** 그러면 무작위 링크 대신 접근 보호를 넣으면 링크 폐기와 삭제는 각각 무엇을 지우는 동작이 되나요?
   **틀리기 쉬운 답:** "추측하기 어려운 URL이면 인증과 같은 효과다"라고 답하는 경우가 있는데, 실제로는 문서에도 데모 한정 조치라고 적어 뒀습니다.

### 더 파볼 것
- [Developers: Stop 80% of PII Before Any LLM Call (MLflow)](https://mlflow.org/articles/pii-redaction-llm) — 정규식 + 체크섬이 잡는 범위와, 자유 서술·동형문자(homoglyph)·토큰 분할처럼 정규식이 놓치는 유형을 구체적으로 나눈다.
- [PII masking patterns for LLM applications (Langfuse)](https://langfuse.com/resources/engineering/pii-masking-llm-applications) — 클라이언트·서버·게이트웨이 세 계층 중 어디에 마스킹을 둘지의 트레이드오프. 이 프로젝트가 클라이언트 계층을 택한 선택의 비교 대상.
- [RFC 7489 (DMARC)](https://datatracker.ietf.org/doc/html/rfc7489) — 판정에 원본 메시지와 DNS 조회, SPF·DKIM 정렬이 필요하다는 것. 본문 복사만으로 인증을 말할 수 없는 이유의 원문 근거.
