## 1. 한 줄 정의

웹 요청 안에서 끝낼 수 없는 긴 작업(전사, LLM 분석, 삭제)을 별도 워커로 빼고, 여기에 만료·정리 스케줄을 함께 붙여 데이터 보관 기간을 코드로 보장하는 구조.

## 2. 어디서 썼는가

- [[wanted-interview-ai-2026]] — FRAME. Trigger.dev로 전사·분석·삭제·만료 정리를 실행하고, 웹 앱은 Vercel에 배포한다.

## 3. 실제로 겪은 문제와 해결

### 왜 필요했나

영상 전사와 LLM 분석은 수 분이 걸릴 수 있어 서버리스 HTTP 요청 수명 안에서 끝나지 않는다. FRAME은 업로드 직후 Supabase 비공개 버킷에 저장만 하고, 이후 전사([[speaker-diarization]]) → 사용자 화자 확인 → 근거 분석([[evidence-linked-llm-output]])을 백그라운드 작업으로 이어 붙였다.

### 웹과 워커를 따로 배포한다

웹 앱(Vercel)과 백그라운드 작업(Trigger.dev)은 별개로 배포되고 환경변수도 각각 등록해야 한다. 자료에 기록된 함정 세 가지:

- Vercel에 등록하는 서버 비밀키에 `NEXT_PUBLIC_` 접두사를 붙이면 안 된다.
- Trigger.dev CLI의 `--env-file`은 **원격 작업의 환경변수를 자동 등록하지 않는다.** Production 환경에 Supabase·AssemblyAI·OpenAI 키와 모델 변수를 직접 등록해야 한다.
- `TRIGGER_SECRET_KEY`는 실행 환경에 맞는 키를 쓴다. 로컬은 Development, Vercel은 같은 프로젝트의 Production 키.

로컬에서는 웹과 별도 터미널에서 `npm run worker:dev`를 띄우고, 배포는 `npm run worker:deploy` + `npm run build`.

### 삭제를 작업으로 만든다

보관 기간을 문서로만 약속하지 않고 스케줄 작업으로 강제했다.

- 영상은 24시간 후 만료. `cleanup-expired-reviews` 스케줄이 **15분 주기**로 정리한다.
- 삭제 요청 시 저장된 영상과 외부(AssemblyAI) 전사를 함께 지우고, **실패한 삭제는 정리 작업에서 재시도**한다.
- 업로드 URL의 유효기간 동안 삭제 표식을 유지해, 삭제 이후 뒤늦게 올라오는 업로드도 정리한다.
- 배포 후 이 스케줄이 활성화되어 있는지 확인하라고 문서에 별도로 적어 두었다.

### 사용량 제한도 여기에 건다

한도는 Supabase 마이그레이션(`001_initial.sql`)이 만드는 사용량 제한 함수로 관리한다. 동시 보관 전체 15건, 최근 24시간 전체 업로드 예약 20건(`DAILY_UPLOAD_LIMIT`), 세션별 3건(`DAILY_SESSION_UPLOAD_LIMIT`). **업로드 예약은 실패해도 사용량에 포함**되며, 앱의 사용량 제한은 API 제공자의 결제 한도를 대체하지 않는다고 명시했다.

소유자 구분은 계정 없이 서명된 HttpOnly 쿠키로 한다. 쿠키를 지우거나 다른 브라우저를 쓰면 기존 영상에 접근할 수 없다.

## 학습

### CS 주제
- 분산시스템: 재시도와 멱등성, 실패한 작업의 뒤따라잡기(reconciliation)
- 클라우드: 서버리스 요청 수명 제한, 웹과 워커의 분리 배포와 환경변수
- 운영체제: 주기 스케줄(cron)과 만료 데이터 정리

### 설명할 수 있어야 하는 것
- 전사·분석이 서버리스 HTTP 요청 수명 안에서 끝나지 않아 업로드는 저장만 하고 나머지를 Trigger.dev 워커로 뺀 판단과, 그 결과 "전사 완료 → 화자 지정 → 분석" 순서가 구조적으로 강제된다는 점
- 보관 기간을 문서 약속 대신 `cleanup-expired-reviews` 15분 주기 스케줄로 강제하기로 한 선택과, 그 대가로 늘어난 운영 항목(웹·워커 이중 배포, 환경변수 각자 등록, 배포 후 스케줄 활성 확인)
- 삭제 재시도와 15분 재조회처럼 재실행을 전제로 설계한 부분과, 반대로 "업로드 예약은 실패해도 사용량에 포함"되어 재시도가 한도(전체 15건·일 20건·세션 3건)를 갉아먹는 부분

### 확인 질문
1. **Q:** (L1 개념) 긴 작업을 웹 요청 안에서 처리하지 않고 별도 워커로 빼는 이유는 무엇인가?
   **A:** 서버리스 HTTP 요청은 수명이 제한돼 있는데, 영상 전사와 LLM 분석은 수 분이 걸릴 수 있어 그 안에서 끝나지 않는다. 그래서 FRAME은 업로드 직후 Supabase 비공개 버킷에 저장만 하고 요청을 끝낸 뒤, 전사([[speaker-diarization]]) → 사용자 화자 확인 → 근거 분석([[evidence-linked-llm-output]])을 Trigger.dev 백그라운드 작업으로 이어 붙였다. 사용자는 기다리는 동안 다른 일을 할 수 있고, 서버는 요청 스레드를 붙잡지 않는다.
   **꼬리:** 작업이 어디까지 진행됐는지를 사용자에게 알리려면 무엇을 저장해야 하는가?
   **틀리기 쉬운 답:** "타임아웃을 늘리면 된다." 함수 실행 시간 상한은 늘려도 유한하고, 사용자가 브라우저를 닫으면 진행 상황이 사라진다.
2. **Q:** (L2 판단) 보관 기간을 문서에 적어 두는 대신 왜 스케줄 작업으로 강제했는가?
   **A:** 약속을 코드로 옮기지 않으면 지켜지는지 아무도 모르기 때문이다. FRAME은 영상을 24시간 후 만료시키고 `cleanup-expired-reviews` 스케줄이 **15분 주기**로 정리한다. 삭제 요청 시에는 저장된 영상과 외부(AssemblyAI) 전사를 함께 지우고, **실패한 삭제는 정리 작업에서 재시도**한다. 업로드 URL의 유효기간 동안 삭제 표식을 유지해, 삭제 이후 뒤늦게 올라오는 업로드까지 정리한다. 배포 후 이 스케줄이 실제로 활성화돼 있는지 확인하라고 문서에 따로 적어 둔 것도 같은 맥락이다.
   **꼬리:** 정리 작업이 하루 멈춰 있었다면, 다시 켰을 때 밀린 만료 건을 어떻게 따라잡는가?
   **틀리기 쉬운 답:** "삭제 API를 제공하니 보관 기간은 지켜진다." 사용자가 삭제를 누르지 않은 데이터가 남고, 삭제 자체가 실패할 수도 있다.
3. **Q:** (L2 판단) 웹 앱과 워커를 따로 배포할 때 실제로 걸렸던 함정은 무엇인가?
   **A:** 셋이 기록돼 있다. (1) Vercel에 등록하는 **서버 비밀키에 `NEXT_PUBLIC_` 접두사를 붙이면 안 된다.** 붙이면 클라이언트 번들로 새어 나간다. (2) Trigger.dev CLI의 `--env-file`은 **원격 작업의 환경변수를 자동 등록하지 않는다.** Production 환경에 Supabase·AssemblyAI·OpenAI 키와 모델 변수를 직접 등록해야 한다. (3) `TRIGGER_SECRET_KEY`는 실행 환경에 맞는 키를 써야 한다 — 로컬은 Development, Vercel은 같은 프로젝트의 Production. 로컬에서는 웹과 별도 터미널에서 `npm run worker:dev`를 띄우고, 배포는 `npm run worker:deploy` + `npm run build`다.
   **꼬리:** 워커에 환경변수 하나가 빠졌을 때 그 사실은 언제·어디서 처음 드러나는가?
   **틀리기 쉬운 답:** "`.env.local`을 워커도 같이 읽는다." 두 배포 대상은 환경변수를 각각 등록해야 한다.
4. **Q:** (L3 한계) 같은 작업이 두 번 돌거나 한 번 빠지면 무엇이 어긋나는가?
   **A:** 이 파이프라인은 재실행을 전제로 설계돼 있다. 삭제는 "실패하면 정리 작업이 다시 시도한다"는 구조여서 같은 대상을 여러 번 지워도 결과가 같아야 정상이고, 만료 정리는 15분마다 "지금 기준으로 만료된 것"을 훑는 방식이라 한 번 빠져도 다음 실행이 따라잡는다. 반면 **사용량 제한은 재시도에 취약하다.** 동시 보관 전체 15건, 최근 24시간 전체 업로드 예약 20건(`DAILY_UPLOAD_LIMIT`), 세션별 3건(`DAILY_SESSION_UPLOAD_LIMIT`)인데 **업로드 예약은 실패해도 사용량에 포함**되므로, 실패한 시도를 반복하면 한도를 스스로 갉아먹는다. 앱의 사용량 제한이 API 제공자의 결제 한도를 대체하지 않는다는 점도 문서에 명시돼 있다.
   **꼬리:** "상태를 active로 설정" 같은 작업과 "잔액을 10 증가" 같은 작업은 재시도에서 왜 다르게 행동하는가?
   **틀리기 쉬운 답:** "재시도를 켜 두었으니 중복 실행은 걱정하지 않아도 된다." 재시도는 작업이 멱등할 때만 안전장치가 되고, 아니면 중복 부작용 증폭기가 된다.
