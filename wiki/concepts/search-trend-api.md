# 검색어 트렌드 API로 관심도 시계열 만들기

## 1. 한 줄 정의

네이버 데이터랩 검색어트렌드와 구글 트렌드에서 받은 상대 검색량을, 기준 검색어와 이동평균으로 다듬어 서로 비교 가능한 관심도 시계열로 바꾸는 방법.

## 2. 어디서 썼는가

- [[bc-card-bigdata-2026]] — 2016-01~2026-09 유행 음식 26개의 검색량(네이버 주간, 구글 월간)을 수집해 유행의 정점 시점, 수명, 교체 간격을 계산했다.

- [[im-challenge-daegu-2026-sns-menu]], SNS 신메뉴 AI 컨설팅. 같은 기준자 방법을 **연령별 비교**에 썼다. Search Trend는 요청 단위로 정규화하므로 연령 필터를 따로 걸면 연령 간 크기를 비교할 수 없다. 한 요청에 기준자 그룹("날씨")을 함께 넣고 `후보 지수 합 ÷ 기준자 지수 합`으로 연령대별 상대 관심도를 냈다. 단계 판정에 쓰는 법은 [[search-index-stage-rule]], 이름 없는 후보를 찾는 앞 단계는 [[ngram-burst-discovery]].
  - 운영 메모(2026-09-14 확인): 네이버 개발자센터(developers.naver.com)에서 검색·데이터랩 API **신규 신청이 중단**됐다. 신규는 네이버 클라우드 플랫폼 → NAVER API HUB에서 Application을 만들고 "Search Trend"·"검색"을 구독해야 하며, 구독 없이 호출하면 `401 errorCode 210 Permission Denied`가 돌아온다. 구 방식(`X-Naver-Client-Id/Secret`, `openapi.naver.com`)은 기존 신청자만 2027-06-30까지 한시 사용. Search Trend는 현재 무료 월 5만 건·50 RPS이고 향후 유료화 공지 예정, 블로그 검색은 무료 일 25,000건.
  - 구글 트렌드는 이 프로젝트에서 비공식 `pytrends` 4.9.2로 받았고 연속 요청 시 429가 나 요청 간 25~30초 간격이 필요했다. `retries`를 주면 urllib3 2.x에서 `method_whitelist` 오류가 나므로 기본값을 썼다. 이후 구현에서는 공식 API가 없어 공개 급상승 RSS만 교차 확인 신호로 남겼다.
  - 정규화 회피의 또 다른 방법: 매일 고정 창(90일)을 통째로 다시 받아 덮어쓰기.

## 3. 실제로 겪은 문제와 해결

**문제 1: 검색량이 요청마다 상대값이다.** 네이버 데이터랩도 구글 트렌드도 결과가 "그 요청 안에서의 최댓값 = 100"인 상대값으로 나온다. 요청을 나눠 받으면 서로 다른 자로 잰 값이라 합칠 수 없다.

해결: 모든 요청에 기준 검색어 하나를 같이 넣었다. 이 프로젝트에서는 `마라탕`을 넣어 마라탕 최고치를 100으로 고정하고 나머지를 그 자에 맞춰 재스케일했다. 기준 검색어는 관측 기간 내내 꾸준히 검색되고 유행 곡선을 타지 않는 단어를 고르는 것이 중요하다.

**문제 2: 네이버 주간 검색량은 잡음이 심하다.** 해결: 4주 이동평균으로 평활한 뒤 정점 시점과 수명 지표를 계산했다.

**문제 3: 검색량이 작은 항목은 지표가 요동친다.** 뚱카롱·십원빵·온정돈까스처럼 검색량이 너무 작은 항목은 지속 기간 통계에서 제외했다. 마라탕·소금빵처럼 유행을 넘어 정착한 품목, 꼬꼬면·허니버터칩처럼 정점이 관측 범위(2016년~) 밖인 품목도 제외했다.

**문제 4: 엔진마다 결과가 다를 수 있다.** 두 엔진을 모두 돌려 대조했다.

- 일치한 것: 정점 시점(탕후루 네이버 2023-09 vs 구글 2023-10, 두쫀쿠는 2026-01로 동일). 다음 유행까지 간격의 단축(구글 9.4→5.1개월, 네이버 9.1→5.0개월). 수명이 최근 2년 급격히 짧아졌다는 방향.
- 어긋난 것: 검색량 진폭. 구글에서는 두쫀쿠가 대만카스테라의 19배인데 네이버에서는 대만카스테라(124)가 두쫀쿠(65)보다 크다. 지난 10년간 구글 점유율 상승·네이버 하락의 영향으로 보인다(원자료 해석).
- 대응: 어긋난 지표는 근거에서 빼거나 "구글 기준"으로 한정해 보조로만 썼다. 두 엔진이 일치하는 지표만 주장의 근거로 삼는 방식.

**문제 5: 관심은 매출이 아니다.** 검색량으로 수명을 재고 카드 매출로 피해를 재면, 둘의 연결은 "정점 시점과 매출 하락 시점이 겹친다"는 것 하나에 기대게 된다. 검색량이 줄어도 매출이 유지되는 품목(소금빵, 마라탕)이 있다는 점을 한계로 명시했다.

**부가 활용: 검색 API로 콘텐츠 양 세기.** 네이버 블로그·카페·뉴스 검색 API로 유행별 누적 게시물 수를 셌다(탕후루 3년 57만, 요아정 2년 35만, 두쫀쿠 8개월 63만). 오래된 유행일수록 글이 계속 쌓이는 조건이므로, 시간당으로 환산한 비교는 보수적인 하한이 된다.

### 설명할 수 있어야 하는 것
- 왜 기준 검색어를 모든 요청에 끼워 넣었는가 (요청 단위 정규화 → 기준자 고정 → 요청 간 비교 가능)
- 대안은 무엇이었고 무엇을 포기했는가 (요청을 쪼개 받기, 고정 창 전체 재수집 / 요청 수와 비용)
- 어떤 조건에서 이 방법이 깨지는가 (기준자가 유행을 타거나 계절을 탈 때, 검색량이 작은 항목, 엔진 간 점유율 변화)

### 확인 질문
1. **Q:** (L1 개념) 네이버 데이터랩·구글 트렌드가 돌려주는 값은 검색 횟수가 아니라 무엇인가? 그 성질 때문에 데이터를 이어 붙일 때 무엇이 문제가 되는가?
   **A:** 두 엔진 모두 "그 요청 안에서의 최댓값 = 100"인 상대값을 준다. 구글 트렌드는 각 시점의 검색량을 해당 지역·기간의 전체 검색량으로 나눈 뒤 그 비율의 최고점을 100으로 재스케일한다. 따라서 기간이나 비교어를 바꾸면 같은 키워드라도 값이 달라진다. 요청을 나눠 받으면 서로 다른 자로 잰 값이라 하나의 시계열로 합칠 수 없다. 이 프로젝트에서는 26개 유행 음식을 여러 요청으로 나눠 받아야 했기 때문에 이 성질이 바로 걸림돌이 됐다.
   **꼬리:** 그러면 "지난주보다 30% 늘었다"는 문장은 언제 참이고 언제 거짓인가?
   **틀리기 쉬운 답:** "100은 검색량 최대치니까 100 대비 비율로 절대량을 복원할 수 있다" — 분모가 전체 검색량이고 요청마다 재정규화되므로 복원되지 않는다.

2. **Q:** (L2 판단) 이 프로젝트에서 기준 검색어로 `마라탕`을 쓴 이유는 무엇이고, 기준자 방식 대신 쓸 수 있었던 방법은?
   **A:** 모든 요청에 같은 기준어를 넣으면 기준어의 최고치가 공통 눈금이 되어, 요청이 달라도 같은 자로 잰 값으로 재스케일할 수 있다. 기준어는 관측 기간 내내 꾸준히 검색되고 유행 곡선을 타지 않는 단어여야 해서 `마라탕`을 골랐다. 대안은 매일 고정 창(90일)을 통째로 다시 받아 덮어쓰는 방식으로, 후속 구현([[search-index-stage-rule]])에서 실제로 썼다. 대신 요청 수와 재수집 비용이 늘고, 창 밖 과거와는 여전히 이어지지 않는다.
   **꼬리:** 기준자로 고른 `마라탕`이 사실은 관측 기간 안에서 정착·성장한 품목이었다면 재스케일 결과는 어떻게 왜곡되는가?
   **틀리기 쉬운 답:** "검색량이 가장 큰 단어를 기준자로 쓰면 된다" — 크기가 아니라 안정성이 기준이다. 큰 단어라도 유행을 타면 눈금 자체가 움직인다.

3. **Q:** (L2 판단) 네이버와 구글 결과가 어긋났을 때 어떻게 처리했는가?
   **A:** 두 엔진을 모두 돌려 대조하고, 일치하는 지표만 주장의 근거로 삼았다. 정점 시점(탕후루 네이버 2023-09 / 구글 2023-10, 두쫀쿠 2026-01 동일)과 교체 간격 단축 방향(구글 9.4→5.1개월, 네이버 9.1→5.0개월)은 일치해 근거로 썼다. 반면 검색량 진폭은 어긋났다 — 구글에서는 두쫀쿠가 대만카스테라의 19배인데 네이버에서는 대만카스테라(124)가 두쫀쿠(65)보다 크다. 지난 10년간 구글 점유율 상승·네이버 하락의 영향으로 보인다는 것이 원자료의 해석이며, 어긋난 지표는 근거에서 빼거나 "구글 기준"으로 한정해 보조로만 썼다.
   **꼬리:** 엔진 점유율이 시간에 따라 변한다면, 10년 시계열에서 "진폭"뿐 아니라 "정점 시점"도 편향될 수 있는가?
   **틀리기 쉬운 답:** "두 값의 평균을 쓰면 된다" — 눈금이 다른 두 상대값의 평균은 의미가 없고, 불일치라는 정보만 지운다.

4. **Q:** (L3 한계) 이 방식으로 만든 관심도 시계열을 "매출 피해"의 근거로 쓸 때 어디가 먼저 깨지는가?
   **A:** 검색량으로 수명을 재고 카드 매출로 피해를 재면, 둘의 연결은 "정점 시점과 매출 하락 시점이 겹친다"는 관측 하나에 기대게 된다. 실제로 검색량이 줄어도 매출이 유지되는 품목(소금빵, 마라탕)이 있어 이 점을 한계로 명시했다. 또 검색량이 작은 항목(뚱카롱·십원빵·온정돈까스)은 지표가 요동쳐 통계에서 제외했고, 네이버 주간 값은 잡음이 심해 4주 이동평균으로 평활한 뒤에야 정점과 수명을 계산할 수 있었다.
   **꼬리:** 4주 이동평균을 걸면 정점 시점 추정에 어떤 체계적 오차가 생기는가?
   **틀리기 쉬운 답:** "검색량이 0에 가까우면 관심이 없는 것" — 0은 "데이터가 부족함"일 수도 있어 관심 없음과 구분되지 않는다.

5. **Q:** (L3 한계) 이 수집 파이프라인을 매일 도는 서비스로 올린다면 운영상 먼저 터지는 곳은?
   **A:** 인증과 할당량이다. 2026-09-14 확인 기준 네이버 개발자센터의 검색·데이터랩 API 신규 신청이 중단돼, 신규는 네이버 클라우드 플랫폼 NAVER API HUB에서 Application을 만들고 "Search Trend"·"검색"을 구독해야 하며 구독 없이 호출하면 `401 errorCode 210 Permission Denied`가 돌아온다. 구 방식(`X-Naver-Client-Id/Secret`, `openapi.naver.com`)은 기존 신청자만 2027-06-30까지 쓴다. Search Trend는 무료 월 5만 건·50 RPS이고 향후 유료화 공지가 예정돼 있으며, 블로그 검색은 무료 일 25,000건이다. 구글은 공식 API가 없어 비공식 `pytrends` 4.9.2로 받았는데 연속 요청 시 429가 나 요청 간 25~30초 간격이 필요했고, `retries`를 주면 urllib3 2.x에서 `method_whitelist` 오류가 나 기본값을 썼다.
   **꼬리:** 월 5만 건 한도 안에서 키워드 수를 늘리려면 무엇을 먼저 줄이겠는가 — 갱신 주기인가, 재수집 창 길이인가?
   **틀리기 쉬운 답:** "429가 나면 즉시 재시도하면 된다" — 간격 없이 재시도하면 차단이 길어진다. 이 프로젝트에서는 25~30초 간격이 필요했다.
