# 빅카인즈 API로 뉴스 신호 뽑기

## 1. 한 줄 정의

한국언론진흥재단 빅카인즈가 제공하는 뉴스 분석 API(키워드 트렌드·연관어 분석·뉴스 검색)로 기사량 시계열, 연관어 비중 추이, 기관 개체명 첫 등장일을 만들어 지표로 쓰는 방법. 기사 원문 크롤링 없이 적법하게 수집한다.

## 2. 어디서 썼는가

- [[news-bigdata-2026-kkeutmul-radar]] — 끝물레이더. 디저트 유행의 단계 판정 신호와 근거 기사 카드를 전부 이 API로 만든다. 신호를 어떻게 해석하는지는 [[supply-side-fad-signal]].

## 3. 활용 계획과 주의점 (기획 단계)

원자료는 대회 전 기획서라 실제 호출 경험은 없다. 계획된 사용법은 API별로 넷이다.

| API | 활용 기능 | 활용 방법 |
| --- | --- | --- |
| 키워드 트렌드 | 확산·쇠퇴 판정, 곡선 겹쳐보기 | 일별 기사 건수 → 7일 이동평균, 4주 증가율, 정점 대비 감소율 산출 |
| 연관어 분석 | 쇠퇴 신호 | 주 단위 연관어 중 흥행어(오픈런·품절·웨이팅)와 쇠퇴어(가격 인하·재고·떨이·폐업)의 비중 추이 → 역전 시점 탐지 |
| 뉴스 검색 (기관 개체명) | 포화 신호 | 기사별 기관 개체명을 유통사·프랜차이즈 사전과 매칭 → 최초 등장일 탐지 |
| 뉴스 검색 | 근거 기사 카드 | 신호 발생일 전후 기사의 제목·언론사·날짜·본문 앞 200자 제공 |

**받아 쓸 수 있는 것**: 일별 기사량, 연관어와 가중치, 기관 개체명, 기사 메타정보와 **본문 앞 200자**. 본문 전체가 아니라 앞 200자만 다룬다는 점이 근거 카드 설계(제목·언론사·날짜·앞 200자)를 규정했다.

**주의 1: 필드 이름과 제공 여부를 미리 확정하지 마라.** 기획서는 "API 명칭·반환 필드는 제공되는 빅카인즈 API 사용자 지침서에 맞춰 적용"이라고 단서를 달았다. 특히 기관 개체명 필드가 제공되지 않을 경우를 대비해 **대체안**을 준비했다: 기사 제목과 본문 앞 200자에서 유통사 사전을 문자열 매칭. 외부 API에 의존하는 핵심 신호는 이렇게 대체 경로를 함께 설계해 두는 편이 안전하다.

**주의 2: 크롤링하지 않는다.** 뉴스 본문 수집은 저작권·이용약관 문제가 있어, 정형화된 분석 결과만 API로 받는 것을 명시적 원칙으로 세웠다.

**주의 3: 키워드 정규화가 선행 작업이다.** 두쫀쿠 = 두바이 쫀득 쿠키처럼 줄임말·동의어가 갈리면 기사량 시계열이 쪼개진다. 동의어 통합과 광고성·동명이의어 기사 필터를 LLM에 맡기고, 단계 판정 자체는 규칙 엔진이 한다([[rule-engine-llm-split]]).

**운영**: 일 1회 배치로 판정을 갱신하고 PostgreSQL에 적재하는 구성(Python + pandas, FastAPI).

### 설명할 수 있어야 하는 것
- 왜 크롤링 대신 API만 쓰기로 했는가 (저작권·이용약관 → 정형 분석 결과만 수신)
- 대안은 무엇이었고 무엇을 포기했는가 (본문 전체 확보를 포기하고 앞 200자로 근거 카드를 설계)
- 어떤 조건에서 이 설계가 깨지는가 (필드 미제공, 키워드 표기 분화, 기사량이 적은 키워드)

### 확인 질문
1. **Q:** (L1 개념) 빅카인즈 API로 만들려는 신호 세 가지는 각각 어떤 API 기능에서 나오고 무엇을 계산하는가?
   **A:** 셋이다. 키워드 트렌드로 일별 기사 건수를 받아 7일 이동평균·4주 증가율·정점 대비 감소율을 계산해 확산과 쇠퇴를 본다. 연관어 분석으로 주 단위 연관어 중 흥행어(오픈런·품절·웨이팅)와 쇠퇴어(가격 인하·재고·떨이·폐업)의 비중 추이를 보고 역전 시점을 쇠퇴 신호로 쓴다. 뉴스 검색으로 기사별 기관 개체명을 유통사·프랜차이즈 사전과 매칭해 최초 등장일을 포화 신호로 잡는다. 여기에 뉴스 검색을 한 번 더 써서 신호 발생일 전후 기사의 제목·언론사·날짜·본문 앞 200자로 근거 기사 카드를 만든다.
   **꼬리:** "일별 기사 건수"는 관심의 지표인가 공급의 지표인가? 왜 그렇게 보는가?
   **틀리기 쉬운 답:** "기사량이 늘면 유행이 시작된 것" — 뉴스는 공급이 붙은 뒤에 늘어나는 경우가 많다([[supply-side-fad-signal]]).

2. **Q:** (L2 판단) 기관 개체명 필드가 제공되지 않을 수 있다는 위험에 어떻게 대비했는가?
   **A:** 대체안을 함께 설계했다. 기사 제목과 본문 앞 200자에서 유통사 사전을 문자열 매칭하는 방식이다. 원자료가 기획서라 실제 호출 경험이 없었고, "API 명칭·반환 필드는 제공되는 빅카인즈 API 사용자 지침서에 맞춰 적용"이라는 단서를 달아 필드 이름과 제공 여부를 미리 확정하지 않았다. 외부 API에 의존하는 핵심 신호는 이렇게 대체 경로를 함께 설계해 두는 편이 안전하다는 것이 이 문서의 요지다.
   **꼬리:** 대체안으로 내려갔을 때 신호의 품질은 어떻게 달라지고, 그것을 사용자에게 알릴 것인가?
   **틀리기 쉬운 답:** "문서에 있으니 필드는 당연히 온다" — 대회 제공 예정 문서였고 자료에 실물이 없었다.

3. **Q:** (L2 판단) 본문 전체가 아니라 앞 200자만 다루기로 한 결정이 설계에 어떻게 반영됐는가?
   **A:** 근거 기사 카드의 구성이 제목·언론사·날짜·본문 앞 200자로 고정됐다. 뉴스 본문 수집은 저작권·이용약관 문제가 있어 정형화된 분석 결과만 API로 받는 것을 명시적 원칙으로 세웠고, 그 제약이 화면 단위까지 그대로 내려온 사례다. 동시에 기관 개체명 대체안의 매칭 범위도 제목과 앞 200자로 묶이게 된다.
   **꼬리:** 앞 200자 안에 유통사 이름이 안 나오는 기사는 어떻게 처리하겠는가?
   **틀리기 쉬운 답:** "분석용이니 본문을 긁어도 된다" — 이 프로젝트는 크롤링하지 않는 것을 원칙으로 못 박았다.

4. **Q:** (L3 한계) 키워드 정규화를 선행 작업으로 둔 이유는? 안 하면 어떤 값이 어떻게 틀어지는가?
   **A:** 두쫀쿠 = 두바이 쫀득 쿠키처럼 줄임말·동의어가 갈리면 기사량 시계열이 쪼개져, 같은 유행이 두 개의 낮은 곡선으로 나뉜다. 그러면 7일 이동평균도 4주 증가율도 실제보다 작게 나오고 정점 시점도 흐려진다. 그래서 동의어 통합과 광고성·동명이의어 기사 필터를 LLM에 맡기고, 단계 판정 자체는 규칙 엔진이 하도록 역할을 나눴다([[rule-engine-llm-split]]).
   **꼬리:** 판정을 LLM이 아니라 규칙 엔진에 맡긴 이유를 한 문장으로 말한다면?
   **틀리기 쉬운 답:** "표기 변형은 형태소 분석으로 자동 통합된다" — 신조어 줄임말은 사전에 없어 통합되지 않는다([[ngram-burst-discovery]]).
