## 1. 한 줄 정의

DART 전자공시에서 기업별 최신 공시를 배치로 긁어 LLM에 넣고, 정해진 JSON 스키마의 4지선다 퀴즈를 미리 생성해 DB에 쌓아 두는 방식.

## 2. 어디서 썼는가

- [[hana-ar-kowalk-2026]] — 기업 본사 방문 시 출제할 퀴즈 3문제를 자동 생성 (계획 단계)

## 3. 실제로 겪은 문제와 해결

파이프라인은 다음과 같다.

1. 크론잡으로 DART에서 코스피 100 기업 공시를 일 1회 수집 (사업보고서, 반기보고서, 주요사항보고서)
2. 공시 텍스트를 GPT-4o에 전달
3. 프롬프트: "다음 기업 공시를 바탕으로 4지선다 퀴즈 3문제를 JSON으로 생성해줘"
4. 응답 JSON을 DB(`quizzes.questions` jsonb)에 저장. `source` 컬럼에 DART 공시 번호를 남긴다.
5. 유저가 해당 기업에 도달하면 앱이 저장된 퀴즈를 로드

즉 **생성은 배치, 소비는 조회**로 분리한다. 유저 요청 시점에 LLM을 호출하지 않으므로 응답 지연과 비용 변동이 없다.

JSON 스키마는 문항마다 `question`, `options`(4개), `answer`(정답 인덱스), `explanation`을 강제한다. 해설을 필수 필드로 둔 덕에 오답 시에도 바로 학습 화면을 보여줄 수 있다.

```json
{
  "company_id": "005930",
  "company_name": "삼성전자",
  "generated_at": "2026-04-01",
  "questions": [
    {
      "question": "...",
      "options": ["...", "...", "...", "..."],
      "answer": 2,
      "explanation": "..."
    }
  ]
}
```

품질에 대한 판단: 원자료는 프로토타입 단계에서 "실제 DART 공시를 쓰되 퀴즈 품질은 데모 수준"이라고 명시적으로 범위를 낮춰 잡았다. 품질 검증 절차는 자료에 없음.

비용: DART API 키는 무료 발급, OpenAI API는 유료지만 퀴즈 생성 정도는 비용이 미미하다고 판단.

## 학습

### CS 주제
- 데이터베이스: jsonb 컬럼에 생성 결과 저장, 출처 컬럼으로 원본 추적
- 클라우드: 크론잡 배치 수집, 요청 시점 외부 API 의존 제거
- 소프트웨어공학: 생성과 소비의 분리, 스키마로 출력 형태 강제

### 설명할 수 있어야 하는 것
- 왜 이 방법을 골랐는가: 유저가 기업에 도달하는 순간 LLM을 부르면 응답 지연과 비용이 요청마다 흔들린다. 그래서 생성은 일 1회 배치, 소비는 DB 조회로 갈랐다.
- 대안은 무엇이었고 무엇을 포기했는가: 온디맨드 생성이면 항상 최신 공시를 반영하지만 지연과 비용 변동을 떠안는다. 배치는 최대 하루치 지연을 감수한다.
- 어떤 조건에서 깨지는가: 품질 검증 절차가 없다. 원자료 스스로 퀴즈 품질을 데모 수준으로 범위를 낮춰 잡았다.

### 확인 질문
1. **Q:** (L1 개념) 생성은 배치, 소비는 조회로 나눈다는 것이 무엇이고 어떤 이득이 있나?
   **A:** 크론잡이 DART에서 코스피 100 기업 공시(사업보고서·반기보고서·주요사항보고서)를 일 1회 수집해 GPT-4o에 넣고, 나온 퀴즈 JSON을 DB(`quizzes.questions` jsonb)에 미리 쌓아 둔다. 유저가 해당 기업에 도달하면 앱은 저장된 퀴즈를 로드하기만 한다. 유저 요청 시점에 LLM을 호출하지 않으므로 응답 지연과 비용 변동이 없다. 대신 퀴즈는 최대 하루 전 기준이 된다.
   **꼬리:** 방문이 드문 기업까지 매일 생성하면 낭비인데, 어느 시점에 온디맨드로 바꾸겠나?
   **틀리기 쉬운 답:** "캐시를 붙이면 같은 효과다." 캐시는 첫 요청이 느리고 미스 시 외부 API 실패가 그대로 사용자에게 간다. 배치는 사용자 경로에서 LLM 의존을 아예 뺀다.
2. **Q:** (L2 판단) 퀴즈 JSON 스키마에 `explanation`을 필수 필드로 둔 이유는? `source` 컬럼은 무엇을 위한 것인가?
   **A:** 문항마다 `question`, `options`(4개), `answer`(정답 인덱스), `explanation`을 강제한다. 해설이 필수라서 오답일 때도 바로 학습 화면을 보여 줄 수 있다. `source` 컬럼에는 DART 공시 번호를 남겨, 어떤 공시에서 나온 문항인지 나중에 되짚을 수 있게 했다. 즉 스키마가 UI 요구사항과 추적 가능성을 동시에 강제하는 자리다.
   **꼬리:** `answer`를 인덱스(정수)로 둔 선택은 어떤 버그를 부를 수 있나?
   **틀리기 쉬운 답:** "해설은 나중에 필요하면 그때 생성하면 된다." 배치로 한 번에 만드는 구조에서는 나중에 생성하려면 또 한 번 전체를 돌려야 한다.
3. **Q:** (L3 한계) 이 파이프라인에서 품질을 어떻게 보장하나? 같은 DART 공시를 쓰는 근거 기반 QA와 무엇이 다른가?
   **A:** 보장하지 않는다. 원자료는 프로토타입 단계에서 "실제 DART 공시를 쓰되 퀴즈 품질은 데모 수준"이라고 명시적으로 범위를 낮춰 잡았고 품질 검증 절차는 자료에 없다. 같은 DART 공시를 LLM에 물린 공시 QA 프로젝트는 답변의 숫자를 근거 표와 대조해 지우는 검증 단계를 따로 두는데, 이쪽은 퀴즈 생성이라 검증 요구 수준이 다르게 잡혔다. 다만 오답 문항이 학습 화면으로 그대로 나간다는 점에서 위험이 없지는 않다.
   **꼬리:** 이 서비스가 퀴즈 통과로 토큰을 지급한다면, 검증 없는 문항은 어떤 문제를 만드나?
   **틀리기 쉬운 답:** "GPT-4o가 공시 원문을 봤으니 사실 오류는 없다." 원문을 봤다는 것과 문항·정답·해설이 원문과 일치한다는 것은 별개이고, 이 파이프라인에는 그 일치를 확인하는 단계가 없다.

### 더 파볼 것
- [OPEN DART](https://opendart.fss.or.kr) — 공시 원본을 제공하는 쪽. 인증키 무료 발급과 제공 항목 범위를 직접 확인할 수 있다
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — 프롬프트로 "JSON으로 만들어 줘"라고 부탁하는 대신 스키마를 strict로 강제하는 방법. 이 파이프라인의 스키마 강제를 한 단계 더 단단하게 하는 쪽
