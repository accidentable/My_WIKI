## 한 줄 정의

2025년 이후 한투 OpenAPI의 주문 TR 코드·필수 파라미터·호가단위가 바뀌어서,
예전 코드를 그대로 쓰면 주문이 거부된다.

## 어디서 썼는가

- [[kis-openapi-invest-2026-09]] — `core/kis/` 전체

## 실제로 겪은 문제와 해결

### TR 코드 변경

| 기능 | 구버전 | 현재 |
|---|---|---|
| 매수 | `TTTC0802U` | `TTTC0012U` |
| 매도 | `TTTC0801U` | `TTTC0011U` |
| 정정/취소 | `TTTC0803U` | `TTTC0013U` |
| 미체결 조회 | `TTTC8036R` | `TTTC0084R` |

### 주문 body 필수 필드

NXT 대체거래소 출범으로 `EXCG_ID_DVSN_CD`가 필수로 추가됐다.
`KRX` / `NXT` / `SOR`(최선주문집행) 중 선택하며 기본값은 `KRX`.

### 호가단위

2023-01-25 개편으로 코스피·코스닥이 통일됐다. 지정가가 호가에 안 맞으면 주문이 거부되므로
모든 지정가를 보정 함수(`core/kis/tick.py`)에 통과시킨다.

| 가격 | 호가단위 | | 가격 | 호가단위 |
|---|---|---|---|---|
| ~2,000 | 1 | | 50,000~200,000 | 100 |
| 2,000~5,000 | 5 | | 200,000~500,000 | 500 |
| 5,000~20,000 | 10 | | 500,000~ | 1,000 |
| 20,000~50,000 | 50 | | | |

### 토큰과 유량제한

- 접근토큰은 24시간 유효하고 재발급은 1분에 1회로 제한된다. 람다처럼 인스턴스가 여럿이면
  각자 발급하다 제한에 걸리므로 SSM 등으로 캐시를 공유해야 한다.
- 유량제한은 실전 계좌 기준 조회 초당 20건, 주문 초당 1건.
  위 프로젝트는 `KIS_RATE_LIMIT_PER_SEC` 기본값을 8로 두어 여유를 뒀다.
- 매수 수량은 **미수없는매수수량**을 기준으로 잡는다. 미수(증거금 대출)를 쓰면
  반대매매 위험이 생기고 대회 수익률 계산이 꼬인다.

### 설명할 수 있어야 하는 것
- 토큰 캐시를 배포 형태에 따라 파일과 SSM으로 나눈 이유와 그 대가를 설명할 수 있습니다.
- 유량제한 기본값을 한도보다 낮게 잡은 이유를 말할 수 있습니다.
- 예전 코드를 그대로 가져왔을 때 가장 먼저 깨지는 곳을 순서대로 말할 수 있습니다.

### 확인 질문
1. **Q:** (L1 개념) 이 API의 토큰과 유량제한 규격이 어떻게 되고, 그게 설계에 어떤 영향을 줬는지 설명해 주시겠어요?
   **A:** 접근토큰은 24시간 유효하고 재발급은 1분에 1회로 제한됩니다. 유량제한은 실전 계좌 기준으로 조회가 초당 20건, 주문이 초당 1건입니다. 그래서 토큰을 필요할 때마다 새로 받는 자원으로 보지 않고 아껴 쓰는 자원으로 다뤘고, 호출도 초 단위로 눌러야 했습니다. 이 프로젝트에서는 `KIS_RATE_LIMIT_PER_SEC` 기본값을 8로 둬서 한도보다 낮게 여유를 뒀고, 호출 래퍼(`core/kis/client.py`)에서 유량제한과 재시도, 토큰 만료 자동 복구를 같이 처리했습니다.
   **꼬리:** 그러면 초당 8건으로 눌러도 호출이 몰리는 구간은 어디일까요? KOSPI100 전 종목 스캔을 떠올려 보시면 어떨까요.
   **틀리기 쉬운 답:** "만료되면 그때 다시 받으면 되니 인스턴스가 몇 개든 상관없다"라고 답하는 경우가 있는데, 실제로는 1분 1회 제한에 걸립니다.
2. **Q:** (L2 판단) 람다 구성에서는 토큰을 SSM에 두고 상주 서버에서는 파일로 두셨는데, 두 경우를 어떻게 다르게 보셨나요?
   **A:** 람다는 컨테이너가 매번 새로 떠서 인스턴스마다 토큰이 없고, 람다 여럿이 각자 발급하면 1분 1회 제한에 걸립니다. 그래서 상태는 DynamoDB, 토큰은 SSM에 두고 캐시를 공유하도록 `deploy.py`가 환경변수를 넣게 했습니다. 서버 1대 상주 방식은 한 프로세스가 계속 살아 있어서 `data/kis_token.json` 파일 캐시로 충분하다고 판단했습니다(`TOKEN_CACHE=file`). 대신 람다 쪽은 컴포넌트가 5개로 늘고 장애가 나면 CloudWatch를 뒤져야 하는 비용을 같이 떠안았습니다.
   **꼬리:** 그러면 두 람다가 거의 동시에 토큰 만료를 발견하면 어떻게 되나요? 어떻게 막으시겠어요?
   **틀리기 쉬운 답:** "람다는 컨테이너를 재사용하니 프로세스 메모리 캐시로 충분하다"라고 답하는 경우가 있는데, 실제로는 재사용이 보장되지 않습니다.
3. **Q:** (L2 판단) 모든 지정가를 호가단위 보정 함수에 통과시키셨는데, 그렇게까지 하신 이유가 있나요?
   **A:** 지정가가 호가단위에 맞지 않으면 주문 자체가 거부되기 때문입니다. 호가단위는 2023-01-25 개편으로 코스피와 코스닥이 통일됐고, 2,000원 미만 1원부터 500,000원 이상 1,000원까지 가격대별로 갈립니다. 그래서 모든 지정가를 `core/kis/tick.py`에 통과시켰습니다. 주문 거부는 전략 판단이 맞았는지와 상관없이 그날 진입을 통째로 날리기 때문에, 전략 코드보다는 API 호출 경계에서 막는 편이 안전하다고 판단했습니다.
   **꼬리:** 그러면 정확히 50,000원처럼 구간 경계에 걸리는 가격은 어느 단위로 처리해야 하나요? 매수와 매도에서 올림과 내림 방향을 같게 두어도 될까요?
   **틀리기 쉬운 답:** "코스피와 코스닥은 호가단위가 다르니 시장별로 분기해야 한다"라고 답하는 경우가 있는데, 실제로는 2023-01-25 개편으로 통일됐습니다.
4. **Q:** (L3 한계) 2025년 이전에 쓰던 코드를 그대로 가져오면 어디서부터 깨질까요?
   **A:** 주문 TR 코드가 먼저 걸립니다. 매수 `TTTC0802U` → `TTTC0012U`, 매도 `TTTC0801U` → `TTTC0011U`, 정정/취소 `TTTC0803U` → `TTTC0013U`, 미체결 조회 `TTTC8036R` → `TTTC0084R`로 바뀌었습니다. 그다음이 주문 body인데, NXT 대체거래소가 출범하면서 `EXCG_ID_DVSN_CD`가 필수 필드로 추가됐고 `KRX` / `NXT` / `SOR`(최선주문집행) 중에서 고르며 기본값은 `KRX`입니다. 세 번째가 호가단위입니다. 증상이 조회 계열은 멀쩡히 도는데 주문만 거부되는 형태로 나타나서, 연결 점검이 통과했다고 주문까지 된다고 보면 안 된다고 생각합니다.
   **꼬리:** 그러면 `SOR`을 고르면 체결 거래소가 달라지는데, 대회 수익률 기록에는 무엇을 함께 남겨야 할까요?
   **틀리기 쉬운 답:** "미수 한도까지 쓰면 같은 자본으로 더 살 수 있으니 유리하다"라고 답하는 경우가 있는데, 실제로는 반대매매 위험이 생기고 대회 수익률 계산이 꼬여서, 매수 수량을 미수없는매수수량 기준으로 잡았습니다.
