## 한 줄 정의

2025년 이후 한투 OpenAPI의 주문 TR 코드·필수 파라미터·호가단위가 바뀌어서,
예전 코드를 그대로 쓰면 주문이 거부된다.

## 어디서 썼는가

- [[kis-openapi-invest-2026-09]] — `core/kis/` 전체

## 실제로 겪은 문제와 해결

### TR 코드 변경

| 기능 | 구버전 | 현재 |
|---|---|---|
| 매수 | `TTTC0802U` | `TTTC0012U` |
| 매도 | `TTTC0801U` | `TTTC0011U` |
| 정정/취소 | `TTTC0803U` | `TTTC0013U` |
| 미체결 조회 | `TTTC8036R` | `TTTC0084R` |

### 주문 body 필수 필드

NXT 대체거래소 출범으로 `EXCG_ID_DVSN_CD`가 필수로 추가됐다.
`KRX` / `NXT` / `SOR`(최선주문집행) 중 선택하며 기본값은 `KRX`.

### 호가단위

2023-01-25 개편으로 코스피·코스닥이 통일됐다. 지정가가 호가에 안 맞으면 주문이 거부되므로
모든 지정가를 보정 함수(`core/kis/tick.py`)에 통과시킨다.

| 가격 | 호가단위 | | 가격 | 호가단위 |
|---|---|---|---|---|
| ~2,000 | 1 | | 50,000~200,000 | 100 |
| 2,000~5,000 | 5 | | 200,000~500,000 | 500 |
| 5,000~20,000 | 10 | | 500,000~ | 1,000 |
| 20,000~50,000 | 50 | | | |

### 토큰과 유량제한

- 접근토큰은 24시간 유효하고 재발급은 1분에 1회로 제한된다. 람다처럼 인스턴스가 여럿이면
  각자 발급하다 제한에 걸리므로 SSM 등으로 캐시를 공유해야 한다.
- 유량제한은 실전 계좌 기준 조회 초당 20건, 주문 초당 1건.
  위 프로젝트는 `KIS_RATE_LIMIT_PER_SEC` 기본값을 8로 두어 여유를 뒀다.
- 매수 수량은 **미수없는매수수량**을 기준으로 잡는다. 미수(증거금 대출)를 쓰면
  반대매매 위험이 생기고 대회 수익률 계산이 꼬인다.

### 설명할 수 있어야 하는 것
- 왜 토큰 캐시를 배포 형태에 따라 파일과 SSM으로 나눴는가
- 유량제한 기본값을 왜 한도보다 낮게 잡았는가
- 예전 코드를 그대로 가져왔을 때 가장 먼저 터지는 지점이 어디인가

### 확인 질문
1. **Q:** (L1 개념) 이 API의 토큰·유량제한 규격은 무엇이고 왜 설계에 영향을 주는가?
   **A:** 접근토큰은 24시간 유효하고 재발급은 1분에 1회로 제한된다. 유량제한은 실전 계좌 기준 조회 초당 20건, 주문 초당 1건이다. 즉 토큰은 필요할 때마다 새로 받으면 되는 자원이 아니라 아껴 써야 하는 자원이고, 호출도 초 단위로 눌러야 한다. 위 프로젝트는 `KIS_RATE_LIMIT_PER_SEC` 기본값을 8로 두어 한도보다 낮게 여유를 뒀고, 호출 래퍼(`core/kis/client.py`)에서 유량제한·재시도·토큰 만료 자동 복구를 함께 처리한다.
   **꼬리:** 초당 8건으로 눌러도 호출이 몰리는 구간은 어디인가? KOSPI100 전 종목 스캔을 떠올려 보라.
   **틀리기 쉬운 답:** "만료되면 그때 다시 받으면 되니 인스턴스가 몇 개든 상관없다" — 1분 1회 제한에 걸린다.
2. **Q:** (L2 판단) 람다 구성에서는 왜 토큰을 SSM에 두고, 상주 서버에서는 파일로 두는가?
   **A:** 람다는 컨테이너가 매번 새로 뜨므로 인스턴스마다 토큰이 없고, 람다 여럿이 각자 발급하면 1분 1회 제한에 걸린다. 그래서 상태는 DynamoDB, 토큰은 SSM에 두어 캐시를 공유하도록 `deploy.py`가 환경변수를 넣는다. 반면 서버 1대 상주 방식은 한 프로세스가 계속 살아 있어 `data/kis_token.json` 파일 캐시로 충분하다(`TOKEN_CACHE=file`). 대신 람다 쪽은 컴포넌트가 5개로 늘고 장애 시 CloudWatch를 뒤져야 한다는 비용이 붙는다.
   **꼬리:** 두 람다가 거의 동시에 토큰 만료를 발견하면 무슨 일이 생기고, 어떻게 막겠는가?
   **틀리기 쉬운 답:** "람다는 컨테이너를 재사용하니 프로세스 메모리 캐시로 충분하다" — 재사용은 보장되지 않는다.
3. **Q:** (L2 판단) 모든 지정가를 호가단위 보정 함수에 통과시키는 이유는?
   **A:** 지정가가 호가단위에 맞지 않으면 주문 자체가 거부되기 때문이다. 호가단위는 2023-01-25 개편으로 코스피·코스닥이 통일됐고, 2,000원 미만 1원부터 500,000원 이상 1,000원까지 가격대별로 갈린다. 그래서 모든 지정가를 `core/kis/tick.py`에 통과시킨다. 주문 거부는 전략 판단이 맞았는지와 무관하게 그날 진입을 통째로 날리므로, 전략 코드가 아니라 API 호출 경계에서 막는 편이 안전하다.
   **꼬리:** 정확히 50,000원처럼 구간 경계에 걸리는 가격은 어느 단위로 처리해야 하는가? 매수와 매도에서 올림·내림 방향을 같게 두어도 되는가?
   **틀리기 쉬운 답:** "코스피와 코스닥은 호가단위가 다르니 시장별로 분기해야 한다" — 2023-01-25 개편으로 통일됐다.
4. **Q:** (L3 한계) 2025년 이전에 쓰던 코드를 그대로 가져오면 어디서부터 깨지는가?
   **A:** 주문 TR 코드가 먼저다. 매수 `TTTC0802U` → `TTTC0012U`, 매도 `TTTC0801U` → `TTTC0011U`, 정정/취소 `TTTC0803U` → `TTTC0013U`, 미체결 조회 `TTTC8036R` → `TTTC0084R`로 바뀌었다. 다음이 주문 body다. NXT 대체거래소 출범으로 `EXCG_ID_DVSN_CD`가 필수 필드로 추가됐고 `KRX` / `NXT` / `SOR`(최선주문집행) 중 고르며 기본값은 `KRX`다. 세 번째가 호가단위다. 증상은 조회 계열은 멀쩡히 도는데 주문만 거부되는 형태로 나타나므로, 연결 점검이 통과했다고 주문까지 된다고 판단하면 안 된다.
   **꼬리:** `SOR`을 고르면 체결 거래소가 달라지는데, 대회 수익률 기록에는 무엇을 함께 남겨야 하는가?
   **틀리기 쉬운 답:** "미수 한도까지 쓰면 같은 자본으로 더 살 수 있으니 유리하다" — 반대매매 위험이 생기고 대회 수익률 계산이 꼬여, 매수 수량은 미수없는매수수량 기준으로 잡았다.
