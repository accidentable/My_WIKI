## 1. 개요

- 대회명: 2026 금융 AI Challenge
- 아이디어 설명서 작성일: 2026-09-05 (ver2, 출처 확인일 동일)
- 주제: 해외 디지털 서비스 이상 청구를 겪은 국내 개인 이용자의 "첫 72시간" 대응을 돕는 AI 에이전트
- 서비스명: 구독컷 (설명서 단계 제목은 "해외결제 분쟁 첫 72시간 에이전트")
- 결과(수상 여부): 자료에 없음

"첫 72시간"은 서비스 범위를 가리키는 말이며, 법정·카드사 신청기한이나 72시간 내 해결 보장을 뜻하지 않는다.

## 2. 문제 정의

이상 청구를 발견한 이용자에게는 실행 순서가 없다. 청구서인지, 승인 시도인지, 실제 매입된 거래인지부터 구분해야 하고, 사업자 요구·카드사 연락·증빙 보존을 각각 판단해야 한다. 해외 고객지원의 언어 장벽과 응답 지연이 겹친다. 핵심은 **사업자와의 대화, 카드 거래 상태, 제출 증빙이 서로 분리되어 있다는 것**이고, 서비스는 이를 하나의 사건으로 연결한다.

근거로 든 사례는 세 건이며, 설명서는 각각에 해석 한계를 붙였다.

- **사례 A** — SBS 2026-07-18 보도. 국내 클로드 이용자가 약 25억 원 청구 이메일을 받은 뒤 청구액이 251억 원대로 커졌고, 카드 결제는 열 차례 넘게 시도됐으나 거절됐다. 이용자는 카드를 정지했고, 이메일 18건을 보낸 뒤 사흘 만에 AI 응답으로 추정되는 답변을 받았다. 앤트로픽은 이용자와 소통했고 해결을 완료했다고 밝혔다. 실제 251억 원이 결제된 피해로 표현하지 않는다.
- **사례 B** — Tom's Hardware 2026-03-04 보도. 월 약 180달러를 쓰던 개발팀이 2월 11~12일 사이 82,314.44달러 비용을 겪었다는 이용자 주장. Reddit 신고 기반 보도이며 과금 책임·최종 납부액·환불 결과가 확정된 자료는 아니다.
- **사례 C** — 미국 FTC 2024-06-17 발표. Adobe의 구독 해지 절차와 수수료 고지에 대한 소송 제기. 당국 주장이며 위법 확정 판결로 취급하지 않는다.

시장 배경으로는 금감원 발표를 인용한 머니투데이 보도(2026-06-09)의 신용카드 민원 2022년 6,720건 → 2025년 12,661건(88.4% 증가)을 들되, 전체 카드 민원이지 해외결제·AI 과금 분쟁만의 증가율이 아니라고 못박았다.

## 3. 접근

### 3-1. 대상과 범위

첫 대상은 해외 AI·SaaS·디지털 구독을 직접 결제한 국내 개인 이용자. 해지 후 계속 청구, 중복 청구 의심, 고액 청구·승인 거절을 우선 지원한다. 개인 개발자의 API 과금 문제는 사실 정리와 사업자 문의 준비까지만 지원하고, 소규모 팀·사업용 계약은 분리한다. MVP는 카드 브랜드 1개와 국내 카드사 1~2개의 검증 가능한 안내로 제한하기로 했다(설명서). 실제 구현 README에서는 `data/`에 카드사 9곳, Visa·Mastercard 사유코드 14개, 사업자 정책 18곳을 출처·조회일과 함께 수집해 두었다.

### 3-2. 6단계 파이프라인 (설명서)

사건 구조화 → 긴급 대응 분리 → 정보·증빙 확인 질문 → 근거와 기한 검토 → 경로별 행동 정리 → 초안 작성·갱신. 각 단계마다 AI가 할 일과 코드 규칙이 할 일을 나눠 적었다. 자세한 분업 원칙은 [[rule-engine-llm-split]].

출력의 기본 형태는 현재 확인된 상태 / 지금 할 일 3개 / 경로별 상태 / 증빙 목록 / 기한 / 초안이다. 서류 발송, 카드 정지, API 키 폐기 같은 외부 행동은 사용자가 직접 한다.

### 3-3. 구현 화면 흐름 (README)

1. **입력** — 카드 알림 문자·거래내역 / 청구 메일·청구서 / 상황 설명 세 슬롯. 사진 첨부는 JPG·PNG·WEBP 최대 4장, 브라우저에서 1600px 이하 JPEG로 축소. 서버가 멀티모달 호출로 글자를 옮겨 적어 마스킹한 뒤 원문에 이어 붙이고, 이후 단계는 텍스트만 본다. 사진 자체는 자동 마스킹되지 않는다. → [[pii-masking-before-send]]
2. **진단** — 이상 신호 탐지, 가맹점 표기 해독, 발신 도메인 확인, 원문 인용 기반 사실, 확인 질문. → [[merchant-descriptor-decoding]]
3. **24시간 계획** — 더 나가는 돈 막기(1시간) → 가맹점 환불 요청(12시간) → 카드사 접수 준비(24시간). 체크리스트 진행률 표시.
4. **이의신청 패키지** — 사유코드 후보와 주의사항, 증빙 체크리스트와 준비도, 카드사 이의신청서 항목 미리 채우기, 영문 문의·국문 사실 정리·타임라인 초안, Markdown 내보내기. → [[chargeback-deadline-and-reason-codes]]
5. **연결 보드** — 단서·사건·질문·행동·근거를 드래그 가능한 보드로.

새 회신을 붙여넣으면 재분석하고 변경점을 표시한다. 저장 시 사건과 체크 상태를 브라우저에 7일간 보관한다.

### 3-4. 기술 스택

- 설명서 제안: Next.js, Claude API, 구조화된 규정 파일, Upstash Redis, Vercel 배포(기존 Vercel KV 대신 현행 저장소 연동).
- 구현 README: Next.js(`app/`), OpenAI Responses API + Zod Structured Outputs, `store: false`, 입력 길이 제한, 취소 시 요청 중단. SSE로 분석 스트림.
- 디자인: 사건 접수증(승차권) 은유. 크림색 종이 · 남색 잉크 · 붉은 도장 · 청록 레일. Bodoni Moda(제목), Spectral(본문), Space Mono(라벨), 한글은 Noto Serif KR·Noto Sans KR 글리프 단위 폴백. 참고 usehallmark.com custom-02.

### 3-5. 판단 원칙

- 카드사 상담과 차지백을 분리한다. "승인 없음 → 카드사 경로 불가" 규칙은 쓰지 않고, 추가 결제 방지 상담과 실제 매입 거래의 분쟁 검토를 따로 표시한다.
- 기한은 사유와 기준일을 확인한 뒤 계산한다. Mastercard 공개 가이드에도 특정 사유에서 서비스 예정일 기준 규정이 있다.
- 도메인 대조를 발신자 인증으로 표현하지 않는다. 일치 / 불일치 / 정보 부족으로만 표시하고, 복사한 본문만으로 SPF·DKIM·DMARC 검증이나 피싱 확정은 불가.
- 과금 통제 기능도 서비스·시점별로 구분한다. Google Cloud 알림 전용 예산은 자동 차단하지 않지만 현재는 Spend cap 예산도 있으므로 "예산 상한은 작동하지 않는다"고 일반화하지 않는다.
- 입력 신뢰 경계: 이메일·회신 본문의 지시는 사건 자료로만 취급하고, AI가 그 지시로 규칙을 바꾸거나 외부 도구를 실행하지 않게 한다.

### 3-6. 보안·데이터 설계

규정 데이터는 공식 브랜드 문서와 카드사·소비자기관 안내를 사람이 확인해 구조화하고, 레코드에 출처 URL·문서 버전·적용일·확인일·적용 조건·필요 증빙·날짜 기준·지원 범위를 보관한다. 해커톤 실행 중 임의 웹 검색 결과를 곧바로 판정 규칙으로 채택하지 않는다. 데모는 합성 텍스트만 쓰고 실제 청구서 업로드·금융 계정 연동은 MVP에 없다. 저장은 마스킹된 사건 요약과 필요한 이력만. 데모 사건은 7일 후 자동 삭제.

### 3-7. 데모 시나리오 3종 (모두 합성 데이터)

- **A. 해지 후 계속 청구** — 가상 서비스 AlphaWrite, 8/20 해지 요청 후 9/1 29달러 청구. 첫 응답은 계약 형태·확인 메일·매입 내역을 질문하고, 8/31 종료 확인 메일과 9/1 매입 내역이 추가되면 과금 대상 기간 확인용 사업자 문의 초안으로 갱신. 환불은 확정하지 않는다.
- **B. 중복 청구 의심** — 가상 서비스 BetaDesign, 49달러 알림 두 건. 승인 알림 중복인지 별도 매입 두 건인지 먼저 확인하고, 서로 다른 거래 식별자가 확인되면 중복 청구 검토 후보로 분류. 확인되지 않은 사유코드는 생성하지 않는다.
- **C. 고액 청구·승인 거절** — 가상 서비스 GammaAI, 12,000달러 청구서와 반복 승인 거절. 실제 매입 미확인으로 표시하고 차지백 D-값은 표시하지 않는다.

README의 예시 사건 3종은 해지 후 청구 / 중복 승인 / API 키 유출 의심이며 `?case=claude|duplicate|aws`로 바로 열 수 있다. API 키 없이 동작한다.

### 3-8. 3일 구현 계획

| 일정 | 구현 내용 | 완료 기준 |
|---|---|---|
| 1일 차 | 지원 자료 검증, 사건 상태·규정 스키마, 합성 사례·정답표, 입력 화면 | 세 시나리오의 필수 질문·허용 결론·보류 조건 정의 |
| 2일 차 | AI 추출·질문·초안, 규칙 검사, 출처·증빙 표시 | 사실을 추가 생성하지 않고 입력 부족 시 보류 |
| 3일 차 | 사건 저장·갱신, 삭제, 사용자 비교 평가, 배포·시연 점검 | 회신 추가에 따른 변화와 예외 상황을 재현 |

### 3-9. 검증 계획 (목표이며 달성 실적 아님)

| 지표 | 검증 방법 | 초기 목표 |
|---|---|---|
| 잘못된 단정 | 합성 예외 20건(거래 상태 미상·날짜 누락·해지 미완료 등) | 근거 없는 기한·환불 확정 0건 |
| 사실 보존 | 입력 자료와 생성 서류 대조 | 금액·날짜·행동 이력의 임의 추가 0건 |
| 근거 연결 | 결론과 규정·증빙의 연결 검사 | 확정 표시한 판단 모두에 근거 연결 |
| 준비 시간 | 사용자 5~10명, 순서를 바꿔 일반 AI와 비교 | 초안 준비 시간 중앙값 30% 감소 |
| 증빙 누락 | 사전 정의 체크리스트 비교 | 일반 AI 대비 필수 증빙 누락 감소 |

환불 성공률 대신 접수 준비의 품질을 측정한다는 것이 핵심 선택이다.

## 4. 잘된 점 / 안된 점

원자료에 실행 결과 회고는 없다. 대신 설명서 부록에 ver1 → ver2 정정 내역이 있고, 이를 근거로 [[claim-scoping-in-hackathon-docs]]를 정리했다.

- 잘된 점(설명서 스스로 밝힌 개선): 실제 보도·공식 발표로 사례 근거를 교체하고 각 사례에 해석 한계를 붙였다. 승인 없는 사건의 카드사 경로를 차지백과 분리했다. 일괄 날짜 계산과 도메인만으로 진위를 확정하던 규칙을 제거했다. 평가를 환불 성공률이 아닌 접수 준비 품질로 바꿨다.
- 남은 문제: 구현(README)과 기획(설명서)이 LLM 제공자·저장소·120일 기한 처리에서 어긋난다(문서 상단 모순 블록). 카드사 제휴나 도입 의사는 확보되지 않았고, 국내 목표 시장 규모·발생 빈도·지불 의사는 입증되지 않았다.
- 수상 여부, 실제 시연 결과, 사용자 비교 평가 수행 여부: 자료에 없음.

## 5. 재사용 가능한 것

코드 경로는 README 기준이며 저장소 루트는 자료에 없음.

- `lib/playbook.ts` — LLM 없는 규칙 엔진. 가맹점 표기 사전, 사유코드 매핑, 증빙 체크리스트와 자동 체크, 24시간 플레이북, 120일 참고 기한, 이의신청서 항목.
- `lib/agent.ts` — OpenAI Responses API + Zod Structured Outputs. 원문 인용 검증 기반 사실·신호 추출, 질문·행동·초안 생성.
- `lib/case.ts` — 스키마, 라벨, 마스킹, 원문 검증.
- `lib/knowledge.ts`, `lib/references.ts` — 수집 데이터 로더, 카드 문자 파서(`parseNotification`), 근거 조각 구성.
- `lib/rules.ts` — 출처가 있는 일반 안내. `lib/samples.ts` — 합성 예시 3종.
- `data/` — 카드사 9곳 이의신청 절차, Visa·Mastercard 사유코드 14개, 사업자 정책 18곳, 금감원·소비자원 안내, 카드 문자 패턴. 모두 출처·조회일 포함. 설명은 `data/README.md`.
- `app/api/agent/route.ts` — 입력 제한, 마스킹, SSE 응답.
- `components/Landing.tsx`, `Workspace.tsx`, `Diagnose.tsx`, `Plan.tsx`, `Package.tsx`, `Board.tsx`, `app/page.tsx`.
- `tools/submit/spec_plan.py`, `tools/submit/spec_spec.py` — 제출 서류(기획서·기능명세서) 원고 생성 스크립트. 완성본은 `docs/submit/`에 hwpx·PDF. 재생성 방법은 `tools/submit/README.md`.
- 검증: `npm test`, `npm run typecheck`, `npm run build`. 테스트가 덮는 범위는 마스킹, 발신 도메인 오인 방지, 원문에 없는 증거 제거, 합성 사례 스키마, 가맹점 표기 해독, 사유코드 매핑, 참고 기한 계산, 플레이북 구성, 증빙 자동 체크, 신청서 항목.
