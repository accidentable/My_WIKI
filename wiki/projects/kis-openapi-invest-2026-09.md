KOSPI100 종목 중 5일 이동평균선 아래에 눌려 있던 종목이 09:05에 5일선을 위로
넘으면 전액 매수하고, 익절·5일선 이탈·보유기간 만료 중 먼저 닿는 조건에서 청산한다.
매매 판단은 전부 코드가 하며 LLM은 쓰지 않는다.

## 문제 정의

장중에는 당일 종가가 없어서 5일선이 확정되지 않는다. 그래서 "지금 5일선을 넘었는가"를
실시간으로 판정할 방법이 필요했다. 또한 대회 계좌로 실주문을 내야 하므로,
2025년 이후 바뀐 한투 API 규격과 호가단위를 정확히 맞추지 못하면 주문이 거부된다.

## 접근

### 진입 조건 (매일 09:05, 전부 만족하는 종목 중 1종목)

1. 직전 5거래일 중 3일 이상 종가가 그날의 5일선 아래
2. 전일 종가 < 전일 5일선
3. 현재가 > 직전 4거래일 종가 평균 (= 5일선 돌파와 동치, [[ma5-intraday-breakout]])
4. 전일 종가 대비 상승률 ≤ 5% (급등 추격 배제)
5. 전일 종가 > 60일선 (하락추세 반등 실패 배제)
6. 20일 평균 거래대금 ≥ 30억 (전액 주문 소화 유동성)

### 종목 선정

후보가 여럿이면 depth(전일 이격도, 1.0) / thrust(돌파 강도, 0.5) / trend(60일 이격도, 0.5) /
value(20일 평균 거래대금, 0.3)를 후보 집단 내 백분위로 환산해 가중합하고 1위 하나만 잡는다.
절대값이 아니라 상대순위라 지표 간 단위 차이에 영향받지 않는다.

### 청산 (먼저 닿는 것)

| 조건 | 판정 시점 |
|---|---|
| +10% 익절 | 장중 10분 간격 감시 |
| 5일선 이탈 | 장중 감시 |
| 3거래일 경과 | 마감 정리(15:15)에만 |

손절선은 없다. 5일선 이탈이 유일한 방어선이고 갭하락은 그대로 맞는다
(`USE_STOP_LOSS=true`, `STOP_LOSS_PCT=3` 으로 추가 가능).
5일선 기준가는 매일 아침 갱신한다 — 진입 당시 값을 고정하면 청산 판정이 틀어진다.
보유일차는 진입일이 1일차.

### 포지션

1종목 × 100%. 분산이 없어 한 종목의 악재가 곧 계좌 전체다(`MAX_POSITIONS`/`POSITION_PCT`로 조정).
매수 수량은 한투의 **미수없는매수수량** 기준 — 미수를 쓰면 반대매매 위험과 대회 수익률 왜곡이 생긴다.

### 기술 스택 / 아키텍처

- 런타임 의존성은 `requests` 하나. 유니버스를 한투 종목마스터 `kospi_code.mst`
  고정폭 파싱으로 뽑아 pandas·FinanceDataReader·스크래핑이 전부 불필요하다
  ([[kis-master-file-universe]]).
- 운영 A(권장): 서버 1대 상주. `python cli.py serve` 하나로 APScheduler(09:05 진입 /
  10분 감시 / 15:15 마감, KST)와 텔레그램 롱폴링 스레드가 같은 프로세스에서 돈다.
  상태 `data/state.json`, 토큰 `data/kis_token.json`. `infra/ncp/setup.sh`가
  KST 설정·venv·의존성·`cli.py check`·systemd(`Restart=always`) 등록까지 처리
  ([[telegram-longpolling-ops]]).
- 운영 B(대안): AWS 람다 4개 + DynamoDB + SSM + EventBridge + API Gateway 웹훅
  (`python infra/deploy.py all`). 서버 장애 걱정은 없으나 컴포넌트가 5개로 늘고
  장애 시 CloudWatch를 뒤져야 한다. 구 스택 정리는 `infra/aws_cleanup.py`(기본 조회만, `--yes`로 삭제).
- 한투 API 규격 변경·호가단위·토큰 제한은 [[kis-openapi-2025-spec]] 참고.

## 잘된 점 / 안된 점

### 잘된 점
- 5일선 돌파 조건을 대수 변형해 장중 즉시 판정 가능하게 만든 것 (종가 없이도 판정)
- 마스터파일 파싱으로 외부 라이브러리를 걷어내 람다 패키지를 몇 MB로 유지
- 롱폴링 선택으로 공개 엔드포인트·인바운드 포트 없이 운영, 웹훅 409 충돌 구조적 제거
- `DRY_RUN` 기본 true, `cli.py check` / `tests/test_pipeline.py`(API 키 없이 실행)로 안전장치 확보

### 안된 점 / 한계 (원자료가 스스로 밝힌 부분)
- 09:05 판정은 5분치 데이터만 본다. 오전에 넘었다가 종가에 깨지는 whipsaw가 구조적으로 존재한다.
  판정을 늦추면 줄지만 당일 상승분을 놓치므로 즉시성을 택했다.
- 백테스트를 돌리지 않았다. `+10%`, `3거래일`, `5일 중 3일`은 합의된 규칙이지 검증된 최적값이 아니다.
- 코스피100 대형주가 3거래일 안에 +10% 가는 일은 드물어, 실제 청산은 대부분
  5일선 이탈이나 기간 만료로 끝날 가능성이 높다.
- 손절선 부재 + 1종목 100% 집중이라 갭하락 리스크가 그대로 노출된다.

### 고민한 점

- **언제 판정할 것인가 — 즉시성 대 whipsaw** — 09:05 판정은 5분치 데이터만 본다. 오전에 5일선을 넘었다가 종가에 다시 깨지는 whipsaw가 구조적으로 존재한다. 판정을 장 후반으로 미루면 줄지만 당일 상승분을 놓친다. 원자료는 "지금은 즉시성을 택한 설정"이라고 적었다.
- **손절선을 넣을 것인가** — 넣지 않았다. 5일선 이탈이 유일한 방어선이고 갭하락은 그대로 맞는다. 다만 포기한 것이 아니라 `.env`에 `USE_STOP_LOSS=true`, `STOP_LOSS_PCT=3`으로 열어 뒀다. 1종목 × 100% 집중과 겹치면 한 종목의 악재가 곧 계좌 전체가 된다는 것을 원자료가 명시했다.
- **미수를 쓸 것인가** — 매수 수량을 한투의 **미수없는매수수량** 기준으로 잡았다. 미수(증거금 대출)를 쓰면 반대매매 위험이 생기고 대회 수익률 계산이 꼬이기 때문이다.
- **운영을 서버로 할 것인가 람다로 할 것인가** — 둘 다 구현하고 서버 상주를 권장으로 뒀다. 람다는 서버가 죽을 걱정이 없는 대신 컴포넌트가 DynamoDB·SSM·EventBridge·API Gateway까지 5개로 늘고 장애 시 CloudWatch를 뒤져야 한다. 구 스택 정리용 `infra/aws_cleanup.py`는 기본이 조회만이고 `--yes`를 붙여야 삭제한다.
- **후보가 여럿일 때 무엇으로 고를 것인가** — depth(전일 이격도 1.0) / thrust(돌파 강도 0.5) / trend(60일 이격도 0.5) / value(20일 평균 거래대금 0.3)를 후보 집단 내 백분위로 환산해 가중합하고 1위 하나만 잡는다. 절대값이 아니라 상대순위라 지표 간 단위 차이에 영향받지 않는다. 다만 가중치 값 자체의 근거는 자료에 없다.

### 예상 질문

1. **Q:** (L1) 이 전략이 "역발상"인 이유는 무엇이고, 진입 조건 6개가 각각 무엇을 걸러내는가?
   **A:** 5일선 위로 달리는 종목을 따라가는 것이 아니라 5일선 **아래에 눌려 있던** 종목이 올라오는 순간을 잡기 때문에 역발상입니다. 조건 1·2(직전 5거래일 중 3일 이상 종가가 5일선 아래, 전일 종가 < 전일 5일선)가 "눌려 있던 상태"를 확인하고, 조건 3(현재가 > 직전 4거래일 종가 평균)이 지금 넘었다는 신호입니다. 나머지 셋은 배제 조건입니다 — 조건 4(전일 대비 상승률 ≤ 5%)는 이미 급등한 것의 추격을, 조건 5(전일 종가 > 60일선)는 하락추세에서의 반등 실패를, 조건 6(20일 평균 거래대금 ≥ 30억)은 전액 주문을 소화 못 하는 종목을 거릅니다.
   **꼬리:** 조건 4의 5%와 조건 6의 30억은 어디서 나온 숫자인가?
   **틀리기 쉬운 답:** "5일선 돌파 추세추종 전략"이라고 소개하는 것. 진입 지점은 같아 보여도 조건 1·2·4가 정반대 방향이다.
2. **Q:** (L2) 백테스트를 하지 않은 프로젝트를 왜 만들었고, 그 숫자들(+10%, 3거래일, 5일 중 3일)은 무엇인가?
   **A:** 검증된 최적값이 아니라 합의된 규칙입니다. 원자료가 그렇게 명시했고, 전부 `config.py`와 `.env`로 조정 가능하게 열어 뒀습니다. 이 프로젝트에서 제가 만든 것은 수익을 내는 전략이 아니라 **전략을 실계좌에서 안전하게 돌리는 실행 인프라**입니다 — 장중 즉시 판정을 가능하게 한 대수 변형, 2025 개편 규격과 호가단위를 통과하는 주문 경로, 토큰 유량제한을 넘지 않는 캐시, `DRY_RUN` 기본값과 API 키 없이 도는 통합 점검. 전략 파라미터의 근거를 물으면 없다고 답하는 것이 정확합니다.
   **꼬리:** 백테스트를 붙인다면 무엇부터 정의해야 하나? 이 전략에서 가장 결과를 흔들 가정은?
   **틀리기 쉬운 답:** "실전 계좌로 돌렸으니 백테스트보다 낫다". 표본이 대회 기간 며칠이면 아무것도 검증하지 못한다.
3. **Q:** (L2) 1종목 × 100%, 손절선 없음이라는 설정을 왜 그대로 뒀는가?
   **A:** 대회 수익률을 겨루는 맥락에서 나온 설정이고, 원자료는 그 대가를 숨기지 않았습니다 — 분산이 없으므로 한 종목의 악재가 곧 계좌 전체이고, 5일선 이탈이 유일한 방어선이라 갭하락은 그대로 맞습니다. 다만 고정이 아니라 `MAX_POSITIONS` / `POSITION_PCT` / `USE_STOP_LOSS` / `STOP_LOSS_PCT`로 전부 열려 있습니다. 즉 "이 값이 옳다"가 아니라 "이 값으로 돌리되 바꿀 수 있게 해 뒀다"가 정확한 설명입니다.
   **꼬리:** 5일선 이탈은 장중 10분 간격 감시로 잡는데, 그 사이에 벌어지는 하락은 어떻게 되는가?
   **틀리기 쉬운 답:** "손절 대신 5일선 이탈이 있으니 리스크 관리가 된다". 갭하락은 두 장치 어느 쪽으로도 막히지 않는다.
4. **Q:** (L3) 이 봇이 실제로 돈을 잃는다면 어느 경로가 가장 유력한가? 코드 버그와 전략 실패를 어떻게 구분하겠는가?
   **A:** 원자료가 밝힌 구조적 경로가 셋입니다. 첫째 whipsaw — 09:05에 넘었다가 종가에 깨지는 경우가 5분치 판정에서는 구조적으로 존재합니다. 둘째 갭하락 — 손절선이 없고 1종목 100%라 그대로 맞습니다. 셋째 청산 편향 — 코스피100 대형주가 3거래일 안에 +10% 가는 일은 드물어서 실제 청산은 대부분 5일선 이탈이나 기간 만료로 끝날 가능성이 높습니다. 즉 익절 조건이 사실상 잘 안 걸리는 설계입니다. 버그와 전략 실패를 가르려면 매 거래의 판정 근거(당시 4일 평균, 현재가, 점수 구성)와 주문 결과가 남아야 하고, 지금은 `data/state.json` 이력과 텔레그램 `/history`가 그 자리를 맡습니다.
   **꼬리:** 세 경로 중 하나를 코드로 줄인다면 무엇을 고르고 무엇을 대가로 내겠는가?
   **틀리기 쉬운 답:** "5일선 이탈이 바로 손절 역할을 한다". 이탈 판정은 10분 간격이고 갭에는 반응하지 못한다.
5. **Q:** (L3) 서버 1대 상주를 권장으로 뒀는데, 이 봇을 여러 계좌·여러 전략으로 늘리면 어디가 먼저 깨지는가?
   **A:** 먼저 유량제한입니다. 실전 계좌 기준 조회 초당 20건, 주문 초당 1건이고 `KIS_RATE_LIMIT_PER_SEC` 기본값을 8로 여유를 뒀는데, 계좌가 늘면 이 여유가 사라집니다. 다음이 토큰입니다 — 재발급이 1분에 1회로 제한되므로 프로세스가 각자 발급하면 막히고, 그래서 람다 구성에서는 SSM으로 캐시를 공유합니다. 세 번째는 단일 프로세스 구조입니다. 스케줄러와 텔레그램 롱폴링이 같은 프로세스에서 돌아 `Restart=always`로 살아나지만, 재시작 순간의 09:05 진입은 놓칠 수 있습니다. 네 번째는 유동성 — 20일 평균 거래대금 30억 컷은 1계좌 전액 기준이므로 자금이 커지면 같은 종목을 담지 못합니다.
   **꼬리:** 그 시점에 운영 B(람다)로 가는 것이 답인가? 무엇이 더 나빠지나?
   **틀리기 쉬운 답:** "람다로 가면 확장성이 해결된다". 유량제한과 토큰 제한은 실행 환경이 아니라 API 쪽 제약이라 그대로 남는다.

### 솔직하게 말할 것

- **백테스트를 돌리지 않았다.** `+10%`, `3거래일`, `5일 중 3일`, 진입 조건의 5%·60일선·30억, 점수 가중치 1.0/0.5/0.5/0.3은 전부 합의된 규칙이지 검증된 최적값이 아니다. 원자료가 스스로 밝힌 내용이므로 먼저 말하는 편이 낫다.
- 결과(수상 여부)와 실제 매매 성과가 자료에 없다. 대회 기간도 "2026-09 자료 기준 시점"이고 정확한 기간은 자료에 없다.
- 저장소가 없다. 코드가 로컬에만 있어 보여 달라는 요청에 바로 응하기 어렵다.
- 코드에 AI 도구가 쓰인 범위를 원자료가 구분해 적지 않았다. 설명할 수 있는 단위는 설계 결정(대수 변형으로 장중 판정, 마스터파일 파싱, 롱폴링 선택, 토큰 캐시 위치)이지 모든 파일의 구현 세부가 아니다.
- 익절 +10%는 코스피100 대형주에서 3거래일 안에 거의 걸리지 않을 것이라고 원자료가 예상했다. 즉 설계상 존재하지만 실효가 낮은 조건이다. "익절·손절·기간 세 축으로 관리한다"고 말하면 과장이다.
- 손절선이 없고 1종목 100%라 갭하락 리스크가 그대로 노출된다. 리스크 관리가 되어 있다고 말하지 않는다.
- 실제로 확인된 범위는 `cli.py check`(토큰·시세·잔고·휴장일 연결)와 `tests/test_pipeline.py`(API 없이 도는 통합 점검)까지다. 실주문 체결 이력의 규모는 자료에 없다.
