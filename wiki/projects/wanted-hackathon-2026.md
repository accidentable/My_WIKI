## 2. 문제 정의

원자료는 문제 정의를 별도 절로 쓰지 않았다. 읽어낼 수 있는 범위는 다음과 같다.

- 사진 한 장에서 "부술 대상"을 사용자가 지정하거나 수정하지 않고, **확인·수정 UI 없이** 바로 타격까지 가는 흐름을 만드는 것이 목표다.
- 소재(나무/금속/유리)에 따라 반응과 소리가 달라야 하므로, 사진 속 물체의 소재를 자동으로 판정해야 한다.
- 모바일 브라우저에서 돌아가야 하므로 모델 크기, 자동재생 정책, 저사양 기기 프레임이 제약이 된다.

## 3. 접근

### 기술 스택

- 3D: three.js (+ RoomEnvironment), importmap으로 `three`, `@mediapipe/tasks-vision` 로드
- 세그멘테이션: MediaPipe InteractiveSegmenter 온디바이스, 모델 `vendor/models/magic_touch.tflite` (약 16MB, 첫 로딩 수 초)
- 소재 판단: 서버 `POST /api/analyze` → OpenAI 비전 (모델명은 상단 모순 블록 참고), 실패 시 색상 통계 휴리스틱 폴백
- 서버: `serve.js` (정적 서버 + analyze 엔드포인트, 키 없으면 503)
- 오디오: Web Audio 합성 효과음
- 실행: `npm install` → `npm start`, PC `http://localhost:5173/`, 폰은 같은 Wi-Fi의 `phone : http://192.168.x.x:5173/`

### 사진 파이프라인

```
사진(≤1024px) → MediaPipe InteractiveSegmenter(중앙 점 시드) → 마스크
  → 시드 연결 성분만 남김 → 외곽선 추적 → RDP 단순화 → 윤곽 폴리곤 + bbox
  → 소재 판단: /api/analyze → 실패 시 색상 휴리스틱 → wood | metal | glass
  → 배경 구멍 채우기(양파껍질 채움 + 블러) 미리 계산
  → 프록시 메시: 사진 조각을 입힌 컷아웃 격자 평면 (배경 사진 평면 앞, 깊이 보정)
```

자세한 내용은 [[on-device-segmentation]], [[photo-proxy-destruction]] 참고.

### 소재별 반응

| 소재 | 위치 반응 | 파괴 |
|---|---|---|
| 나무 | 눌린 자국·쪼개짐 무늬, 안으로 밀렸다 튕김, 사진에서 뽑은 색의 가시·먼지 | 3타에 보로노이 5~8조각(두께 있음, 사진 텍스처 유지), 배경은 채워진 빈자리 노출 |
| 금속 | 격자 정점을 밀어 넣는 영구 찌그러짐 + 긁힌 자국, 불꽃, 페인트 조각, 섬광 | 부서지지 않음 |
| 유리 | 방사형 금(가산 오버레이), 반짝이는 조각 | 손상 누적/재타격 시 40~70개 얇은 조각으로 산산조각, 타격점에서 퍼지는 파동 |

### 모드

- 사진 모드: 촬영 / 앨범 / 샘플 사진 → 자동 분석 → 바로 타격
- 테스트 벤치: 나무 상자 / 금속 드럼통 / 유리 병 샘플 3D 물체로 소재별 반응·소리 확인
- `?material=glass` URL 파라미터로 개발용 소재 강제

### 비용

`gpt-6-astra` 기준 입력 $10 / 출력 $50 per 1M 토큰, 이미지는 `detail: low`로 보내 사진 한 장당 약 10원 안팎. 아끼려면 `OPENAI_MODEL=gpt-5.6-luna`.

## 4. 잘된 점 / 안된 점

### 잘된 점 (원자료에 성과로 서술된 것)

- 확인·수정 UI 없이 사진 → 분석 → 타격이 이어지는 흐름을 완성. 첫 로딩 이후 사진당 1초 내외.
- 소재별 반응 규칙을 테스트 벤치와 사진 프록시에 **같은 규칙으로** 적용.
- 키가 없거나 호출이 실패해도 색상 휴리스틱으로 자동 폴백되어 데모가 멈추지 않음 (힌트에 "간이 판단"/"OpenAI" 표시).
- 물체 인터페이스를 공통 규약으로 통일: `{ group, hittables(), hit(intersection, strength), update(dt), dispose(), stats(), statusText() }`.
- `npm run build:single`로 three.js만 CDN에서 받는 단일 HTML(`dist/index.html`) 배포 가능.

### 안된 점 / 알려진 제한

- **OpenAI 실제 응답 경로 미검증.** 작업 PC에 키가 없어 키 없을 때의 503 폴백만 확인했다.
- 단일 파일 빌드는 MediaPipe WASM·모델·샘플 사진을 담지 못해 **사진 탭 없이** 테스트 벤치로만 열린다. `dist/artifact.html`도 같은 제약.
- 세그먼트는 사진 중앙 물체를 자동 선택. 중앙에 없으면 직접 탭해야 한다.
- 배경 채우기는 진짜 인페인팅이 아니라 주변색 번짐이라 복잡한 배경에서 뭉개진다.
- 파편끼리 충돌하지 않고 바닥만 인식. 유리 파편 70개는 저사양 폰에서 프레임 저하.
- iOS Safari 진동 미지원. 모바일 자동재생 정책 때문에 첫 터치 이후에야 소리가 켜진다.
- 사내/카페 Wi-Fi는 기기 간 통신을 막을 수 있어 폰 테스트는 핫스팟이 확실하다.
- `samples/`의 `glass-bottle.jpg`, `metal-mokapot.jpg`, `ceramic-mug.jpg`, `wood-chair.jpg`는 출처 확인이 필요하다 (나머지는 Wikimedia Commons, `samples/CREDITS.md`).

## 면접 준비

### 한 문장 소개

사진을 찍으면 브라우저 안에서 온디바이스 AI가 물체 영역을 잘라내고 소재(나무/금속/유리)를 판단해, 확인·수정 UI 없이 그 자리에서 가상 방망이로 부수는 모바일 대응 웹 3D 데모입니다. 네이티브 앱이 아니라 브라우저에서 돌고, 첫 모델 로딩(약 16MB) 이후에는 사진당 1초 내외로 분석에서 타격까지 이어집니다.

### 고민한 점

- **확인·수정 UI를 넣을 것인가** — 넣지 않고 사진 중앙 점을 시드로 자동 선택해 바로 타격까지 가도록 했다. 대가로 물체가 중앙에 없으면 빗나가고, 이를 "물체 밖을 탭하면 그 자리의 다른 물체를 새로 잘라낸다"는 별도 조작으로 메웠다.
- **소재 판정을 API에 맡길 것인가 로컬에서 할 것인가** — API 우선, 실패 시 색상 통계 휴리스틱으로 자동 폴백하는 2단 구성을 택했다. 중요한 것은 폴백으로 내려간 사실을 숨기지 않고 힌트에 "간이 판단"/"OpenAI"로 표시하기로 한 점이다.
- **모델과 비용을 어디에 맞출 것인가** — 기본값은 플래그십으로 두되, 계정 권한이 없으면(404/403) `OPENAI_MODEL_FALLBACKS`의 모델을 순서대로 시도하고 어떤 모델이 답했는지 서버 로그에 남긴다. 이미지는 `detail: low`, 응답은 JSON 스키마 고정, 비용을 아끼려면 경량 모델로 바꾸라고 문서에 적었다.
- **단일 파일로 공유할 것인가, 사진 모드를 살릴 것인가** — 둘 다는 안 됐다. MediaPipe WASM·모델·샘플 사진을 단일 HTML에 담을 수 없어, 공유용 빌드는 테스트 벤치만 열리는 반쪽으로 남겼다.
- **파편 수를 얼마나 늘릴 것인가** — 유리는 40~70개 얇은 조각으로 산산조각 내지만, 저사양 폰에서 잠깐 프레임이 떨어진다고 자료가 인정한다. 다음 단계 목록에도 "파편 수 vs. 프레임"이 튜닝 항목으로 남아 있다.

### 예상 질문

1. **Q:** (L1) 이걸 네이티브 앱이 아니라 브라우저에서 돌리기로 하면서 생기는 제약은 무엇이고, 각각 어떻게 다뤘는가?
   **A:** 세 가지가 자료에 남아 있습니다. 첫째, 모델을 앱에 번들할 수 없어 약 16MB의 `.tflite`를 첫 실행 때 내려받아야 하고 몇 초가 걸립니다. 이후에는 사진당 1초 내외로 돕니다. 둘째, 모바일 자동재생 정책 때문에 소리를 처음부터 켤 수 없어 첫 터치 이후에 켜지도록 했고, iOS Safari는 진동을 지원하지 않아 안드로이드에서만 진동이 옵니다. 셋째, 배포·테스트 환경이 네트워크에 묶여서, 폰으로 보려면 같은 Wi-Fi의 `phone : http://192.168.x.x:5173/`를 열어야 하고 기기 간 통신을 막는 사내·카페 Wi-Fi에서는 핫스팟을 쓰라고 안내했습니다.
   **꼬리:** 16MB 모델을 매번 받게 하지 않으려면 무엇을 바꾸겠는가?
   **틀리기 쉬운 답:** "웹이라 어디서든 바로 된다"고만 말하는 답. 첫 로딩 비용과 자동재생·진동 같은 플랫폼 정책 제약이 실제로 UX를 바꿔 놓았다.
2. **Q:** (L2) 잘라낸 영역을 사용자가 확인·수정하는 UI를 일부러 넣지 않았다. 왜였고, 대신 무엇을 치렀나?
   **A:** 목표가 "사진 → 분석 → 타격"이 끊기지 않고 이어지는 손맛이었기 때문입니다. 자료가 사진 모드를 설명하면서 "확인·수정 UI 없음"을 기능처럼 앞에 적어 둔 것이 그 의도를 보여줍니다. 치른 비용은 정확도입니다. 세그먼트는 사진 중앙 물체를 자동 선택하므로 물체가 중앙에 없으면 엉뚱한 걸 잡고, 그때는 사용자가 물체 밖을 탭해 대상을 새로 잘라내야 합니다. 이 탭은 스윙을 하지 않는 별도 동작으로 분리해, 수정 자체는 가능하게 두되 흐름을 멈추지는 않도록 했습니다.
   **꼬리:** 확인 단계를 넣는다면 어디에 넣어야 흐름을 가장 덜 해치겠는가?
   **틀리기 쉬운 답:** "AI가 정확해서 확인이 필요 없었다"는 답. 자료는 중앙에 없으면 빗나간다는 걸 알려진 제한으로 명시했다. 정확해서가 아니라 흐름을 위해 감수한 선택이다.
3. **Q:** (L2) 테스트 벤치의 3D 물체와 사진에서 잘라낸 프록시는 만들어지는 방식이 전혀 다른데, 소재별 반응 규칙은 같다. 어떻게 그렇게 만들었나?
   **A:** 물체를 공통 인터페이스로 통일했습니다. `{ group, hittables(), hit(intersection, strength), update(dt), dispose(), stats(), statusText() }` 하나만 지키면 입력·HUD·파편 코드가 대상을 구분하지 않습니다. 그래서 나무는 3타에 보로노이 5~8조각, 금속은 영구 찌그러짐에 파괴 없음, 유리는 손상 누적 후 40~70개 조각이라는 규칙을 벤치와 사진 프록시 양쪽에 같은 규칙으로 적용할 수 있었습니다. 자료도 이를 "벤치와 같은 규칙을 사진 프록시에 그대로 적용"이라고 성과로 적고 있습니다.
   **꼬리:** 소재가 하나 더 늘면 어디를 고쳐야 하나?
   **틀리기 쉬운 답:** "사진도 결국 3D 메시니까 자동으로 같다"는 답. 사진 쪽은 컷아웃 격자 평면이고 배경 채우기·깊이 보정이 따로 붙어 있어, 인터페이스를 맞춰 준 덕에 같아진 것이다.
4. **Q:** (L3) 심사위원이 자기 폰으로 이 데모를 연다. 무엇이 먼저 실패하는가?
   **A:** 순서대로 보면, 우선 폰이 로컬 서버에 닿지 못하는 경우입니다. 사내·카페 Wi-Fi가 기기 간 통신을 막으면 주소 자체가 열리지 않아 핫스팟이 확실하다고 자료가 적었습니다. 연결되면 다음은 첫 모델 로딩 몇 초의 침묵입니다. 그다음이 기대와 다른 동작인데, 첫 터치 전에는 소리가 나지 않고 iOS에서는 진동이 없습니다. 마지막이 성능으로, 유리 파편 70개 구간에서 저사양 폰의 프레임이 떨어집니다. 그리고 파일 하나로 공유한 빌드를 열었다면 사진 탭 자체가 없습니다.
   **꼬리:** 이 중 어느 것을 제일 먼저 고치겠는가? 왜?
   **틀리기 쉬운 답:** "렌더링 최적화가 문제"라고 바로 답하는 것. 자료가 적은 실패는 네트워크와 플랫폼 정책 쪽이 먼저고, 프레임 저하는 특정 구간에 국한된다.
5. **Q:** (L3) 비전 API 판정 경로가 실제로 동작한다는 걸 어떻게 확인했나?
   **A:** 확인하지 못했습니다. 작업 PC에 키가 없어서 키가 없을 때의 503 폴백만 확인했고, 실제 응답 경로는 미검증이라고 자료가 명시합니다. 검증 수단은 준비돼 있어서, 서버를 켠 상태에서 `node tools/analyze.js samples/mug.jpg`로 한 장씩 시험할 수 있고, 어떤 모델이 답했는지 서버 로그에 찍히도록 해 뒀습니다. 다음 단계 목록에도 "API 키 연결 후 비전 판단 경로 검증"이 2번 항목으로 남아 있습니다.
   **꼬리:** 키 없이도 그 경로의 회귀를 막으려면 무엇을 두겠는가?
   **틀리기 쉬운 답:** "폴백이 있으니 문제없다"는 답. 폴백이 동작한다는 것은 주 경로가 동작한다는 증거가 아니고, 오히려 주 경로가 조용히 죽어도 화면이 정상으로 보이게 만든다.

### 솔직하게 말할 것

- **대회명이 원자료에 없다.** README 본문 어디에도 대회 이름 표기가 없고, "해커톤용 데모"라는 말만 있다. 위키가 붙인 "원티드 해커톤"은 프로젝트 분류상의 이름이다. [[wanted-interview-ai-2026]]과 같은 회차인지도 이 자료로는 판단할 수 없다. 면접에서 대회명을 말하려면 다른 기록으로 먼저 확인해야 한다.
- **OpenAI 모델명이 원자료 안에서 갈린다.** "소재 판단" 절은 기본 `gpt-6-astra`에 폴백 `gpt-5.6-sol`·`gpt-5.6-terra`, 경량 대안 `gpt-5.6-luna`라고 적는데, "사진 파이프라인" 다이어그램은 `gpt-5-mini`라고 적는다. 출처는 같은 파일이고 어느 쪽이 실제 코드값인지는 자료에 없다(다이어그램이 갱신되지 않은 옛 값일 가능성은 추정일 뿐이다). 모델을 물으면 이 불일치를 그대로 말하는 편이 안전하다.
- **OpenAI 실제 응답 경로는 미검증이다.** 키가 없어 503 폴백만 확인했다. "AI가 소재를 판단한다"고 단정하면 "그럼 정확도는요"라는 꼬리질문에서 근거가 없다. 실제로 확인된 것은 폴백 동작과 CLI 검증 수단이 있다는 것까지다.
- **기간과 수상 여부가 자료에 없다.** "2026-09 기준 최신 플래그십"이라는 표현 때문에 2026년 9월 전후 작업으로 보는 것은 추정이다.
- **샘플 사진 4장의 출처가 확인되지 않았다.** `glass-bottle.jpg`, `metal-mokapot.jpg`, `ceramic-mug.jpg`, `wood-chair.jpg`는 폴더에 있던 파일이라 출처 확인이 필요하다고 자료가 직접 적었다. 나머지는 Wikimedia Commons이고 `samples/CREDITS.md`에 있다.
- **배경 채우기는 인페인팅이 아니다.** 주변색 번짐(양파껍질 채움 + 블러)이라 복잡한 배경에서는 뭉개진다. "AI 인페인팅"이라고 말하면 안 된다.
- **파편 물리도 제한적이다.** 파편끼리 충돌하지 않고 바닥만 인식한다.
- **AI 도구가 어디까지 짰는지 기록이 없다.** 원자료에 AI 생성 범위가 적혀 있지 않다. 보로노이 파괴, RDP 단순화, 휴리스틱 점수식 같은 부분은 코드를 다시 열어 설명할 수 있는지 미리 확인해 두는 편이 낫다.
