## 2. 문제 정의

원자료는 문제 정의를 별도 절로 쓰지 않았다. 읽어낼 수 있는 범위는 다음과 같다.

- 사진 한 장에서 "부술 대상"을 사용자가 지정하거나 수정하지 않고, **확인·수정 UI 없이** 바로 타격까지 가는 흐름을 만드는 것이 목표다.
- 소재(나무/금속/유리)에 따라 반응과 소리가 달라야 하므로, 사진 속 물체의 소재를 자동으로 판정해야 한다.
- 모바일 브라우저에서 돌아가야 하므로 모델 크기, 자동재생 정책, 저사양 기기 프레임이 제약이 된다.

## 3. 접근

### 기술 스택

- 3D: three.js (+ RoomEnvironment), importmap으로 `three`, `@mediapipe/tasks-vision` 로드
- 세그멘테이션: MediaPipe InteractiveSegmenter 온디바이스, 모델 `vendor/models/magic_touch.tflite` (약 16MB, 첫 로딩 수 초)
- 소재 판단: 서버 `POST /api/analyze` → OpenAI 비전 (모델명은 상단 모순 블록 참고), 실패 시 색상 통계 휴리스틱 폴백
- 서버: `serve.js` (정적 서버 + analyze 엔드포인트, 키 없으면 503)
- 오디오: Web Audio 합성 효과음
- 실행: `npm install` → `npm start`, PC `http://localhost:5173/`, 폰은 같은 Wi-Fi의 `phone : http://192.168.x.x:5173/`

### 사진 파이프라인

```
사진(≤1024px) → MediaPipe InteractiveSegmenter(중앙 점 시드) → 마스크
  → 시드 연결 성분만 남김 → 외곽선 추적 → RDP 단순화 → 윤곽 폴리곤 + bbox
  → 소재 판단: /api/analyze → 실패 시 색상 휴리스틱 → wood | metal | glass
  → 배경 구멍 채우기(양파껍질 채움 + 블러) 미리 계산
  → 프록시 메시: 사진 조각을 입힌 컷아웃 격자 평면 (배경 사진 평면 앞, 깊이 보정)
```

자세한 내용은 [[on-device-segmentation]], [[photo-proxy-destruction]] 참고.

### 소재별 반응

| 소재 | 위치 반응 | 파괴 |
|---|---|---|
| 나무 | 눌린 자국·쪼개짐 무늬, 안으로 밀렸다 튕김, 사진에서 뽑은 색의 가시·먼지 | 3타에 보로노이 5~8조각(두께 있음, 사진 텍스처 유지), 배경은 채워진 빈자리 노출 |
| 금속 | 격자 정점을 밀어 넣는 영구 찌그러짐 + 긁힌 자국, 불꽃, 페인트 조각, 섬광 | 부서지지 않음 |
| 유리 | 방사형 금(가산 오버레이), 반짝이는 조각 | 손상 누적/재타격 시 40~70개 얇은 조각으로 산산조각, 타격점에서 퍼지는 파동 |

### 모드

- 사진 모드: 촬영 / 앨범 / 샘플 사진 → 자동 분석 → 바로 타격
- 테스트 벤치: 나무 상자 / 금속 드럼통 / 유리 병 샘플 3D 물체로 소재별 반응·소리 확인
- `?material=glass` URL 파라미터로 개발용 소재 강제

### 비용

`gpt-6-astra` 기준 입력 $10 / 출력 $50 per 1M 토큰, 이미지는 `detail: low`로 보내 사진 한 장당 약 10원 안팎. 아끼려면 `OPENAI_MODEL=gpt-5.6-luna`.

## 4. 잘된 점 / 안된 점

### 잘된 점 (원자료에 성과로 서술된 것)

- 확인·수정 UI 없이 사진 → 분석 → 타격이 이어지는 흐름을 완성. 첫 로딩 이후 사진당 1초 내외.
- 소재별 반응 규칙을 테스트 벤치와 사진 프록시에 **같은 규칙으로** 적용.
- 키가 없거나 호출이 실패해도 색상 휴리스틱으로 자동 폴백되어 데모가 멈추지 않음 (힌트에 "간이 판단"/"OpenAI" 표시).
- 물체 인터페이스를 공통 규약으로 통일: `{ group, hittables(), hit(intersection, strength), update(dt), dispose(), stats(), statusText() }`.
- `npm run build:single`로 three.js만 CDN에서 받는 단일 HTML(`dist/index.html`) 배포 가능.

### 안된 점 / 알려진 제한

- **OpenAI 실제 응답 경로 미검증.** 작업 PC에 키가 없어 키 없을 때의 503 폴백만 확인했다.
- 단일 파일 빌드는 MediaPipe WASM·모델·샘플 사진을 담지 못해 **사진 탭 없이** 테스트 벤치로만 열린다. `dist/artifact.html`도 같은 제약.
- 세그먼트는 사진 중앙 물체를 자동 선택. 중앙에 없으면 직접 탭해야 한다.
- 배경 채우기는 진짜 인페인팅이 아니라 주변색 번짐이라 복잡한 배경에서 뭉개진다.
- 파편끼리 충돌하지 않고 바닥만 인식. 유리 파편 70개는 저사양 폰에서 프레임 저하.
- iOS Safari 진동 미지원. 모바일 자동재생 정책 때문에 첫 터치 이후에야 소리가 켜진다.
- 사내/카페 Wi-Fi는 기기 간 통신을 막을 수 있어 폰 테스트는 핫스팟이 확실하다.
- `samples/`의 `glass-bottle.jpg`, `metal-mokapot.jpg`, `ceramic-mug.jpg`, `wood-chair.jpg`는 출처 확인이 필요하다 (나머지는 Wikimedia Commons, `samples/CREDITS.md`).

## 면접 준비

### 한 문장 소개

사진을 찍으면 브라우저 안에서 온디바이스 AI가 물체 영역을 잘라내고 소재가 나무인지 금속인지 유리인지 판단해서, 확인이나 수정 화면 없이 그 자리에서 가상 방망이로 부수는 모바일 대응 웹 3D 데모입니다. 네이티브 앱이 아니라 브라우저에서 돌고, 첫 모델 로딩 약 16MB가 끝나면 사진당 1초 안팎으로 분석에서 타격까지 이어집니다.

### 아키텍처

- [client] 웹 데모 :: three.js, importmap, Web Audio :: 브라우저 (PC `localhost:5173`, 폰은 같은 Wi-Fi 주소)
- [client] 온디바이스 세그멘터 :: MediaPipe InteractiveSegmenter, `magic_touch.tflite` 약 16MB, WASM :: 브라우저
- [client] 색상 휴리스틱 폴백 :: `src/photo/material.js` 색상 통계 점수식 :: 브라우저
- [server] 로컬 서버 :: `serve.js`, Node.js, 프레임워크 없음 :: 개발 PC, 포트 5173
- [external] 비전 소재 판정 :: OpenAI 비전 API, `detail: low`, JSON 스키마 응답 :: OpenAI API
- 웹 데모 -> 온디바이스 세그멘터 :: 사진(최대 1024px)과 중앙 시드 점
- 온디바이스 세그멘터 -> 웹 데모 :: 마스크, 윤곽 폴리곤, bbox
- 웹 데모 -> 로컬 서버 :: `POST /api/analyze`, 잘라낸 물체 이미지
- 로컬 서버 -> 비전 소재 판정 :: 이미지와 소재 접기 규칙(`INSTRUCTIONS`) 요청
- 비전 소재 판정 -> 로컬 서버 :: 물체 이름과 wood/metal/glass 판정
- 로컬 서버 -> 웹 데모 :: 판정 결과, 키 없으면 503
- 웹 데모 -> 색상 휴리스틱 폴백 :: 503이나 호출 실패 시 사진 색상 통계

### 고민한 점

- **확인·수정 화면을 넣을 것인가** — 사진을 찍고 나서 영역을 확인받는 단계를 넣으면 안전하겠지만 손맛이 끊기겠다고 판단해서, 사진 중앙 점을 시드로 자동 선택하고 바로 타격까지 가게 했습니다. 실제로 돌려 보니 물체가 중앙에 없으면 엉뚱한 걸 잡길래, 물체 밖을 탭하면 그 자리를 새로 잘라내는 조작을 따로 붙여서 수정 자체는 가능하되 흐름은 안 멈추게 했습니다.
- **소재 판정을 API에 맡길 것인가 로컬에서 할 것인가** — API를 먼저 부르고 실패하면 색상 통계 휴리스틱으로 내려가는 2단으로 짰습니다. 정하면서 가장 신경 쓴 건 폴백으로 내려간 사실을 숨기지 않는 것이어서, 힌트에 "간이 판단"인지 "OpenAI"인지 그대로 띄우기로 했습니다.
- **모델과 비용을 어디에 맞출 것인가** — 기본값은 플래그십으로 두되 계정 권한이 없어 404나 403이 오면 `OPENAI_MODEL_FALLBACKS`에 적힌 모델을 순서대로 시도하고, 어떤 모델이 답했는지 서버 로그에 남기게 했습니다. 이미지는 `detail: low`로 보내고 응답은 JSON 스키마로 고정했으며, 비용을 아끼려면 경량 모델로 바꾸라고 문서에 적어 뒀습니다.
- **단일 파일로 공유할 것인가, 사진 모드를 살릴 것인가** — 둘 다 되게 하려다 안 됐습니다. MediaPipe WASM과 모델, 샘플 사진을 HTML 하나에 담을 수가 없어서, 공유용 빌드는 테스트 벤치만 열리는 반쪽으로 남겨 두는 쪽을 택했습니다.
- **파편 수를 얼마나 늘릴 것인가** — 유리를 40~70개 얇은 조각으로 깨뜨리면 보기에는 확실히 좋은데 저사양 폰에서 잠깐 프레임이 떨어진다고 자료가 인정하고 있습니다. 다음 단계 목록에도 파편 수와 프레임을 맞바꾸는 튜닝이 그대로 남아 있습니다.

### 예상 질문

1. **Q:** (L1) 이걸 네이티브 앱이 아니라 브라우저에서 돌리기로 하면서 어떤 제약이 생겼고 각각 어떻게 다루셨나요?
   **A:** 세 가지가 자료에 남아 있습니다. 모델을 앱에 넣을 수 없어서 약 16MB짜리 `.tflite`를 첫 실행 때 내려받아야 하고 몇 초가 걸리는데, 그 뒤로는 사진당 1초 안팎으로 돕니다. 모바일 자동재생 정책 때문에 소리를 처음부터 켤 수 없어서 첫 터치 이후에 켜지게 했고, iOS Safari는 진동을 지원하지 않아 안드로이드에서만 진동이 옵니다. 마지막은 네트워크인데, 폰으로 보려면 같은 Wi-Fi의 `phone : http://192.168.x.x:5173/`를 열어야 하고 기기 간 통신을 막는 사내나 카페 Wi-Fi에서는 핫스팟을 쓰라고 안내해 뒀습니다.
   **꼬리:** 16MB 모델을 매번 받게 하지 않으려면 무엇을 바꾸시겠어요?
   **틀리기 쉬운 답:** "웹이라 어디서든 바로 됩니다"라고만 말하는 경우가 있는데, 실제로는 첫 로딩 비용과 자동재생·진동 같은 플랫폼 정책이 사용 경험을 꽤 바꿔 놓았습니다.
2. **Q:** (L2) 잘라낸 영역을 사용자가 확인하고 고치는 화면을 일부러 빼셨는데, 왜 그러셨고 대신 무엇을 치르셨나요?
   **A:** 목표가 사진에서 분석, 타격까지 끊기지 않는 손맛이었기 때문입니다. 자료에서도 사진 모드를 설명하면서 "확인·수정 UI 없음"을 기능처럼 앞에 적어 뒀습니다. 치른 값은 정확도인데, 세그먼트가 사진 중앙 물체를 자동으로 고르다 보니 물체가 중앙에 없으면 엉뚱한 걸 잡고 그때는 사용자가 물체 밖을 탭해서 대상을 다시 잘라내야 합니다. 이 탭은 스윙을 하지 않는 별도 동작으로 떼어 놔서, 고칠 수는 있게 두되 흐름이 멈추지는 않게 했습니다.
   **꼬리:** 확인 단계를 넣는다면 어디에 넣어야 흐름을 가장 덜 해칠까요?
   **틀리기 쉬운 답:** "AI가 정확해서 확인이 필요 없었습니다"라고 답하는 경우가 있는데, 실제로는 중앙에 없으면 빗나간다는 걸 알려진 제한으로 적어 뒀고 흐름을 위해 감수한 선택이었습니다.
3. **Q:** (L2) 테스트 벤치의 3D 물체와 사진에서 잘라낸 프록시는 만들어지는 방식이 전혀 다른데 소재별 반응 규칙은 같습니다. 어떻게 그렇게 만드셨나요?
   **A:** 물체를 공통 인터페이스로 맞췄습니다. `{ group, hittables(), hit(intersection, strength), update(dt), dispose(), stats(), statusText() }` 하나만 지키면 입력과 HUD, 파편 코드가 대상을 구분하지 않습니다. 덕분에 나무는 3타에 보로노이 5~8조각, 금속은 영구 찌그러짐에 파괴 없음, 유리는 손상이 쌓인 뒤 40~70개 조각이라는 규칙을 벤치와 사진 프록시 양쪽에 같은 규칙으로 걸 수 있었습니다. 자료도 벤치와 같은 규칙을 사진 프록시에 그대로 적용했다고 성과로 적고 있습니다.
   **꼬리:** 소재가 하나 더 늘면 어디를 고쳐야 하나요?
   **틀리기 쉬운 답:** "사진도 결국 3D 메시니까 자동으로 같습니다"라고 답하는 경우가 있는데, 실제로 사진 쪽은 컷아웃 격자 평면이고 배경 채우기와 깊이 보정이 따로 붙어 있어서 인터페이스를 맞춰 준 덕에 같아진 것입니다.
4. **Q:** (L3) 심사위원이 자기 폰으로 이 데모를 연다고 하면 무엇이 먼저 실패할까요?
   **A:** 순서대로 보면 우선 폰이 로컬 서버에 닿지 못하는 경우입니다. 사내나 카페 Wi-Fi가 기기 간 통신을 막으면 주소 자체가 안 열려서 핫스팟이 확실하다고 자료에 적어 뒀습니다. 연결되면 다음은 첫 모델 로딩 몇 초의 침묵이고, 그다음은 기대와 다른 동작인데 첫 터치 전에는 소리가 나지 않고 iOS에서는 진동이 없습니다. 마지막이 성능으로, 유리 파편 70개 구간에서 저사양 폰 프레임이 떨어집니다. 파일 하나로 공유한 빌드를 열었다면 사진 탭 자체가 없다는 점도 같이 말씀드려야 할 것 같습니다.
   **꼬리:** 이 중에 어느 걸 제일 먼저 고치시겠어요. 이유는요?
   **틀리기 쉬운 답:** "렌더링 최적화가 문제입니다"라고 바로 답하는 경우가 있는데, 실제로 자료에 적힌 실패는 네트워크와 플랫폼 정책 쪽이 먼저고 프레임 저하는 특정 구간에만 나타납니다.
5. **Q:** (L3) 비전 API 판정 경로가 실제로 동작한다는 걸 어떻게 확인하셨나요?
   **A:** 확인하지 못했습니다. 작업 PC에 키가 없어서 키가 없을 때의 503 폴백만 봤고, 실제 응답 경로는 검증하지 못했다고 자료에 그대로 적혀 있습니다. 확인할 수단은 만들어 뒀는데, 서버를 켠 상태에서 `node tools/analyze.js samples/mug.jpg`로 한 장씩 시험할 수 있고 어떤 모델이 답했는지 서버 로그에 찍히게 해 뒀습니다. 다음 단계 목록에도 API 키를 연결한 뒤 비전 판단 경로를 검증하는 일이 2번 항목으로 남아 있습니다.
   **꼬리:** 키 없이도 그 경로의 회귀를 막으려면 무엇을 두시겠어요?
   **틀리기 쉬운 답:** "폴백이 있으니 문제없습니다"라고 답하는 경우가 있는데, 실제로 폴백이 도는 것은 주 경로가 도는 증거가 아니고 오히려 주 경로가 조용히 죽어도 화면이 멀쩡해 보이게 만듭니다.
