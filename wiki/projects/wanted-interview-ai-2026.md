## 1. 개요

- **코드 저장소**: https://github.com/Wanted-Frame/Frame — 팀 조직 계정 (출처: 로컬 git 원격, 2026-09-22 확인)

- 대회: 원티드 AI Championship 2026 해커톤
- 프로젝트명: FRAME
- 기간: 자료에 없음
- 주제: 채용 영상(지원 영상·녹화 면접)에서 검토 기준에 해당하는 지원자 발언을 찾아 원문과 타임스탬프로 연결하는 도구
- 배포: https://frame-interview.vercel.app/ (별도 API 키 없이 샘플 인터뷰 체험 가능)
- 결과(수상 여부): 자료에 없음

## 2. 문제 정의

영상에는 지원자의 경험과 생각이 담겨 있지만 필요한 부분을 다시 찾기 어렵다. '협업 경험'이나 '성능 개선 과정'을 확인하려면 재생 위치를 반복해서 옮기거나 긴 전사문을 읽어야 한다. 면접관 질문과 지원자 답변이 섞여 있어 발언 주체도 따로 확인해야 한다.

FRAME은 **검토 기준 → 관련 발언 → 원본 구간**을 연결해 담당자가 근거를 찾아 확인하는 과정을 돕는다.

### 검토 원칙 (제품이 명시한 4가지)

- 원본에 연결되는 근거: 분석 결과는 실제 전사 구간에 연결되고 담당자가 직접 재생해 확인한다. → [[evidence-linked-llm-output]]
- 지원자 발언 중심: 면접관 발언은 질문 맥락으로만 쓰고 지원자의 경험 근거와 구분한다.
- 불확실성 표시: 관련 발언을 찾지 못했거나 인식이 불확실한 경우를 구분하고, 발언이 없다는 이유로 역량 부족을 판단하지 않는다.
- 사람의 최종 판단: 담당자가 근거를 수정할 수 있고, 서비스는 점수·순위·합격 여부를 자동 결정하지 않는다.

## 3. 접근

### 사용 흐름

1. 영상과 기준 준비 — MP4 업로드, 직군 선택 시 기본 검토 기준 4개 + 공통 기준 2개 로드, 수정·추가·삭제 가능
2. 화자 확인 — 전사된 발언을 보고 지원자와 면접관을 사용자가 지정
3. 관련 발언 탐색 — 기준별 결과에서 원문과 연결된 시간 구간 확인
4. 원본 검토 — 영상 재생으로 문맥 확인, 근거 추가·제외
5. 결과 저장 — Markdown 내보내기

### 파이프라인

```
영상 업로드·기준 입력 → Supabase 비공개 저장 → Trigger.dev 백그라운드 작업
→ AssemblyAI 전사·화자 구분 → 사용자 화자 확인 → OpenAI 기준별 발언 연결
→ 원문·타임스탬프 검토
```

### 기술 스택

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 웹 | Next.js · React · TypeScript | 업로드, 영상 재생, 전사·근거 검토 화면과 API |
| 데이터 | Supabase | 검토 데이터 및 비공개 영상 저장 |
| 음성 처리 | AssemblyAI (`universal-2`) | 한국어 전사와 화자 구분 |
| 근거 분석 | OpenAI (`gpt-4.1-mini`) | 검토 기준과 지원자 발언 연결 |
| 작업 실행 | Trigger.dev | 전사·분석·삭제 및 만료 데이터 정리 |
| 배포 | Vercel | 웹 애플리케이션 호스팅 |

실행 환경은 Node.js 24 + npm. `npm ci && npm run dev`로 환경변수 없이 샘플 모드(외부 API 미호출) 실행.

### 제약과 한도

- 한국어 MP4 **최대 50MB · 15분**, 검토 기준 **3~6개**
- 업로드 영상은 비공개 저장, **24시간 후 만료**. 사용자가 직접 삭제 가능
- 동시 보관 전체 15건, 최근 24시간 전체 업로드 예약 20건(`DAILY_UPLOAD_LIMIT`), 세션별 3건(`DAILY_SESSION_UPLOAD_LIMIT`)
- 업로드 예약은 실패해도 사용량에 포함. 앱 사용량 제한은 API 제공자 결제 한도를 대체하지 않음

### 데이터 처리·보안

- 영상은 Supabase 비공개 버킷 저장 + 서명 URL 접근
- 서명된 HttpOnly 쿠키로 브라우저 세션별 소유자 구분 → 쿠키를 지우거나 다른 브라우저를 쓰면 기존 영상에 접근 불가
- 전사를 위해 영상이 AssemblyAI에, 근거 분석을 위해 전사가 OpenAI에 전달. OpenAI 요청은 `store: false`
- 앱 보관 기간과 외부 제공자의 데이터 처리 정책은 별개임을 명시
- 삭제 요청 시 영상 파일과 외부 전사를 삭제하고, 실패한 삭제는 정리 작업에서 재시도. 업로드 URL 유효기간 동안 삭제 표식을 유지해 지연 업로드도 정리

자세한 백그라운드 작업 설계는 [[background-job-pipeline]], 전사·화자 구분은 [[speaker-diarization]] 참고.

### 디자인 시스템

조용한 근거 검토 작업 공간. 넓은 여백, 얇은 구분선, 어두운 본문, 밑줄 액션으로 주장에서 출처로 이동하는 동선에 시각적 잡음을 없앴다.

- 색: `--bg #FFFFFF`, `--ink #202124`, `--muted #666666`, `--line #E5E5E5`, `--focus #555555`
- 타이포: 본문 `Noto Sans KR`, UI/메타 `Manrope`. 본문 14~15px / 행간 1.75~1.95, 제목 18~25px
- 레이아웃: 4px 기본 리듬(12·16·20·24·32px), 데스크톱 2열 / 850px 미만 1열. 읽기 영역이 자체 스크롤을 갖고 페이지 셸은 뷰포트에 고정. 모달은 최소 32px 거터, 최대 740px
- 컴포넌트: 근거 액션(타임스탬프/문맥/비교/제외 버튼), 기준 프리셋(직군 선택 + 편집 가능한 기준 행 6개, 최소 3 최대 6), 비교 모달(native dialog)
- 깊이: 그림자 없이 테두리만. 다이얼로그는 단일 회색 테두리 + 어두운 배경
- 접근성: 모든 액션에 보이는 텍스트 또는 접근성 레이블, 키보드 포커스 가시성 유지, native dialog 키보드 동작 보존, 비교 화면 본문 14px 이상, `prefers-reduced-motion` 존중
- 인정한 부채: 현재 작업 공간이 CSS의 아이콘 숨김 규칙을 쓰고 있어, 새 비교 액션도 시각 언어 혼용을 피하려고 같은 패턴을 따름

모션은 로딩 스피너와 native dialog 동작으로만 제한.

## 4. 잘된 점 / 안된 점

원자료에 명시적인 회고나 자평은 없다. 다만 자료가 스스로 밝힌 사항은 다음과 같다.

- 의도적으로 지킨 것: LLM 출력이 아니라 원본 전사 구간을 최종 근거로 두고, 점수·합격 판정을 자동화하지 않음
- 인정한 부채: CSS 아이콘 숨김 규칙 사용 (위 디자인 절)
- 배포 시 주의로 기록된 함정: Vercel 서버 비밀키에 `NEXT_PUBLIC_` 접두사 금지, Trigger.dev CLI의 `--env-file`은 원격 작업 환경변수를 자동 등록하지 않음, `cleanup-expired-reviews` 스케줄 활성화 확인 필요

## 5. 재사용 가능한 것

- 프로젝트 구조: `src/app`(페이지·API), `src/components`(영상 검토 화면), `src/lib`(데이터 모델·근거 검증·샘플 데이터), `src/server`(세션·DB·외부 API), `src/trigger`(백그라운드 작업), `supabase/`(DB 초기 설정), `public/demo/`(가상 인터뷰 영상·포스터), `tests/`, `docs/`
- Supabase 초기 마이그레이션 `supabase/migrations/001_initial.sql` — 검토 데이터 테이블, 사용량 제한 함수, 비공개 영상 버킷을 한 번에 생성
- 샘플 모드: 외부 API 없이 도는 데모 경로. 직접 제작한 64초 가상 인터뷰 + 합성 음성 + 사전 작성 분석 결과 → 심사위원이 키 없이 바로 체험 가능
- 세션 비밀값 생성: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
- 검증 명령: `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e` (브라우저 테스트는 설치된 Microsoft Edge 사용, 샘플 재생·탐색/근거 편집/화자 변경/업로드 제한/모바일 레이아웃 검사)
- 워커: `npm run worker:dev`(로컬), `npm run worker:deploy`(배포)
- 디자인 토큰 5개짜리 미니멀 팔레트와 "테두리만" 표면 전략

## 면접 준비

### 한 문장 소개

채용 영상에서 '협업 경험' 같은 검토 기준에 해당하는 지원자 발언을 찾으려면 재생 위치를 반복해서 옮기거나 긴 전사문을 읽어야 했습니다. FRAME은 업로드된 MP4를 전사·화자 구분한 뒤 기준별로 관련 발언을 연결하고, 모든 결과를 원본 전사 구간과 타임스탬프로 되돌려 담당자가 직접 확인하게 만든 도구입니다. 점수·순위·합격 여부는 자동으로 결정하지 않고, 배포본에서 API 키 없이 샘플 인터뷰를 체험할 수 있습니다.

### 기술 스택과 선택 이유

| 기술 | 역할 | 왜 이걸 썼나 | 대안과 포기한 것 |
|---|---|---|---|
| Next.js · React · TypeScript | 업로드·영상 재생·근거 검토 화면과 API | 이유 자료에 없음 | 이유 자료에 없음 |
| Supabase | 검토 데이터 저장 + 영상 비공개 버킷 | 이유 자료에 없음 (사용 방식만 기록: 비공개 버킷 저장 + 서명 URL 접근) | 이유 자료에 없음 |
| AssemblyAI (`universal-2`) | 한국어 전사와 화자 구분 | 이유 자료에 없음. 단 자료는 모델을 바꿀 때 "한국어 전사·화자 구분 및 구조화된 응답 지원"을 먼저 확인하라고 적어, 이 셋을 선택 요건으로 본 것은 드러난다 | 이유 자료에 없음 |
| OpenAI (`gpt-4.1-mini`) | 검토 기준과 지원자 발언 연결 | 이유 자료에 없음. 요청에 `store: false`를 쓴다는 처리 방침만 기록 | 이유 자료에 없음 |
| Trigger.dev | 전사·분석·삭제 작업과 만료 데이터 정리(15분 주기 `cleanup-expired-reviews`) | 이유 자료에 없음 (역할과 배포 함정만 기록) | 이유 자료에 없음 |
| Vercel | 웹 앱 호스팅 | 이유 자료에 없음 | 이유 자료에 없음 |
| Node.js 24 + npm | 실행 환경, `npm ci && npm run dev`로 환경변수 없이 샘플 모드 | 이유 자료에 없음 | 이유 자료에 없음 |

### 고민한 점

- **화자 역할을 자동으로 정할 것인가** — 전사·화자 구분은 AssemblyAI가 하지만, 어느 화자가 지원자인지는 사용 흐름 2단계에서 사용자가 확인·지정하도록 남겼다. 결과적으로 분석 전에 사람이 한 번 개입하는 단계가 파이프라인 중간에 고정됐다.
- **자동 점수·순위를 넣을 것인가** — 넣지 않기로 하고 이를 제품 원칙 4가지 중 하나로 명시했다. 담당자가 근거를 추가·제외할 수 있게 하고, 관련 발언을 찾지 못한 경우를 "역량 부족"으로 읽지 않도록 구분해 표시한다. 자료에 규제 검토 서술은 없고 제품 원칙으로만 선언돼 있다.
- **심사위원이 키 없이 볼 수 있게 할 것인가** — 외부 API를 호출하지 않는 샘플 모드를 따로 만들고, 직접 제작한 64초 가상 인터뷰 + 합성 음성 + 사전 작성 분석 결과를 붙였다. 결과는 배포본에서 API 키 없이 체험 가능하지만, 실제 경로와 샘플 경로 두 갈래를 코드에 유지해야 한다.
- **원본 영상을 얼마나 오래, 누구 것으로 둘 것인가** — 24시간 만료 + 사용자 직접 삭제 + 서명된 HttpOnly 쿠키로 세션별 소유자 구분을 택했다. 대가로 쿠키를 지우거나 다른 브라우저를 쓰면 기존 영상에 접근할 수 없다는 점을 자료가 그대로 인정한다.
- **사용량 한도를 어디까지 앱에서 막을 것인가** — 동시 보관 15건, 24시간 전체 20건, 세션별 3건으로 걸되, 업로드 예약이 실패해도 사용량에 포함하고 "앱 사용량 제한은 API 제공자 결제 한도를 대체하지 않는다"고 명시했다.

### 예상 질문

1. **Q:** (L1) 사용자가 영상을 올린 뒤 결과를 볼 때까지 시스템이 거치는 단계를 순서대로 설명하라.
   **A:** 업로드와 검토 기준 입력 → Supabase 비공개 버킷 저장 → Trigger.dev 백그라운드 작업 시작 → AssemblyAI 전사·화자 구분 → 사용자가 지원자/면접관 화자를 확인 → OpenAI가 기준별로 관련 발언을 연결 → 화면에서 원문·타임스탬프로 검토하고 Markdown으로 내보냅니다. 중간에 사람이 화자를 확정하는 단계가 들어가므로 전체가 한 번에 끝나는 자동 파이프라인이 아니라 두 구간으로 끊긴 비동기 흐름입니다.
   **꼬리:** 화자 확인 전에 분석을 먼저 돌리면 무엇이 잘못되나?
   **틀리기 쉬운 답:** "업로드하면 AI가 알아서 분석해준다"고 뭉뚱그리는 답. 화자 확정이라는 사람 개입 단계와 그 때문에 작업이 두 번 나뉜다는 점이 빠지면 파이프라인을 설명하지 못한 것이다.
2. **Q:** (L2) 채용 도구인데 점수·순위·합격 여부를 자동으로 내지 않기로 했다. 이 결정이 화면과 데이터에 실제로 어떻게 드러나는가?
   **A:** 세 곳에 드러납니다. 첫째, 결과 단위가 점수가 아니라 "기준 ↔ 관련 발언 ↔ 타임스탬프" 연결이라 화면의 최종 산출물이 재생 가능한 구간입니다. 둘째, 담당자가 근거를 추가·제외할 수 있어 시스템 출력이 최종본이 아닙니다. 셋째, 관련 발언을 찾지 못했거나 인식이 불확실한 경우를 따로 구분해 표시하고, 발언이 없다는 이유로 역량 부족이라고 판단하지 않는다고 못 박았습니다. 다만 이 결정의 근거로 규제나 법령을 검토했다는 서술은 자료에 없고, 제품 원칙으로만 선언돼 있습니다.
   **꼬리:** 그럼에도 사용자가 이 화면을 보고 사실상 순위를 매긴다면, 도구가 할 수 있는 일은 무엇인가?
   **틀리기 쉬운 답:** "AI가 점수를 매기면 편향되니까 뺐다"고만 답하는 것. 자료에는 편향 측정이나 공정성 검증 기록이 없으므로, 검증한 적 없는 주장을 이유로 대면 꼬리질문에서 무너진다.
3. **Q:** (L2) 심사위원이 API 키 없이 바로 체험할 수 있게 만든 결정은 무엇을 얻고 무엇을 지불했나?
   **A:** 얻은 것은 진입 장벽 제거입니다. 배포 URL만 열면 타임스탬프 재생, 전사 검색, 근거 수정과 내보내기를 그대로 해볼 수 있고, 로컬에서도 `npm ci && npm run dev`만으로 환경변수 없이 돕니다. 지불한 것은 샘플 자산과 두 갈래 실행 경로입니다. 64초 가상 인터뷰 영상과 합성 음성, 사전 작성 분석 결과를 직접 만들어야 했고, 외부 API를 호출하지 않는 샘플 모드를 코드에 유지해야 합니다. 브라우저 테스트도 샘플 재생·탐색, 근거 편집, 화자 변경, 업로드 제한, 모바일 레이아웃을 검사하는 쪽으로 구성돼 있고, 실제 서비스 연결은 별도로 확인한다고 적혀 있습니다.
   **꼬리:** 샘플 경로와 실제 경로가 갈라져 한쪽만 동작하는 상태를 어떻게 막겠는가?
   **틀리기 쉬운 답:** "데모 데이터를 넣어뒀다"로 끝내는 답. 샘플 모드가 외부 API를 아예 호출하지 않는 별도 경로라는 점을 말하지 않으면 그냥 목업과 구분되지 않는다.
4. **Q:** (L3) 한국어 MP4 50MB·15분, 동시 보관 15건, 24시간 20건이라는 한도가 걸려 있다. 사용자가 10배가 되면 어디가 먼저 깨지는가?
   **A:** 앱이 스스로 건 한도가 먼저 막습니다. 24시간 전체 20건과 동시 보관 15건은 사용자 수와 무관한 절대값이라, 사용자가 늘면 새 업로드가 거절되는 쪽으로 먼저 나타납니다. 그다음이 외부 비용과 처리량입니다. 자료가 "업로드 예약은 실패해도 사용량에 포함"되고 "앱 사용량 제한은 API 제공자 결제 한도를 대체하지 않는다"고 못 박은 것은, 앱 한도를 풀면 AssemblyAI·OpenAI 결제 한도가 다음 벽이 된다는 뜻입니다. 15분 영상 전사와 기준별 분석은 요청 안에서 끝낼 수 없어 Trigger.dev로 뺀 작업이므로, 동시 업로드가 몰리면 워커 처리 대기가 체감 지연이 됩니다. 각 한도를 넘겼을 때의 실제 동작을 측정한 기록은 자료에 없습니다.
   **꼬리:** 한도를 올리기 전에 무엇을 먼저 계측하겠는가?
   **틀리기 쉬운 답:** "서버를 늘리면 된다"는 답. 병목이 자체 서버가 아니라 외부 API 처리량과 결제 한도, 그리고 앱이 명시적으로 건 상한이라는 점이 빠진다.
5. **Q:** (L3) 영상은 AssemblyAI로, 전사는 OpenAI로 나간다. 사용자가 삭제를 요청하면 실제로 무엇이 지워지고 무엇이 안 지워지는가?
   **A:** 삭제 요청 시 영상 파일과 외부 전사를 삭제하고, 실패한 삭제는 정리 작업에서 재시도합니다. 업로드 URL이 유효한 동안은 삭제 표식을 유지해 뒤늦게 도착한 업로드도 정리합니다. OpenAI 요청은 `store: false`로 보냅니다. 다만 자료는 "앱의 보관 기간과 외부 제공자의 데이터 처리 정책은 구분된다"고 명시하고 있어서, 외부 제공자 쪽에 무엇이 얼마나 남는지는 이 앱이 보장하는 범위 밖입니다. 면접에서도 여기까지가 확인된 범위라고 말하는 편이 맞습니다.
   **꼬리:** "전부 지워집니다"라고 사용자에게 고지할 수 있나? 없다면 뭐라고 써야 하나?
   **틀리기 쉬운 답:** "24시간 뒤 자동 삭제되니 데이터가 남지 않는다"는 답. 앱 보관 기간과 외부 제공자 정책이 별개라는 것을 자료 스스로 구분해 적어 두었다.
