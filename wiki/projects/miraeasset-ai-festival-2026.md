# 미래에셋증권 AI Festival 2026 — 공시 근거 기반 AI Agent

## 1. 개요

- **코드 저장소**: https://github.com/miraeasset-aifestival-2026-dart/dis-136 — 초기 설계 버전은 https://github.com/accidentable/AI_miraeasset (비공개) (출처: 로컬 git 원격, 2026-09-22 확인)

- 대회명: 제10회 2026 미래에셋증권 AI Festival, 공시 Agent 과제
- 팀: 마크주식버그 (윤태호)
- 산출물: DART 공시 질의응답 API. 평가 API `http://49.50.137.93:8000/answer` (GET/POST), 상태 확인 `/health`
- 코퍼스: 주최 측 제공 DART 공시 70개사, 2023.01~2026.03, 4,204건
- 제출 문서: README, `API_SPEC.md`, 기술 제안서 PDF
- 검증 보고서 일자: 2026-09-04 (3차 실전 검증)
- 결과(수상 여부): 자료에 없음

## 2. 문제 정의

리서치 담당자가 자연어로 던지는 공시 질문에, **근거 접수번호가 붙은 답**을 돌려주는 것이 과제다.
평가 규칙이 과제 자체를 규정한다.

- LLM은 HyperCLOVA X만 쓴다. 다른 모델을 쓰면 평가 대상에서 빠진다.
- 제공 코퍼스 외 데이터(뉴스·리포트·위키·OpenDART 실시간 호출)를 쓰지 않는다.
- 모든 답변에 근거 공시의 접수번호를 표시한다.
- 확인할 수 없으면 "공시에서 확인되지 않음"이라고 말한다. 추측하지 않는다.
- 공시에 근거가 없는 미래 예측·투자의견을 만들지 않는다.

즉 정확도보다 먼저 **근거 없는 문장을 내지 않는 것**이 요구사항이다.

## 3. 접근

### 3-1. 설계의 축 — 질의 시점에 검색하지 않고 미리 구조화한다

초기 설계 단계에서 정한 전제는 "코퍼스는 유한하고 고정돼 있다"였다. 서식이 정해진 공시는
결정론적으로 파싱해 SQL 테이블로 만들고, 서술형 정기공시만 검색에 맡긴다.
계약 금액 비교나 "해지된 계약이 있는가" 같은 질의는 유사도 검색이 아니라 SQL로 답한다.
**수치 정확도를 임베딩에 맡기지 않는 것**이 핵심이었고, 이 전제는 최종 제출물까지 그대로 유지됐다.

### 3-2. 최종 구성

| 계층 | 구현 | 역할 |
|---|---|---|
| 수집·파싱 | `src/parse/*` (DART XML·XForms HTML 파서) | 공시 유형별 정형 레코드, 원문 섹션, 표 격자 생성 |
| 저장·검색 | SQLite `db/disclosure.db` (FTS5 3종: 섹션·정기보고서 표·수시공시 표), `db/title_vectors.db` (목차 제목 임베딩 311, bge-m3) | 정형값과 검색 근거 보존 |
| 도구 계층 | `src/agent/tools.py`, `table_tools.py` (도구 36종) | 회사·기간·유형·표 이름으로 근거를 확정 |
| 오케스트레이터 | `src/agent/orchestrator.py` | 정책·범위 판정, 결정론 경로 73종, 게이트, 분해, 사전 검색, 검증 |
| 모델 | HyperCLOVA X HCX-005 (function calling) | 도구 선택과 근거 기반 서술 |
| 제공 | FastAPI `src/agent/server.py`, systemd, Docker | GET/POST `/answer`, `/health` |

주요 테이블 규모: `documents` 4,204, `document_sections`+FTS 146,625, `report_tables`+FTS 628,827,
`filing_tables`+FTS 27,318, `financial_facts` 6,193, `contracts`/`corrections`/`terminations` 1,106/2,160/20,
`holdings` 1,083, `major_events`/`material_events`/`investments` 598/300/43.

### 3-3. 질문 처리 흐름 8단계

1. 정책·범위 판정 — 개인정보·투자 권유·미래 전망·프롬프트 공격은 모델 호출 전에 차단. 코퍼스 밖 회사·기간은 정보한계 응답.
2. 결정론 경로 73종 — 재무지표, 증감률·순위·두 회사 비교, 계약 금액·상대·기간·정정 체인, 지분·최대주주, 자사주·증자·사채 결의, 해지, 부문·지역별 매출 표 등. 규칙이 답하면 0초 안에 접수번호와 함께 반환. → [[deterministic-rule-path]]
3. 게이트 — 규칙의 답이 질문을 다 덮는지 확인하고, 일부만 덮으면 그 결과를 **확정 사실표**로 모델에 넘긴다.
4. 복합 질문 분해 — 물음이 둘 이상이면 독립 하위 질문으로 나눈다.
5. 근거 공급(사전 검색) — 해당 연도·분기의 표와 섹션, 계약 체인, 자금 사용·조달 표, 정정 표를 미리 넣는다. 항목이 행이고 건이 열인 가로 표는 건별 레코드로 변환.
6. 도구 루프 — HCX-005가 도구를 고르고(최대 2회 재요청) 렌더링된 근거만 보고 작성. 문항 예산 80초.
7. 검증 — 연도 열 확인, 금액 정규화 후 근거 대조, 미뒷받침 주장 완화, 접수번호 정리. → [[grounded-answer-verification]]
8. 응답 — 5필드 JSON (`question_id`, `question`, `retrieved_context`, `think_trace`, `answer`).

### 3-4. API 계약

`/answer`는 **어떤 입력에도 HTTP 200과 5필드**로 응답한다. 평가 하네스가 JSON 파싱에 실패해
문항이 무응답 처리되는 일을 막기 위해 내부 예외·모델 호출 실패·시간 초과까지 전부 한계 응답으로 되돌린다.
부재의 종류(사실 없음 / 공시유보 / 시간 예산 초과 / 모델 오류 / 정책 차단 / 범위 밖)마다 문장이 다르고,
근거가 없는 한계 응답에는 접수번호를 붙이지 않는다.

### 3-5. 정정공시 처리

정정공시는 원공시와 `superseded_by` / `supersedes` 체인으로 연결되어, 조회는 기본적으로
최신 유효 판을 돌려주고 정정 전후 값은 `corrections`에서 읽는다. → [[disclosure-correction-chain]]

### 3-6. 초기 설계에서 최종까지의 변화

| 항목 | 초기 설계 | 최종 제출물 |
|---|---|---|
| 정기공시 처리 | 목차 기반 섹션 분할 → 섹션 임베딩 → 하이브리드 리랭킹 | FTS5 3종이 런타임 검색을 맡고, 임베딩은 **목차 제목 311건**만(`title_vectors.db`). `retrieval/`의 hybrid·vector_store는 파일럿 잔존으로 런타임 미사용 |
| 도구 수 | 11종 | 36종 (+ 표 격자 도구 `table_tools.py` 신설) |
| 표 데이터 | 계획에 별도 층 없음 | `report_tables` 628,827 / `filing_tables` 27,318 격자로 적재 |
| 오케스트레이션 | function calling으로 두 층 호출 | 정책 판정 → 결정론 경로 73종 → 게이트 → 분해 → 사전 검색 → 도구 루프 → 검증의 다단 파이프라인 |
| 평가 | 자체 골든셋 자동 생성(`goldenset/generate.py`) + `evalkit` 채점기 | 골든셋 과적합이 확인되어 DB가 질의를 고르는 3차 검증으로 전환. 회귀 테스트 617개로 고정 |
| 배포 | 로컬·Ncloud 서버 수동 운용, PowerShell 셋업 스크립트 | Docker(비루트·읽기 전용 FS·`no-new-privileges`) + systemd `disclosure-api.service` |

방향이 바뀐 지점은 하나다. **검색을 잘하는 쪽에서 규칙으로 확정하는 쪽으로** 무게가 옮겨갔다.
임베딩은 서술 섹션을 찾는 보조 수단으로 축소됐고, 대신 표를 격자로 적재해 규칙이 직접 값을 꺼내게 했다.

## 4. 잘된 점 / 안된 점

### 잘된 점

- 3차 실전 검증 전체 스윕 **74/74, 실패 0** (G1 매출액 24, G2 해지 10, G3 자금조달 8, G4 설비투자 비교 12, G5 메타모픽 4, G6 정책·정보한계 10).
- G5 메타모픽에서 패러프레이즈·기업명 별칭(현대차/현대자동차 등)을 바꿔도 수치뿐 아니라 **접수번호까지 동일**했다. 매출 경로에는 문구 과적합이 없다는 뜻.
- G6 정책·정보한계 10건이 전부 0.0초 — 모델 호출 전에 차단된다.
- 후처리 필터 오제거 검증(L5): 실제 답변 102건에 재적용해 변경 1건, 그 1건이 의도한 제거였다. 오제거 0건.
- 회귀 테스트 617개가 DB만 있으면 모델 호출 없이 돈다(`tests/stub_client.py` 주입, 임베딩 자동 비활성).

### 안된 점 / 고친 것

- **해지 질의의 골든셋 문구 과적합(심각)**. `deterministic_termination`이 따옴표로 감싼 계약명이 있어야 발동하는 정규식이라, 주최 측 템플릿("OO기업이 2025년에 체결한 주요 계약 이후 해지된 계약이 존재하는가?")은 전부 모델 경로로 빠졌다. 그동안 해지가 **없는** 기업 하나만 검증해 "없음" 기본값으로 맞고 있었다. 해지가 실재하는 5개사로 돌리자 매 실행 5사 중 2사 오답, 실패 기업은 매번 달랐다(모델 비결정성). 두산퓨얼셀은 두 번 다 예산 한계(90.1초 / 82.1초)까지 갔다 — 평가 타임아웃 위험. `deterministic_termination_scan` 신설로 positive 5/5, negative 5/5, 응답 0.0~0.1초.
- **`'예상되는 매출액'` 활용형 누수**. `validated_disclosed_facts`가 `'예상 매출액'`은 막았지만 `되는` 때문에 lookahead가 어긋나 통과시켰다. 24개사 스윕에서 1건(세아베스틸지주). 값과 접수번호는 정확했고 수식어만 남았다. 활용형 `되는/된/되었던/되어 있는/하는/치`까지 제거.
- **체커 자체의 오탐 4종**. 접수번호를 금액으로 오인(14자리), 계산된 차액을 "근거에 없는 수치"로 판정, 승자 추출 창 70자가 상대 기업 숫자를 집음, 문장 첫머리 기업명을 승자로 오인. 12건 전부 수기 검산하니 시스템은 정확했다. → [[self-authored-eval-overfitting]]

### 알려진 한계

- 규칙이 확정하는 조회는 재현되지만, 모델이 쓰는 서술·비교·나열은 호출마다 표현과 일부 수치가 달라진다.
- 같은 달 같은 상대방과 맺은 계약이 여럿이면 질문만으로 건을 특정하지 못할 수 있다.
- 수치 검증이 근거 값·단위 환산·합차만 허용하므로 그 밖의 계산 결과는 "(근거 표의 값과 맞지 않아 표시하지 않음)"으로 지워진다.
- 3차 검증의 독립 SQL 오라클도 저자가 스키마를 읽고 썼으므로 파싱 단계의 오해까지는 함께 틀릴 수 있다.
- L5 후처리 검증은 최종 답변 기준이라 모델 원문 전체를 덮지 못한다(서버가 필터 적용 전 원문을 남기지 않음).
- G4 설비투자 금액에는 절대 정답 오라클이 없다. 자기일관성과 순서 대칭만 봤고 절대값은 단위 테스트 4건이 고정한다.

## 5. 재사용 가능한 것

- **다단 파이프라인 골격**: `src/agent/orchestrator.py` — 정책 판정 → 결정론 경로 → 게이트 → 분해 → 사전 검색 → 도구 루프 → 검증. 근거 필수 QA에 그대로 옮길 수 있는 구조. → [[deterministic-rule-path]]
- **항상 200을 돌려주는 평가 API 계약**: 5필드 고정 스키마 + 부재 종류별 문장 분기. 평가 하네스 무응답 처리를 막는 패턴. (`API_SPEC.md`)
- **금액 정규화 대조 검증**: 표 셀에 단위를 곱해 원 단위 정수로 정규화한 뒤 답변 수치와 대조, 두 값의 합·차만 추가 허용. → [[grounded-answer-verification]]
- **저자 편향을 줄인 검증 하네스**: `runs/sweep.py`, `runs/filter_diff.py` (로컬 전용, `.gitignore` 대상이라 제출 저장소에는 없음). 질의 인스턴스를 DB가 고르고 정답을 독립 SQL로 만드는 설계. → [[self-authored-eval-overfitting]]
- **정정 체인 모델링**: `superseded_by`/`supersedes` + `corrections` 분리. 이력이 있는 문서 데이터 전반에 적용 가능. → [[disclosure-correction-chain]]
- **모델 스텁 회귀 테스트**: `tests/stub_client.py`로 API 키 없이 617개 테스트 실행.
- **컨테이너 보안 기본값**: 비루트 사용자, 읽기 전용 파일시스템, 읽기 전용 DB 마운트, `no-new-privileges`, `/health` 검사.

## 면접 준비

### 한 문장 소개

DART 공시 4,204건에 자연어로 물으면 근거 접수번호가 붙은 답을 돌려주는 API를 만들었습니다. 수치·날짜·상대방처럼 확정할 수 있는 사실은 SQL 규칙 73종이 표에서 직접 꺼내고 모델은 계산하지 않게 했으며, 답에 적힌 숫자와 접수번호는 근거와 대조해 검증합니다. 저자 편향을 줄인 3차 실전 검증에서 74문항을 모두 통과했고, 결과(수상 여부)는 자료에 없습니다.

### 기술 스택과 선택 이유

| 기술 | 역할 | 왜 이걸 썼나 | 대안과 포기한 것 |
|---|---|---|---|
| HyperCLOVA X HCX-005 | 도구 선택(function calling), 근거 기반 서술 | 대회 규칙이 HyperCLOVA X만 허용해서, 다른 모델을 쓰면 평가 대상에서 빠집니다 | 선택지 없음 |

### 고민한 점

- **검색을 잘할 것인가, 규칙으로 확정할 것인가** — 초기 설계는 목차 기반 섹션 분할에 섹션 임베딩과 하이브리드 리랭킹을 얹는 쪽이었는데, 만들어 보니 수치 질문에서 근거를 골라 오는 일이 계속 불안했습니다. 최종에서는 FTS5 3종이 런타임 검색을 맡고 임베딩은 목차 제목 311건으로 줄었으며, 대신 표를 격자 65만여 행으로 적재해 규칙이 값을 직접 꺼내게 했습니다. 도구는 11종에서 36종으로, 결정론 경로는 73종으로 늘었고, "수치 정확도를 임베딩에 맡기지 않는다"는 초기 전제만 그대로 남았습니다.
- **골든셋을 직접 만들어도 되는가** — 자체 생성 골든셋(`goldenset/generate.py`)과 `evalkit` 채점기로 평가하다가 과적합을 발견했습니다. 1·2차 세트 14문항이 과제소개자료 p7의 참고 질의 6종 템플릿에 기업 하나씩 끼운 것이었습니다. 3차에서는 질의 인스턴스를 DB가 SQL로 고르고, 정답을 에이전트 도구가 아닌 독립 SQL로 만들고, 오라클이 없는 경우에는 자기일관성과 메타모픽으로 판정하게 바꿨습니다. 회귀 테스트 617개는 고정물로 남겼습니다.
- **해지 질의를 규칙으로 잡을 것인가 모델에 맡길 것인가** — `deterministic_termination`이 따옴표로 감싼 계약명을 요구하는 정규식이라 주최 측 템플릿은 전부 모델 경로로 빠지고 있었습니다. 그동안 해지가 없는 기업 하나만 검증해서 "없음" 기본값으로 맞고 있었던 것인데, 해지가 실재하는 5개사로 돌려 보니 매 실행 5사 중 2사가 틀렸고 실패 기업이 매번 달랐습니다. 두산퓨얼셀은 두 번 다 예산 한계(90.1초, 82.1초)까지 갔습니다. 존재 여부는 구조화 행으로 확정할 수 있다고 판단해 `deterministic_termination_scan`을 새로 만들었고 positive 5/5, negative 5/5, 응답 0.0~0.1초가 됐습니다.
- **자동 검사기를 믿을 것인가** — G4 설비투자 비교가 처음에는 대량 실패로 나와서 시스템을 의심했는데, 12건을 전부 손으로 검산해 보니 시스템이 다 맞고 체커가 틀린 것이었습니다. 접수번호 14자리를 금액으로 오인하고, 계산된 차액을 근거에 없는 수치로 판정하고, 승자 추출 창 70자가 상대 기업 숫자를 집고, 문장 첫머리 기업명을 승자로 오인하는 네 가지였습니다. 자동 검사도 저자가 쓰면 틀린다는 것이 이때 남긴 기록입니다.
- **문장을 통째로 지우는 필터를 넣을 것인가** — `strip_external_referrals`는 오차단이 오답보다 나쁘다고 보고 따로 확인했습니다. 실제 답변 102건에 세 필터를 다시 적용해 보니 변경이 1건이고 그 1건이 의도한 제거였습니다. 다만 이 검증은 최종 답변 기준이라 모델 원문 전체를 덮지 못하는데, 서버가 필터 적용 전 원문을 남기지 않기 때문입니다.

### 예상 질문

1. **Q:** (L1) 이 시스템을 RAG라고 부르실 수 있나요? 일반적인 벡터DB 기반 RAG와 무엇이 다른지 설명해 주시겠어요?
   **A:** 근거를 찾아 모델에 넣는다는 점은 같지만, 근거를 고르는 주된 수단이 벡터 유사도가 아닙니다. 코퍼스가 70개사 4,204건으로 유한하고 고정돼 있어서 질의 시점에 검색하는 대신 미리 구조화했습니다. 정형 테이블과 FTS5 3종이 런타임 검색을 맡고, 임베딩은 정기보고서 목차 제목 311건에만 씁니다. 수치·날짜·상대방·정정 이력은 아예 검색하지 않고 SQL 규칙 73종이 표에서 꺼냅니다. 수치 정확도를 임베딩에 맡기지 않으려고 그렇게 했습니다.
   **꼬리:** 코퍼스가 400만 건이고 매일 새 공시가 들어온다면 이 설계에서 무엇을 먼저 바꾸시겠어요?
   **틀리기 쉬운 답:** "벡터DB를 안 썼으니 RAG가 아니다"라고 답하는 경우가 있는데, 실제로는 검색해서 근거를 넣는 방식은 그대로이고 검색기의 종류만 바뀐 것입니다.
2. **Q:** (L2) 규칙 경로와 모델 경로 중 어느 쪽이 답했느냐에 따라 시스템의 성질이 어떻게 달라지나요? 두 경로는 어떻게 이어 붙이셨나요?
   **A:** 규칙이 확정한 조회는 호출마다 같은 답이 나오고 0초 안에 접수번호와 함께 돌아옵니다. 모델이 쓰는 서술·비교·나열은 호출마다 표현과 일부 수치가 달라지는데, 해지 질의에서 실패 기업이 매 실행 바뀌는 형태로 그 비결정성이 실제로 드러났습니다. 두 경로는 게이트로 잇습니다. 규칙의 답이 질문을 다 덮는지, 물은 항목마다 대상이 있는지, 두 회사를 물었으면 둘 다 있는지 확인하고, 일부만 덮으면 그 결과를 확정 사실표로 모델에 넘겨 답변 앞에 그대로 남깁니다. 규칙이 이미 확정한 값을 버리지 않는 것이 이 게이트의 목적입니다.
   **꼬리:** 게이트가 "다 덮었다"고 잘못 판정하면 무슨 일이 생기나요?
   **틀리기 쉬운 답:** "규칙이 실패하면 모델이 알아서 보완한다"고 답하는 경우가 있는데, 실제로는 해지 질의에서 규칙이 조용히 빠지고 모델이 "해지 없음"을 답한 일이 있었습니다.
3. **Q:** (L2) 평가 API가 어떤 입력에도 HTTP 200과 5필드를 돌려주게 설계하셨는데, 오류를 오류로 알리지 않는 방식을 왜 고르셨나요?
   **A:** 평가 하네스가 JSON 파싱에 실패하면 그 문항이 무응답 처리되기 때문입니다. 내부 예외, 모델 호출 실패, 문항 예산 80초 초과까지 전부 한계 응답으로 되돌립니다. 대신 부재의 종류를 문장으로 구분합니다. 사실 없음, 공시유보, 시간 예산 초과, 모델 오류, 정책 차단, 범위 밖이 서로 다른 문장이고, 근거가 없는 한계 응답에는 접수번호를 붙이지 않습니다. 상태 코드로 알리던 것을 본문 문장으로 옮긴 셈입니다.
   **꼬리:** 평가용이 아니라 사내 서비스로 낸다면 이 계약을 그대로 두시겠어요? 모니터링은 어떻게 하시겠어요?
   **틀리기 쉬운 답:** "항상 200이면 클라이언트가 편하다"고 답하는 경우가 있는데, 실제로는 편의 때문이 아니라 무응답 처리를 막으려는 선택이었고 그 대가로 장애가 응답 본문에 숨습니다.
4. **Q:** (L3) 74/74라는 숫자는 면접에서 어디까지 주장하실 수 있나요?
   **A:** 저자 편향을 줄인 3차 검증의 전체 스윕에서 실패가 0이었다는 데까지입니다. 정확도 100%라고 말하면 안 된다고 생각합니다. 남은 구멍이 넷 있습니다. 3차 방법론도 제가 설계하고 실행했고 독립 SQL 오라클도 제가 같은 스키마 이해로 썼으므로 파싱 단계의 오해는 함께 틀릴 수 있습니다. G4 설비투자 금액에는 절대 정답 오라클이 없어 자기일관성과 순서 대칭만 봤고 절대값은 단위 테스트 4건이 고정합니다. L5 후처리 검증은 최종 답변 기준이라 모델 원문 전체를 덮지 못합니다. 74문항도 6개 그룹에 걸친 표본이지 코퍼스 전체가 아닙니다. 원자료에는 진짜 독립을 원하면 구현을 보지 않은 별도 에이전트에게 질의를 쓰게 하는 것이 남은 카드라고 적어 두었습니다.
   **꼬리:** 그 별도 에이전트 방식에도 남는 편향은 무엇일까요?
   **틀리기 쉬운 답:** "전수 회귀 617개가 통과하니 안전하다"고 답하는 경우가 있는데, 실제로는 617개가 모델 스텁으로 도는 테스트라 모델이 쓰는 문장을 검사하지 않습니다.
5. **Q:** (L3) 이 시스템이 가장 먼저 무너지는 질문 유형은 무엇인가요?
   **A:** 규칙이 덮지 못하고 모델이 써야 하는 서술·비교·여러 건 나열입니다. 같은 달 같은 상대방과 맺은 계약이 여럿이면 질문만으로 건을 특정하지 못하고, 근거 값·단위 환산·합차를 벗어난 계산은 검증에서 지워져 "(근거 표의 값과 맞지 않아 표시하지 않음)"이 됩니다. 시간 쪽으로는 모델 경로가 길어지는 질문이 80초 예산에 닿는데, 해지 질의를 고치기 전에 두산퓨얼셀이 두 번 다 90초대까지 갔던 것이 그 사례입니다. 이건 정확도가 아니라 타임아웃으로 나타나는 실패입니다.
   **꼬리:** 예산 80초를 늘리는 것과 결정론 경로를 하나 더 만드는 것 중 어느 쪽을 택하시겠어요? 판단 근거는 무엇인가요?
   **틀리기 쉬운 답:** "느린 건 성능 문제라 인프라로 해결된다"고 답하는 경우가 있는데, 실제로는 해지 질의의 지연이 규칙이 빠져 모델이 헤맨 결과였고 규칙을 하나 추가하자 90초가 0.1초가 됐습니다.

### 솔직하게 말할 것

- 결과(수상 여부)가 자료에 없습니다.
- `retrieval/`의 hybrid·vector_store는 파일럿 잔존이라 런타임에서 쓰이지 않습니다. 저장소에 코드가 있다고 해서 하이브리드 검색을 구현해 서비스했다고 말씀드릴 수는 없습니다.
- 3차 검증 하네스(`runs/sweep.py`, `runs/filter_diff.py`)와 검증 보고서는 로컬 전용이고 `.gitignore` 대상이라 제출 저장소에 없습니다. 검증 과정을 보여 달라고 하시면 코드로 보여 드릴 수 없습니다.
