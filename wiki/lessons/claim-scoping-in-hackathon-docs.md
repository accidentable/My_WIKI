# 주장의 범위를 좁히는 개정이 자료를 더 강하게 만든다

## 1. 교훈 한 문장

해커톤 기획서의 개정은 주장을 키우는 방향이 아니라, 각 근거가 실제로 뒷받침하는 범위까지 주장을 줄이고 그 한계를 문서에 적어 두는 방향으로 갈 때 자료가 더 단단해진다.

## 2. 근거가 된 사례

- [[finance-ai-2026-subscription-cut]], 2026 금융 AI Challenge 아이디어 설명서 ver2. 부록에 ver1에서 정정·보강한 항목이 표로 남아 있다.

ver1 → ver2에서 실제로 좁힌 것들.

| 항목 | 좁힌 방향 |
|---|---|
| 국내 고액 청구 사례 | SBS 원보도를 확보해 이메일 18건·사흘로 정정하고, 승인 거절 사실과 사업자의 해결 완료 입장을 반영. "251억 원 결제 피해"로 쓰지 않음 |
| 해외 8만 달러 사례 | 날짜·금액·출처를 명시하고 "Reddit 이용자 신고 기반 보도"라는 확인 한계를 표시 |
| 구독 분쟁 근거 | FTC 소송 제기 자료를 쓰되 당국의 주장과 확정 판결을 구분 |
| 민원 88% 증가 | "전체 신용카드 민원 2022~2025년 증가율"로 범위를 명시. 해외결제·AI 과금만의 수치가 아님 |
| 승인 없는 사건 | "승인 없음 → 카드사 경로 불가" 일괄 규칙 제거, 추가 결제 방지 상담과 차지백 검토를 분리 |
| 기한·발신자 판단 | 일괄 날짜 계산과 도메인만으로 진위 확정하는 규칙 제거 |
| 예산 상한 | "예산 상한은 작동하지 않는다"는 일반화를 버리고 알림 예산과 Spend cap을 구분 |
| 평가 지표 | 환불 성공률 대신 접수 준비 품질(잘못된 단정 0건, 사실 보존, 근거 연결)로 변경 |
| 차별성 | "최초"·독점 기술 주장을 빼고, 기존 Visa 분쟁 도구의 존재를 명시한 뒤 접수 전 구간을 진입점으로 재정의 |

같은 태도가 제품 동작에도 옮겨 갔다. 확정할 수 없는 것은 보류하고, 사유코드는 후보로만 표시하고, 지원 범위는 화면에 적는다. 기획서에서 근거 범위를 따지는 훈련이 그대로 판단 규칙이 된 셈이다.

보강 방향도 함께 있었다. 범위를 좁히는 대신 각 사례에 출처 URL과 확인일을 붙이고, 규정 레코드에 문서 버전·적용일·적용 조건을 필드로 두었다. [[bc-card-bigdata-2026]]에서도 외부 데이터에 수집일을 붙여 다뤘으므로, 출처·조회일 기록은 두 프로젝트에 걸친 습관으로 보인다.

- [[im-challenge-daegu-2026-sns-menu]], SNS 신메뉴 AI 컨설팅. 여기서는 개정이 아니라 **문서를 쓰는 시점부터** 같은 태도가 들어갔고, 좁히는 대상이 세 층으로 나뉜다.

| 좁힌 층 | 방식 |
|---|---|
| 문서의 지위 | 기획서 머리에 "구현 전 기획이며 이미 개발된 기능이 아니다", 인계 문서에 "기능 명세는 구현할 대상이며 완료 보고가 아니다"를 명시 |
| 인용한 주장 | "AI 때문에 유행 주기가 6개월에서 7일~1개월로 줄었다"를 검증된 인과로 쓰지 않음. "모든 유행이 서울에서 시작해 대구로 간다"도 법칙이 아닌 가설로 표기 |
| 사례의 지위 | 두쫀쿠·버터떡·피자설기는 아이디어 설명용 사례일 뿐, 현재 유행 판정이나 자동 탐지가 작동한다는 뜻이 아니라고 못박음 |
| 차별성 | 경쟁 서비스 9종을 먼저 조사해 "AI 메뉴 추천 자체가 최초"·"원가 계산으로 독창적"·"지역명을 붙여서 차별화" 주장을 모두 배제하고, 실행률·거절 사유·재판매·준비 부담으로 검증하겠다고 씀 |
| 지표 | 초기 인터뷰 5~10개 가게 결과는 탐색적 검증이며 보편적 매출 상승률로 일반화하지 않음. 분모·측정 기간·표본 수를 함께 표시 |
| 데이터 해석 | 거주인구를 방문객으로, 게시물 수를 시장 수요로, 업종 분류 집계를 영업 확인이나 시장 규모로 바꾸지 않음 |

구현 쪽에도 같은 규칙이 이어졌다. 키가 없으면 고정 샘플을 실제 AI 생성처럼 보여주지 않고, `dataMode`/`acquisitionMethod=demo`/`generationMode`로 데모와 실제를 DB·API 수준에서 나눴다. 자기 조사 문서의 표에서 "7일 규칙" 열이 실제로는 14일 규칙 값임을 구현 단계에서 찾아내 기록한 것도 같은 습관이다.

세 프로젝트를 겹쳐 보면 공통 형태가 보인다. **주장을 줄인 자리에 검증 절차를 넣는다.** 금융 AI는 환불 성공률 대신 접수 준비 품질로 지표를 바꿨고, SNS 신메뉴는 유행 예측 대신 "미리 잡을 수 없는 유행(스파이크형)을 골라 내는" 필터를 넣었다.

## 3. 다음에 어떻게 적용할 것인가

- 기획서를 고칠 때 "무엇을 더 넣을까"보다 "이 문장이 저 출처로 정말 뒷받침되나"를 먼저 본다. 뒷받침이 부족하면 문장을 줄이고 한계를 한 줄 적는다.
- 인용한 수치마다 모집단을 명시한다. 전체 통계를 세부 영역의 증가율처럼 쓰지 않는다.
- 보도 기반 사례는 "보도된 주장"과 "확정된 사실"을 표기로 구분한다.
- 목표 지표는 달성 실적이 아님을 표에 명시하고, 검증 가능한 대리 지표(준비 품질)로 바꿀 수 있는지 검토한다.
- 개정할 때 정정 내역 표를 문서 부록에 남긴다. 심사·회고·위키 반영 모두에서 이 표가 가장 쓸모 있었다.
