# My_WIKI: 해커톤 경험을 면접 언어로 정리하는 LLM 위키

해커톤 14회와 여러 프로젝트에서 쌓인 자료를 LLM이 규칙에 따라 위키로 정리하고, 그 결과를 면접 준비용 사이트로 만드는 저장소입니다. 사람은 원자료를 넣고 질문만 하고, 문서를 쓰고 고치는 일은 LLM(Claude Code, Codex)이 맡습니다.

- 사이트: https://hackathon-wiki-rho.vercel.app/
- 현재 규모: 프로젝트 문서 14개, 개념 문서 49개, 교훈 문서 4개, 처리한 원자료 35건 (2026-09-22 기준)

## 왜 만들었나

해커톤을 열네 번 하고 나니 README, 기획서, 발표 대본, AI와 나눈 대화 기록이 폴더마다 흩어져 있었습니다. 그런데 정작 "그 프로젝트에서 왜 그 기술을 골랐는지"를 물으면 바로 답하지 못하는 경우가 많았습니다. 해커톤에서는 AI가 대신 짜고 넘어간 부분이 많았기 때문입니다. 그래서 LLM에게 계속 구현만 시키는 데서 한 발 나아가, 각 프로젝트의 아키텍처를 개발자 눈으로 다시 점검하고 다음에 만들 때 조심할 것을 정리해 두는 곳이 필요하다고 생각했습니다.

형식은 Andrej Karpathy가 2026년 4월에 올린 ["LLM Knowledge Bases"](https://x.com/karpathy/status/2039805659525644595) 글에서 가져왔습니다. 사람은 `raw/`에 원자료만 넣고, LLM이 그것을 `wiki/`의 마크다운 문서로 점진적으로 컴파일하며, 규칙은 `CLAUDE.md`나 `AGENTS.md` 같은 파일 하나에 두고, 질문은 원자료 대신 위키에 한다는 틀입니다.

다만 이 저장소의 목적은 지식을 쌓는 데서 끝나지 않습니다. 해커톤을 거듭하면서 구현을 LLM에 기대는 정도가 지나치다고 느꼈고, 그 습관을 떨쳐내려면 LLM이 대신 짜고 넘어간 것을 제가 다시 설명할 수 있어야 한다고 생각했습니다. 그래서 카파시의 틀 위에 면접 준비라는 목적을 얹었습니다. 모든 개념 문서에 "설명할 수 있어야 하는 것"과 확인 질문을 두고, 프로젝트 문서에 "솔직하게 말할 것" 절을 둔 이유가 그것입니다.

## 구성

```
raw/            사람이 넣는 원자료. LLM은 읽기만 하고 절대 고치지 않음
raw/done/       처리가 끝난 원자료 (35건)
wiki/index.md   전체 목차. 모든 작업은 여기서 시작
wiki/projects/  프로젝트 하나당 문서 하나 (14개)
wiki/concepts/  기술·도메인 개념 문서 (49개)
wiki/lessons/   여러 프로젝트에 걸친 교훈 (4개)
log.md          무엇을 언제 반영했는지 시간순 기록. 추가만 하고 고치지 않음
wiki-rules.md   운영 규칙 14개 절. 어떤 도구든 이 파일을 먼저 읽음
tools/lint.py   점검 스크립트 (결정적 검사 + OpenAI API 판단 검사)
tools/build_site.py  위키를 한 장짜리 면접 노트 사이트로 빌드
.claude/agents/ Claude Code 서브에이전트 (ingest, lint)
AGENTS.md       Codex용 같은 규칙
```

## 원자료, 사실, 내 생각, LLM의 해석을 어떻게 구분하는가

이 위키에서 가장 신경 쓴 부분입니다. 처음에는 "원자료에 없는 사실을 지어내지 않는다"는 규칙 하나면 될 줄 알았는데, 첫 점검에서 지적 8건 중 4건이 다른 종류의 왜곡이었습니다. 원자료가 "검토했다", "생각한다"라고 쓴 것을 위키가 "기각했다", "이다"로 바꿔 놓은 것입니다. 문장을 매끄럽게 다듬는 과정에서 조심스러움이 깎이는 것이 가장 흔한 왜곡이라는 것을 그때 알았고, 개별 문서를 고치는 대신 규칙으로 대응했습니다.

지금 지키는 구분은 이렇습니다.

- `raw/`는 사람이 쓴 원자료이고 LLM은 수정하지 않습니다. 처리가 끝나면 `raw/done/`으로 옮기기만 합니다.
- 위키 문서는 머리말에 `sources:`로 근거가 된 원자료 파일을 적습니다. 점검 스크립트가 이 경로가 실재하는지 확인합니다.
- 원자료에 없는 추론은 "(추정)"이라고 표시합니다.
- 원자료의 확신 수준을 그대로 보존합니다. 원자료가 밝힌 한계와 단서 조항은 결론 문장과 같은 단락에 함께 옮깁니다.
- 서로 모순되는 서술을 발견하면 지우지 않고, 두 서술과 출처를 남긴 채 문서 상단에 `⚠️ 모순` 블록으로 표시합니다.
- 면접 준비 표의 "왜 이걸 썼나" 칸은 원자료에 근거가 없으면 "이유 자료에 없음"으로 비워 둡니다. 비워진 칸은 제가 직접 채울 자리이고, 지어내는 것보다 비워 두는 편이 낫다고 판단했습니다.

## 넣기 · 묻기 · 점검

작업은 세 가지뿐입니다.

**넣기(ingest).** `raw/`에 파일이 생기면 서브에이전트가 인덱스를 읽고, 원자료를 읽고, 건드릴 기존 문서 1~4개만 골라 갱신하거나 새 문서를 만듭니다. 새 개념이 나와도 한 문단 이상 쓸 내용이 있을 때만 concept 문서를 만들고, 여러 프로젝트에 걸쳐 반복되는 패턴이 보이면 lesson 문서를 만듭니다. 끝나면 인덱스와 로그를 갱신하고 원자료를 `done/`으로 옮깁니다.

**묻기(query).** 위키 전체를 읽지 않고 인덱스에서 관련 문서만 골라 답합니다. 위키에 없는 내용이면 "위키에 없음"이라고 말하게 했습니다. 답이 여러 문서를 엮은 새 종합이면 lesson이나 concept로 저장할지 제안합니다.

**점검(lint).** `tools/lint.py`가 두 층으로 검사합니다. 1층은 코드로 하는 결정적 검사(깨진 링크, 인덱스 누락, 머리말 형식, sources 경로)이고, 2층은 OpenAI API로 하는 판단 검사(중복 개념, 모순 서술, 원자료 대비 누락·왜곡)입니다. GitHub Actions가 push마다 1층을 돌리고 주 1회 2층까지 돌려 결과를 `log.md`에 커밋합니다. 점검은 지적만 하고 내용을 자동 수정하지 않습니다.

Claude Code는 `.claude/agents/`의 ingest·lint 서브에이전트로, Codex는 `AGENTS.md`로 같은 규칙을 따릅니다. 두 도구가 같은 저장소를 고치므로 시작할 때 pull, 끝날 때 바로 push하는 것을 규칙에 넣었습니다.

## 실제 사례: 타코 트럼프 코드 한 장이 어떻게 정리됐나

원자료 한 건이 어떻게 위키가 되는지 [타코 트럼프](https://github.com/accidentable/tacotrump) 사례로 보이면 이렇습니다.

1. 저장소의 `index.html` 메타, git log 43줄, 파일 목록, 주요 소스 코드를 뽑은 코드 개요 한 장을 `raw/`에 넣었습니다.
2. 넣기 에이전트가 프로젝트 문서 `taco-index-2026-03` 하나와 개념 문서 네 개를 만들었습니다. 지표를 safe·redline 사이 선형 보간으로 정규화해 합산하는 방식, 무료 시장 데이터를 직접 호출하고 실패를 fallback으로 덮는 방식, Vercel 파이썬 크론과 Redis로 상태가 바뀔 때만 웹푸시를 보내는 방식, 그리고 FastAPI 로컬판과 서버리스판을 복제해 두었을 때 생기는 로직 표류입니다.
3. 정리 과정에서 코드의 어긋남이 드러났습니다. 로컬판은 지표 다섯 개만 합산하면서 레벨 경계는 여섯 개 기준을 쓰고 있었고, 점수 함수의 주석과 실제 상수가 달랐습니다. 이어진 점검에서는 크론 함수 설명("5분마다")과 실제 설정(매시간)이 다른 것도 잡혔습니다.
4. 프로젝트 문서의 면접 준비 절에는 "6일 43커밋으로 혼자 만들면서 무엇을 의도적으로 안 했고 그 대가가 어디에 나타났나" 같은 예상 질문과, 해커톤 출품작이 아니라는 것부터 레드라인 값의 근거가 없다는 것까지 "솔직하게 말할 것" 일곱 항목이 들어갔습니다.
5. 개념 문서 "백엔드 이중 구조"의 "다음에 어떻게 할 것인가"에는 순수 로직을 프레임워크 없는 모듈 하나로 빼서 양쪽이 import할 것, 그게 안 되면 같은 입력에 같은 점수를 내는지 확인하는 테스트 하나라도 둘 것이 적혔습니다.

원자료가 2026-09-22 시점의 스냅샷이라 이후 커밋(공개 API, AWS 이전)은 반영되어 있지 않습니다. 이것도 이 방식의 성질입니다. 위키는 넣은 만큼만 압니다.

## 프로젝트 사이를 잇는 문서

개념 문서마다 "어디서 썼는가" 절이 있어 같은 기술을 쓴 프로젝트가 서로 연결됩니다. 예를 들어 유행 수명을 재는 개념은 BC카드 빅데이터 해커톤에서 처음 나왔고, 뒤에 뉴스빅데이터 해커톤과 대구 신메뉴 프로젝트 사례가 같은 문서에 붙었습니다.

교훈 문서 네 개는 프로젝트 두 개 이상에서 반복된 패턴만 담습니다.

- 기획서 개정은 주장을 키우지 말고 근거가 받쳐 주는 범위까지 좁혀라 (금융 AI Challenge, 대구 신메뉴 프로젝트)
- 효과는 대조군을 직접 돌려 말하고, 어느 실험의 수치인지 붙여 말하라 (Blockthon Memory Market)
- 내가 만든 평가는 내가 아는 실패만 잡는다 (미래에셋 공시 에이전트)
- 기술보다 사용자 문제를 먼저 적어라 (원티드 면접 AI, 미드나잇 해커톤 기획 대화)

## 정리된 지식을 어떻게 쓰는가

지금 구현된 활용처는 면접 준비입니다. 프로젝트 문서에는 한 문장 소개, 기술 선택 이유 표, 아키텍처 절, 고민한 점, 예상 질문, 솔직하게 말할 것이 들어가고, 개념 문서에는 CS 과목과 이어지는 학습 절이 들어갑니다. 질문은 L1 개념, L2 이 프로젝트에서의 판단, L3 규모가 커지거나 조건이 바뀌면 어디가 깨지는가의 세 층으로 쓰고, 꼬리질문과 틀리기 쉬운 답을 같이 둡니다. 답은 반드시 문서 본문이나 원자료로 뒷받침되어야 하고, 점검이 이것을 확인합니다.

사이트(`tools/build_site.py`)는 이 절들을 파싱해 홈 → 프로젝트 → 개념 순서로 보여 주고, 아키텍처 절을 그림으로 그리며, 이해도 기록을 브라우저에 저장합니다. 파일 하나로 빌드되어 Vercel에 그대로 올라갑니다.

다음 프로젝트를 설계할 때 이 위키를 실제로 참고한 기록은 아직 없습니다. 위키 문서가 모두 2026년 9월 22일에 만들어졌고 그 뒤로 새 프로젝트를 시작하지 않았기 때문입니다. Codex 규칙에는 다른 프로젝트 폴더에서 코딩을 마무리할 때 회고를 `raw/`에 넣자고 제안하도록 적어 두었습니다.

## 현재 구현된 것과 앞으로의 목표

구현된 것은 위에 적은 규칙 14개 절, 넣기·묻기·점검 흐름, 두 층 점검 스크립트와 CI, 면접 노트 사이트, Notion 해커톤 트래커와의 역할 분담(대회 정보의 원본은 Notion, 무엇을 만들었는가의 원본은 위키)입니다.

앞으로 하려는 것은 이 정도로 생각하고 있습니다.

- 위키에 정리된 "다음에 어떻게 할 것인가"를 새 프로젝트 시작 시점에 자동으로 꺼내 보는 흐름
- 프로젝트가 끝날 때 회고를 `raw/`에 넣는 습관을 도구로 강제하기
- 점검이 지적한 것 중 보류한 항목(범위 한정 표현, 한계 병기)을 처리하기

## 한계

- 위키 문서 대부분이 2026-09-22 하루에 만들어졌습니다. 서브에이전트를 여러 개 병렬로 돌려 프로젝트 10개를 한 번에 넣었기 때문인데, 그만큼 사람이 한 건씩 검토한 밀도는 낮습니다.
- 원자료 자체가 AI와 함께 쓴 README와 기획서인 경우가 많아, 위키가 보존하는 "확신 수준"도 그 문서의 것입니다. 원자료가 부풀려 썼다면 위키도 그대로 옮깁니다.
- 판단 검사는 OpenAI API에 의존하고 결과가 실행마다 달라질 수 있습니다. 결정적 검사만 CI 실패 조건으로 씁니다.
- 위키에 담긴 것은 제 경험이라, 공개 사이트에는 프로젝트 세부와 솔직한 자기 평가가 그대로 올라가 있습니다.

## 실행법

```bash
# 결정적 검사만
python tools/lint.py

# 판단 검사까지 (OPENAI_API_KEY, LINT_MODEL 필요)
python tools/lint.py --llm

# 사이트 빌드 → site/index.html
python tools/build_site.py
```

원자료를 넣으려면 `raw/`에 마크다운이나 텍스트 파일을 두고, Claude Code나 Codex에서 "반영해"라고 하면 됩니다. 규칙은 `wiki-rules.md`에 있습니다.
